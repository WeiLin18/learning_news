1. **[React][工程知識][實務指南] Stop Writing useMemo and useCallback：React Compiler 遷移實戰指南**
   一份步驟式的遷移教學，不是原則性描述：先確保 git 狀態乾淨、開專屬分支（不要在 main 上遷移）；用 `eslint-plugin-react-hooks` 先掃出違反 Rules of React 的地方（不純的元件、錯誤的 hook 用法）；React Compiler 內建相容性檢查器，會列出哪些寫法會擋住安全的自動優化；最後才移除手動 `useMemo`/`useCallback`,交給編譯器處理。範例對比：
   ```jsx
   // 遷移前：手動判斷要不要 memo
   const sorted = useMemo(() => items.sort(cmp), [items]);
   // 遷移後：直接寫原始邏輯,依賴 compiler babel/vite plugin 自動優化
   const sorted = items.sort(cmp);
   ```
   建議策略是「先在新程式碼採用,再逐步擴大到既有 codebase」,不要一次全專案遷移。
   來源：個人技術部落格（開放搜尋補充，作者 Adeel Imran）｜https://adeelhere.com/blog/2026-03-24-react-compiler-migration-guide
   發布日期：2026-03-24（較早，約 4.5 個月前）

2. **[React][RSC][工程知識][實務指南] React Server Components in 2026：Patterns, Pitfalls, and When to Actually Use Them**
   拆解團隊在 RSC 上真正會踩的坑,而不是重複介紹 RSC 是什麼：把 server-only 模組（例如 `fs`、環境變數 secret）不小心 import 進會被打進 client bundle 的檔案,會造成難以除錯的 build 錯誤——文中建議用 `server-only` 套件在 build 期就直接擋下這種誤用。另外指出很多 proxy/load balancer 預設會 buffer 輸出,導致 React 的串流失效,可以用這行指令驗證正式環境是否真的在串流：
   ```bash
   curl -N https://your-app.com/dashboard | head -c 100
   # 應該看到 HTML 片段陸續到達,不是一次性全部出現
   ```
   還點名一個常見反模式「爆米花效應」（popcorn effect）：每個小元素都各自包一層 Suspense,結果畫面在短時間內連續跳出一堆 skeleton→內容的轉換,體感比單一稍長的載入狀態更差。
   來源：jsmanifest 個人技術部落格（開放搜尋補充）｜https://jsmanifest.com/react-server-components-patterns-pitfalls-2026
   發布日期：2026 年（確切日期不確定，建議上線前再次核對）

3. **[資安][工程知識][實務指南] Joyfill npm 套件遭植入 RAT：供應鏈攻擊警示與應對步驟**
   `@joyfill/layouts` 與 `@joyfill/components` 的兩個 beta 版本被植入惡意程式,特別之處是**惡意程式碼在套件被 import 時才觸發**,不是傳統在安裝階段的 postinstall script——這代表單純用 `npm install --ignore-scripts` 完全防不住。惡意程式還用 Tron/Aptos/BNB Smart Chain 這幾條區塊鏈當作「死信箱」接收指令,讓攻擊者能隨時換基礎設施而不用更新套件本身。具體應對步驟：
   ```bash
   npm ls @joyfill/layouts @joyfill/components   # 先確認專案有沒有用到
   # 若版本 >= @joyfill/layouts@0.1.2-2773.beta.0 或
   #        @joyfill/components@4.0.0-rc24-2773-beta.4 → 立即移除
   npm install @joyfill/layouts@<2026-07-28前的版本> --save-exact  # 釘住安全版本
   ```
   並建議輪換所有暴露在受影響環境中的憑證。對任何有在用第三方 npm 套件的前端專案（幾乎所有專案都是）,這是提醒「supply chain 攻擊已經進化到繞過傳統防護手段」的即時案例。

5. **[Build工具][工程知識] Tree Shaking 原理解析：現代打包器怎麼判斷「哪些程式碼是死的」**
   解釋 Webpack、Rollup、Vite 這些打包器怎麼做 dead-code elimination：從進入點開始追蹤每個 `import`,建立完整依賴圖,標記哪些 export 真的被用到,沒被追蹤到的就被視為「死程式碼」直接砍掉。關鍵前提是**必須用 ES Module 語法**（`import`/`export`）——因為它的靜態結構讓打包器不用真的執行程式碼就能分析;CommonJS 的 `require()` 是動態的,打包器沒辦法保證安全地砍掉任何東西。範例對比：
   ```js
   // utils.js（ESM,可以被 tree-shake）
   export const used = () => {};
   export const unused = () => {}; // 沒被 import 過,會被砍掉

   // utils.cjs（CommonJS,無法被 tree-shake）
   module.exports = { used: () => {}, unused: () => {} }; // 整包都留著
   ```
   來源：patterns.dev（開放搜尋補充）｜https://www.patterns.dev/vanilla/tree-shaking/

11. **[React][框架] Remix 3：放棄 React,改用 fork 過的 Preact**
    這是本次最大的框架動態：Remix 3 把自己重新定位成完整的全端框架,而不只是「路由＋渲染」這個中間層,做法是**完全脫離 React**——前端保留 JSX 語法,但底層改用 fork 過的 Preact,並改成命令式模型（state 是一般變數,呼叫 `this.update()` 才通知畫面重新渲染,不是 React 的宣告式 hooks 模型）。官方明確說**沒有從 Remix 2 遷移的路徑**,Remix 2 使用者建議改走 React Router v7（8/2 digest 第 12 則提到的 v8 也是同一條路線的延續）。範例概念（命令式而非 hooks）：
    ```jsx
    class Counter {
      count = 0;
      increment = () => { this.count++; this.update(); }; // 明確呼叫才觸發重渲染
      render() { return <button onClick={this.increment}>{this.count}</button>; }
    }
    ```
    對正在用 Remix 2 的團隊,這代表短期內升級路徑會是 React Router v7,而不是等 Remix 3。
    來源：Remix 官方部落格（開放搜尋補充）｜https://remix.run/blog/wake-up-remix
    發布日期：2026-07（近期）
