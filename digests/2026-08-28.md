### 1. 你的 SPA 正在漏記憶體：用 Soak Test 找到它 [工程知識] [補收]

**標籤**：工程知識／記憶體管理／測試／Playwright

SPA 的記憶體洩漏最難捕捉，原因是症狀往往在使用幾小時後才出現。這篇文章提出「Soak Test（浸泡測試）」方法：讓 Playwright 自動模擬使用者操作幾十甚至幾百次，每次操作後對 `performance.memory.usedJSHeapSize` 取樣，畫成折線圖——漏記憶體的應用程式會呈現一條穩定上升的直線，正常的則會在某個範圍內平穩震盪。

文章從「為什麼短時測試找不到洩漏」開始解釋（因為 GC 在短時間內可以掩蓋問題），接著示範完整的 Playwright 腳本，包含如何每隔 N 次操作強制觸發 GC、如何把 heap snapshot 輸出成 GitHub Actions artifact 做 CI 回歸比對。

**範例一（取樣 heap 大小）**：
```js
const heapSizes = [];
for (let i = 0; i < 50; i++) {
  await page.click('#load-more'); // 模擬真實操作
  const heap = await page.evaluate(() => performance.memory.usedJSHeapSize);
  heapSizes.push(heap);
}
// heapSizes 若持續上升 → 確認有洩漏
```

**範例二（Before/After）**：修正前，每次點擊新增列表項 heap 增加約 800KB，50 次操作後多佔 40MB；移除未清除的 event listener 後，每次增加 < 5KB，曲線持平。

📖 https://denodell.com/blog/your-spa-is-leaking-memory-soak-test-it

### 2. 純瀏覽器端即時語音 AI 助理：Transformers.js + WebGPU 全端實作 [工程知識] [補收]

**標籤**：工程知識／AI 前端／Transformers.js／WebGPU

LogRocket 這篇教學示範如何在**不依賴後端或外部 API** 的情況下，完全在瀏覽器內建立即時語音對話 AI 助理。技術棧：Transformers.js（Hugging Face 瀏覽器端推論庫）+ WebGPU（利用 GPU 加速）+ Web Speech API（語音輸入）。整個 pipeline 本機執行，使用者的語音完全不離開裝置。

文章從「選對夠小又夠用的模型」切入，介紹 `Xenova/whisper-tiny.en`（語音轉文字）與 `Qwen2.5-0.5B`（文字生成）的取捨，並說明為什麼需要 Web Worker——推論會阻塞主執行緒，不放進 Worker 的話 UI 會完全凍結。對 WebGPU 不支援的裝置，文章也示範了自動 fallback 到 wasm 後端的寫法。

**範例（在 Worker 中初始化 pipeline）**：
```js
import { pipeline } from '@xenova/transformers';

// Web Worker 內執行，避免阻塞 UI
const transcriber = await pipeline(
  'automatic-speech-recognition',
  'Xenova/whisper-tiny.en',
  { device: 'webgpu' } // 不支援時自動 fallback 到 wasm
);

const result = await transcriber(audioBlob);
console.log(result.text); // → 轉錄後的文字
```

**效能對比**：wasm 後端每次推論約 2-3 秒；WebGPU 後端降到 0.4 秒，即時感大幅提升。對話體驗從「說完等一下」變成「近乎即時回應」。

📖 https://blog.logrocket.com/voice-ai-agent-browser/
（[補收] 來源：PR #16，首次補收）

### 3. 讓 Dashboard 真正推動決策：資料視覺化的 UX 重構思路 [工程知識]

**標籤**：工程知識／UX 工程／資料視覺化／Dashboard

Smashing Magazine 這篇文章（2026-08-26）點出多數 Dashboard 的根本問題：展示了「資料」，卻沒有引導使用者「做決定」。作者提出「Decision-First Design」框架——從「使用者最終要做哪個決定？」出發，反向設計圖表類型、指標選擇和視覺層次，而不是把能塞進去的資料都塞進去。

文章列出幾個實際技巧：用「Spark Chart + 單一主要數字」取代複雜折線圖（管理者一眼看出趨勢）；用顏色標示「需要行動的區間」而非純粹裝飾；加入比較基準——光顯示「本月銷售 $120K」沒意義，「比上月 +8%、比去年同期 -3%」才能觸發具體行動。

**Before/After 範例**：

*Before*：一張折線圖疊加 7 日均線、30 日均線、重要事件標注，資訊豐富但沒有「行動提示」，決策者需要自己解讀 5 分鐘。

*After*：Spark Chart 縮圖＋「本月 $120K（▲8% vs 上月）」大數字，低於年均線的區段以紅色底色標示，決策者 5 秒內得出「這個月表現超預期，但年化比去年弱，需要確認下半年策略」的結論。

對前端工程師的啟發：在開始實作之前，先跟 PM 或數據分析師確認「這個 widget 要讓使用者做什麼決定」，再選擇對應的視覺化類型，而不是先做出圖表再想用途。

📖 https://www.smashingmagazine.com/2026/08/rethinking-data-visualisation-ux-approach-dashboards/

### 4. DeepSeek Harness：萬物皆插件的 AI Agent 框架，兩天 14 萬 GitHub 星 [GitHub Trending]

**標籤**：GitHub Trending／AI 工具／TypeScript／Agent 框架

DeepSeek 於 2026 年 8 月 13 日發布 **DeepSeek Harness（dsh）**，一個以 TypeScript 撰寫、MIT 授權的 AI Agent 框架，核心理念是「Everything is a Plugin」。不只是工具（tools）可以是插件，連模型介面卡（model adapter）、工具登錄表（tool registry）、Session Log、沙箱環境，甚至 Agent Loop 本身都可以被抽換。上線後兩天突破 9.5 萬星，最終在一週內衝到 141,532 星＋14,350 forks，創下 GitHub 有史以來最快到達 20K 星的記錄（壓過 DeepSeek R1 的 5.7 天，只花了一小時多）。

架構上，dsh 採用 Cordis 框架，讓每個插件有自己的生命週期與依賴注入機制。對開發者的實際意義：可以用一行設定把預設模型從 OpenAI 換成本地 Ollama，或插入自訂日誌收集器，不需要修改框架核心程式碼。社群已有 90+ 個插件，包含 dsh-TUI（終端介面）、deepseek-harness-desktop（桌面包裝）等。

**範例一（安裝與啟動）**：
```bash
npm install -g deepseek-harness
dsh init my-agent  # 產生基本配置
dsh run            # 啟動互動式 Agent 終端
```

**範例二（替換模型 adapter 為本地 Ollama）**：
```ts
import { definePlugin } from 'deepseek-harness';

export default definePlugin({
  name: 'ollama-adapter',
  install(ctx) {
    ctx.model.setProvider(async (prompt) => {
      const res = await fetch('http://localhost:11434/api/generate', {
        method: 'POST',
        body: JSON.stringify({ model: 'llama3.2', prompt }),
      });
      return (await res.json()).response;
    });
  },
});
```

### 5. This Week in React #294：React Compiler 全面推進、TanStack 四件套並進 [前端技術棧]

**標籤**：前端技術棧／React／TanStack／Next.js／shadcn

TWIR #294（Sébastien Lorber 主編）涵蓋近期 React 生態系重點。

**React Compiler 普及**：多個主要框架（包含 Next.js）已預設開啟 React Compiler，過去需要手動寫 `useMemo`/`useCallback` 的情境，Compiler 自動分析並插入最佳化，讓開發者可以寫更乾淨的「無記憶化樣版」程式碼。

**TanStack 家族**：TanStack Start（SSR）、Router（型別安全路由）、Query（非同步狀態）、Form（表單管理）四個包這週都有小幅更新，並持續針對 React Compiler 做配合調整，減少不必要的 re-render。

**shadcn/ui 新 chart 元件**：shadcn 新增若干 chart 相關元件，配合 Recharts v4 使用，讓「設計品質的資料圖表」不再需要從零刻起。

**範例（React Compiler 前後對比）**：
```tsx
// Before（需要手動記憶化）
const SortedList = ({ items }) => {
  const sorted = useMemo(() => [...items].sort(), [items]);
  const handleClick = useCallback(() => doSomething(), []);
  return <List items={sorted} onClick={handleClick} />;
};

// After（React Compiler 自動優化，程式碼更直白）
const SortedList = ({ items }) => {
  const sorted = [...items].sort();   // Compiler 自動決定是否記憶化
  return <List items={sorted} onClick={() => doSomething()} />;
};
```

### 6. 你的網站為什麼永遠不應該「完成」：持續演進的前端工程觀 [前端技術棧]

**標籤**：前端技術棧／工程文化／效能監控／迭代開發

Smashing Magazine 這篇文章（2026-08-25）從實際工程角度論證「上線 = 完成」是個危險誤區，提出三個維度說明網站為什麼需要持續演進：

**1. 效能衰退**：JavaScript bundle 會因依賴更新、新功能累積而悄悄膨脹——沒有持續監測，半年後 LCP 可能從 1.2s 退化到 3.5s，使用者跳出率隨之上升，而工程師不知道是哪次變更造成的。

**2. 瀏覽器平台更新**：Web Platform 持續演進（Baseline、Interop），六個月前需要 polyfill 的 API 現在可直接用；反過來也有 deprecated API 開始出現警告，不主動清理就會累積技術債。

**3. 使用者行為改變**：行動裝置佔比、網路速度、輸入方式持續在變——去年設計的 UX 假設今年未必成立。

文章提供「每季健康檢查清單」框架：審查 bundle size、Core Web Vitals、可棄用依賴，並示範如何把 Bundlewatch 整合進 CI pipeline。

**Before/After**：
- Before：無監控，半年後工程師發現 main bundle 從 120KB 爬到 340KB，不知道哪次 PR 造成的。
- After：Bundlewatch 進 CI，每次 PR 若 bundle 增加超過 5KB 就自動在 PR 留言提醒，退化在合入時就被抓到。

📖 https://www.smashingmagazine.com/2026/08/why-website-should-never-stop-changing/

### 7. Firefox 154 Web 平台更新：sibling-index()、text-box 正式成為 Baseline [前端技術棧]

**標籤**：前端技術棧／Web 平台／Baseline／瀏覽器

Firefox 154（2026-08-18 發布）讓若干 Web 平台功能達到 **Baseline: Newly Available** 狀態（Chrome、Firefox、Safari 全線支援），對前端開發者最直接的意義是：可以**直接在生產環境使用，不需要 polyfill 或 feature detection**。

本次達到 Baseline 的主要功能：

- **sibling-count() / sibling-index()**：讓元素可根據在兄弟元素中的位置動態計算屬性值，不再需要 JavaScript 注入 `--index` 自訂屬性或手動操作 DOM。
- **text-box-trim / text-box-edge / text-box**：精確剪裁文字前後的 leading 空白，解決多語言排版和圖示對齊的老難題。

**範例一（sibling-index() 做錯開動畫，以前要 JS，現在純 CSS）**：
```css
/* 第 1 個子元素 delay 0.1s，第 2 個 0.2s，自動遞增 */
.item {
  animation-delay: calc(sibling-index() * 0.1s);
}
```

**範例二（text-box 讓標題與圖示精準對齊）**：
```css
h1 {
  /* 移除 cap-height 以下的多餘空白 */
  text-box: trim-both cap alphabetic;
}
```

Baseline Newly Available 代表可以停止為這些功能維護 polyfill 或 JS fallback，有效減少 bundle size。

📖 https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/154

### 8. SvelteKit 3 RC：Remote Functions 正式升級、向 Next.js RPC 架構叫板 [前端技術棧]

**標籤**：前端技術棧／Svelte／SvelteKit／RPC／框架比較

SvelteKit 3 Release Candidate 於 2026 年 8 月 13 日正式發布，帶來多項架構層面的變動。最受矚目的是 **Remote Functions**（原 experimental「server-only functions」）正式畢業——這是一套 RPC 層，允許開發者在元件中直接呼叫伺服器端函式，框架負責序列化、網路請求和型別安全，不需要手動撰寫 API 路由。

英國科技媒體 The Register 在 8 月 19 日以「SvelteKit 3 puts heat on Next.js with radical approach to RPCs」為題報導，將其定性為對 Next.js Server Actions / Remix actions 架構的直接挑戰——SvelteKit 的做法不需要在函式上加 `"use server"` 指令，而是用明確的 `.remote.ts` 副檔名分離邊界，減少意外把伺服器程式碼暴露給客戶端的風險。

其他重大改動：環境變數透過明確的 `src/env.ts` 型別檔案導入（不再隱性注入）；Service Worker 支援完整的 TypeScript 型別檢查；Shallow Routing 正式整合進 `goto()`；Migration 腳本一鍵遷移。

**範例（Remote Function vs Next.js Server Action 對比）**：

```ts
// SvelteKit 3 — src/lib/server/user.remote.ts（明確副檔名標示邊界）
export async function getUser(id: string) {
  return db.users.findById(id); // 這段程式碼永遠不會進 client bundle
}

// 元件中直接呼叫（框架負責 RPC）
import { getUser } from '$lib/server/user.remote';
const user = await getUser(params.id);
```

```ts
// Next.js 14 — 對比：需要在函式頂部加指令
'use server';  // 若忘記加，伺服器程式碼可能洩漏到客戶端
export async function getUser(id: string) { ... }
```

**升級指令**：`npx sv@next migrate sveltekit-3`（有互動式引導）。

📖 https://svelte.dev/blog/sveltekit-3-release-candidate
