### 1. Shopify Checkout Blocks 從自製元件遷移至 Polaris Web Components [補收]

`[工程知識]` `[Web Components]` `[Shopify]` `[補收]`

Shopify 工程師公開了一份 Checkout Blocks 應用程式的遷移記錄：把過去手刻的 UI 元件全面換成 Polaris Web Components，最終達到 bundle 體積減少 40–85%、頁面載入速度提升 7–8% 的效果。遷移最大的工程難題是 Shadow DOM 封裝與 SSR hydration 的衝突：自製元件在 server 端渲染時假設 DOM 結構一致，但 Web Components 的 Shadow DOM 邊界讓 React hydration 需要額外適配。

以下是元件 API 的遷移前後對比：

```html
<!-- 遷移前：自製元件，需要自己管理 className、主題、focus ring、鍵盤事件 -->
<div class="checkout-btn checkout-btn--primary" tabindex="0" role="button">
  <span class="checkout-btn__label">確認付款</span>
</div>
<!-- dark mode、hover 動畫、ARIA 屬性都要自己寫 JS 維護 -->

<!-- 遷移後：Polaris Web Component，互動行為、主題、無障礙全部封裝在元件內 -->
<polaris-button variant="primary" tone="success">確認付款</polaris-button>
<!-- dark mode、focus 管理、ARIA 屬性都由 Polaris 負責，完全不用手動維護 -->
```

```js
// Polaris 的 CustomEvent 介面比 onClick prop 更適合跨框架使用
document.querySelector('polaris-button').addEventListener('polaris:click', (e) => {
  e.detail.event.preventDefault(); // 可以取得原始 DOM event
  submitOrder();
});
```

這份記錄難得地坦誠列出失敗的嘗試（例如某些複雜互動在 Shadow DOM 裡無法正常 slot），對「是否要在 React 專案中引入 Web Components」的團隊，是比理論文章更有參考價值的實戰案例。

### 2. The Death Of The Button: Why The Best Interface Is No Interface

`[工程知識]` `[UX]` `[AI輔助開發]`

Smashing Magazine 這篇文章主張：Web UX 的下一個轉折點是「最好的介面不是更好看的按鈕，而是根本不需要按鈕」。作者認為，AI 讓使用者可以直接表達意圖、略過傳統介面的所有中間步驟——這對前端工程師和 UX 設計師的工作方式都有根本影響。

使用情境的 before/after 對比最能說明這個轉變：

**舊模式（點擊驅動）**：使用者要「開啟城市下拉」→「選台北」→「設定日期」→「篩選兒童設施」→「按搜尋」→「從列表選擇」→「點選預訂」——7 個步驟、7 個 UI 元件。

**新模式（意圖驅動）**：使用者說「幫我找下週末可帶小孩去台北的親子活動，評分 4.5 以上，訂週六下午的那場」——1 個輸入，AI 執行所有中間步驟，只在關鍵決策點回來確認。

對前端工程師的實際意義是：API 設計需要同時支援「使用者點擊」和「AI agent 呼叫」兩種操作者：

```typescript
// 舊設計：假設使用者操作，靠 UI 做驗證
interface BookingButton {
  onClick: () => void;
}

// 新設計：AI-friendly API，agent 可以直接傳入結構化資料
interface BookingAPI {
  reserve(params: {
    activityId: string;
    date: string;            // ISO 8601，不需要 date picker UI
    attendees: number;       // 不需要 stepper UI
    confirmedByUser: boolean; // agent 已獲使用者確認
  }): Promise<{ confirmationId: string }>;
}
// 同一個 API，既可讓 UI 按鈕呼叫，也可讓 AI agent 直接呼叫
```

文章特別強調「透明度」是新 UX 的核心：AI 替使用者做決定時，必須讓使用者隨時看到並能叫停——這反而比傳統 UI 需要更多用心設計。

📖 [Smashing Magazine](https://www.smashingmagazine.com/2026/09/death-button-why-best-interface-is-no-interface/) ｜ 2026-09-09 ｜ 優先來源

### 3. htmx 4.0：The Fetchening——底層從 XHR 遷移到 Fetch API

`[工程知識]` `[htmx]` `[Web 平台]` `[遷移指南]`

htmx 4.0 於 2026-08-28 正式發布，最大改變是把底層 HTTP 請求機制從 XMLHttpRequest 換成 Fetch API（作者自稱「The Fetchening」）。對大多數使用者而言，HTML 屬性語法不變；但有幾個預設行為調整是 breaking change，升級前需要逐一確認。

最重要的破壞性改動：**屬性繼承不再自動套用**，需要明確加 `:inherited` 修飾詞：

```html
<!-- htmx 3.x：父元素的屬性自動被子元素繼承，容易產生意外行為 -->
<form hx-boost="true" hx-target="#result">
  <button hx-post="/submit">送出</button>
  <a href="/cancel">取消</a>  <!-- 意外繼承了 hx-boost，變成 AJAX 請求 -->
</form>

<!-- htmx 4.0：需要明確標記 :inherited，行為更可預測 -->
<form hx-boost:inherited="true" hx-target:inherited="#result">
  <button hx-post="/submit">送出</button>
  <a href="/cancel" hx-boost="false">取消</a>  <!-- 明確關閉，不再意外繼承 -->
</form>
```

第二個行為改變：htmx 4 現在會對 4xx 和 5xx 回應也執行 swap（把錯誤頁面的 HTML 顯示到目標元素），而 htmx 2 預設是忽略這些錯誤回應：

```html
<!-- htmx 4：回傳 422 時也會 swap，error 訊息直接顯示在 #result -->
<form hx-post="/submit" hx-target="#result" hx-swap="innerHTML">
  ...
</form>

<!-- 如果只想在成功時 swap，可在後端對錯誤回傳 204（No Content） -->
<!-- htmx 4 不 swap 204 和 304，這是例外 -->
```

在 npm 上，`latest` tag 仍維持 v2.x 到 2027 年初；試用 v4 需要指定 `next` tag：`npm install htmx.org@next`。官方維護兩個版本並行支援，完整遷移指南在 four.htmx.org。

### 4. anomalyco/opencode — 開源 coding agent，本週暴增逾 3,000 stars

`[GitHub Trending]` `[AI輔助開發]` `[TypeScript]`

opencode 是 TypeScript 撰寫的開源 coding agent，以 206,000+ stars 長期居 GitHub Trending 高位，本週又新增超過 3,000 stars。它內建兩個職責不同的 agent：**build agent**（完整開發存取權，可讀寫檔案、執行 shell 指令）和 **plan agent**（唯讀分析模式，適合 code review 或需要受限環境的情境）。

```bash
# 安裝
npm install -g @anomalyco/opencode

# plan 模式（唯讀）：分析程式碼，不做任何修改
opencode plan "解釋這段 useEffect 的 cleanup 函式在做什麼，以及省略它會有什麼問題"

# build 模式（完整存取）：實際執行修改任務
opencode build "把 UserCard.tsx 的 class component 重構成 functional component，保留所有現有行為"
# opencode 會讀取相關檔案、作出修改，並產出 diff 讓你確認後再套用
```

兩個 agent 的分工設計解決了「單一 agent 同時分析與改代碼容易出錯」的問題——plan 負責分析與規劃，build 負責執行，職責清晰。對習慣 Claude Code 或 Cursor 但想要一個完全開源、可自架、不依賴特定 AI 廠商的替代方案，opencode 是目前最完整的選項之一。

### 5. Tailwind Labs 宣布加入 Shopify

`[前端技術棧]` `[業界動態]`

Tailwind CSS 的創作者 Adam Wathan 帶領整個 Tailwind Labs 團隊（約 20 人）加入 Shopify。Tailwind CSS 目前服務超過 500 萬個專案，Tailwind UI、Heroicons、Headless UI 和 Catalyst 都是 Tailwind Labs 旗下產品——這是 2026 年前端工具生態最受矚目的業界事件之一。

根據公告，Tailwind CSS 和所有旗下產品**繼續以開源形式維護**，不會被關閉或吸收進 Shopify 內部工具。Shopify 的動機是讓 Tailwind Labs 在更有資源的環境下加速開發，同時讓 Shopify 的前端技術棧能更緊密整合 Tailwind 生態系。

這讓人聯想到 Shopify 過去的策略布局：Remix 在 2022 年加入 Shopify（後於 2024 年轉讓給 React Router 維護），以及 Shopify 與 React 社群的長期深度關係。對現有 Tailwind 使用者，短期影響不大；長期值得觀察的是 Shopify 是否會把 Tailwind 整合進 Dawn 主題架構或 Polaris 設計系統，讓 Shopify 的主題開發體驗進一步現代化。

### 6. Cursor Cloud Agents 現可在 Vercel Sandbox 執行

`[前端技術棧]` `[AI輔助開發]` `[DevOps]`

Vercel 宣布其 Sandbox 環境支援 Cursor 的 Self-Hosted Cloud Agents——讓 AI coding agent 在受控的 Vercel 沙箱中執行長時間任務，不需要在本機持續掛著 agent 進程。對於「讓 AI agent 在背景自主執行、完成後回報」的工作流程，這個整合大幅降低設定複雜度。

實際的工作流示意（以自動修 CI 失敗為例）：

```
觸發條件：CI 失敗通知
    ↓
啟動 Cursor Cloud Agent（在 Vercel Sandbox 執行，不佔用本機）
    ↓
Agent 讀取錯誤 log → 分析根本原因 → 修改程式碼 → 執行測試
    ↓
測試通過 → 開 PR → 通知工程師 review
（全程 agent 在 Vercel 雲端執行，工程師本機無需在線）
```

```bash
# 設定 Cursor Cloud Agent 使用 Vercel Sandbox（需 Vercel 帳號 + Cursor 訂閱）
vercel link              # 連結專案到 Vercel
cursor agent create      # 建立 cloud agent
cursor agent deploy --sandbox vercel  # 部署至 Vercel Sandbox
# 之後 agent 的任務在 Vercel 受控環境執行，本機不需要持續運行
```

Vercel Sandbox 提供網路隔離、執行時間限制、資源上限等保護，比讓 agent 直接存取本機環境更安全。對想把 AI agent 整合進 CI/CD 流程但擔心安全性的團隊，這是一個可以直接試驗的入口。

### 7. Astro 7.3：多個 preview server 同時跑、logger 傳遞給插件

`[前端技術棧]` `[框架]` `[Astro]`

Astro 7.3（2026-09-03）是一個集中改善 DX 的 minor release。最實用的新功能是 `--ignore-lock` 旗標，讓你可以同時啟動多個 Astro preview server——過去第二個 `astro preview` 啟動時會因找到既有 lock 檔而失敗。

```bash
# 舊做法：同時開兩個 preview server 會出錯
astro preview --port 4321           # 正常啟動
astro preview --port 4322           # ❌ 失敗：找到既有 lock 檔

# Astro 7.3：加上 --ignore-lock 允許多個 preview 同時存在
astro preview --port 4321
astro preview --port 4322 --ignore-lock  # ✅ 正常啟動
# 使用情境：A/B 比較兩個 build 的輸出、同時預覽多個分支的靜態結果
```

第二個重要改動：Astro 的 runtime logger 現在會被傳入自訂的 image service 和 cache provider，讓插件的警告訊息能遵守 Astro 的 `--silent` / `--verbose` 設定，不再直接輸出到 console 無視你的 log level：

```typescript
// 舊寫法：直接用 console.warn，繞過 Astro log level 設定
const myImageService = {
  async transform(image) {
    console.warn('轉換失敗，使用原始圖片'); // --silent 模式下仍會印出
    return image;
  }
};

// Astro 7.3 新寫法：使用傳入的 logger，遵守 Astro log 設定
const myImageService = defineImageService({
  async transform(image, { logger }) {
    logger.warn('轉換失敗，使用原始圖片'); // 在 --silent 模式下靜默 ✓
    return image;
  }
});
```

對使用 Cloudflare Workers 的開發者，`@astrojs/cloudflare` 在這版也加入 `finalize()` helper，讓 custom worker entrypoint 可以在 Astro 完成渲染後執行收尾邏輯（例如修改 response header 或寫入快取）。
