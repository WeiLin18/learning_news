### 1. Turn one giant AI-generated pull request into a reviewable stack

`[補收]` `[AI輔助開發]` `[實務指南]` `[工程知識]`

GitHub 官方部落格這篇教團隊怎麼把 coding agent 一次吐出的巨大 PR，拆成一串「有序、可個別審查」的 stacked pull requests，而不是在「巨大 PR 難審」和「手動拆多個 PR 要自己同步衝突」之間二選一。

做法是用 GitHub 的 Stacked PRs 功能，依程式碼的「層次」（例如 schema → API → UI）切成多個小 PR，每個 PR 的 base 指向下一層的 branch，形成一條可逐層審查、一次點擊合併整串的鏈：

```
PR #1 (schema)  ← base: main
PR #2 (API)     ← base: PR #1 的 branch
PR #3 (UI)      ← base: PR #2 的 branch
審查者可以逐層 review，合併時一次操作即可整串合併，不用自己手動同步各 PR 之間的衝突
```

文中引用 Gartner 預測，coding agent 到 2028 年會讓 SDLC 各階段生產力提升 50%，但 PR 越大、review 品質越差正是這個技巧要解決的痛點。對正在把 AI coding agent 導入日常開發流程、又苦於 review 大 PR 的前端團隊，是很具體的落地做法——也是「可具體照做的 AI 輔助開發指南」這個使用者偏好方向裡耐放的一篇，隔了兩週再看依然實用。

### 2. Vercel 開出 100 萬美元懸賞：誰能從 Vercel Sandbox 逃逸出來

`[資安]` `[AI輔助開發]` `[工程知識]`

Vercel Sandbox 是專門讓 AI coding agent 安全執行程式碼的沙盒環境——agent 自己寫的程式碼、跑的指令，都在這個沙盒裡完成，不會碰到真正的正式環境。Vercel 這次直接開一個為期兩週（8/18–9/1）的公開 HackerOne 懸賞，總獎金上限 100 萬美元，目標就是找出這個沙盒有沒有辦法被「逃逸」出去。

架構上，每個 Sandbox 跑在裸機 EC2 主機上，各自擁有一個獨立的 Firecracker microVM（含專屬的 guest kernel），真正在跑 agent 程式碼的 Linux container 則在 microVM 裡面——**microVM 本身才是安全邊界**，不是裡面的 container：

```
裸機 EC2 主機
  └─ Firecracker microVM（每個 sandbox 各自獨立，含專屬 guest kernel）
       └─ Linux container（agent 產出的程式碼實際在這裡執行）
安全邊界畫在 microVM 這一層，不是 container 這一層
```

規則很明確：只靠靜態分析找出的理論漏洞不算數，一定要真的示範「逃出這層邊界」（例如讀到或改到別的租戶的資料）才會拿到獎金，單一報告最高 5 萬美元。對正在評估「要不要把 AI agent 產出的程式碼丟進沙盒執行」這類架構的團隊，這個懸賞金額本身就是 Vercel 對自家隔離機制有多少信心的具體訊號。

📖 [Vercel Blog](https://vercel.com/blog/one-million-dollar-hacker-challenge-for-vercel-sandbox) ｜ 2026-08-18（近期，2 天前）｜ 開放搜尋補充

## 知名前端工程師個人部落格

### 3. Addy Osmani — Software Factories, Light and Dark

`[補收]` `[Blog]` `[AI輔助開發]`

Addy Osmani 提出「軟體工廠」的比喻：AI 輔助開發正從「寫程式碼」轉變成「設計並營運一整套自動化迴圈」——一個 loop 反覆做「收集脈絡 → 實作 → 驗證 → 改善」。他把「工廠」分成「光明」與「黑暗」兩種：黑暗工廠讓程式碼在無人閱讀、只靠機器互相驗證下就上線；光明工廠則把人類判斷力前移到設計與架構階段，而不是留到最後才審一次。

核心主張是「背壓（back pressure）」：一個 loop 能拿到多少自主權，取決於你能多快、多可靠地驗證它的產出，而不是它能吐出多少程式碼——驗證跟不上，給再多自主權都是風險：

```
黑暗工廠：AI 產出 → 直接合併 → 出事才回頭查
光明工廠：AI 產出 → 先過測試/型別/lint 關卡 → 人類抽查關鍵決策點 → 才合併
```

對正在把 Claude Code / Cursor 等 coding agent 導入團隊、思考「該給多少自主權」的工程主管很有參考價值，是一篇原則性但可以直接對照自家流程檢查的文章。

### 4. Cursor Origin：Cursor 推出自己的程式碼代管平台，正面對上 GitHub

`[AI輔助開發]` `[DX工具]`

Cursor 這次推出「Origin」——一個內建在 Cursor 裡的程式碼代管平台（repo、PR、code browsing 全部在 Cursor 內完成），並與 GitHub 做雙向同步：在 Cursor 裡留言，會即時同步到 GitHub 上的對應 PR；反過來在 GitHub 上回覆或按讚，幾秒內也會出現在 Cursor 裡。目前以 early beta 開放給所有付費方案使用者。

```
情境：團隊還沒打算搬離 GitHub，但想在 Cursor 內直接管理 PR
→ 在 GitHub 組織設定裡連接 Cursor Origin，選擇要同步的 repo
→ 之後在 Cursor 或 GitHub 任一邊留言、review，另一邊幾秒內同步顯示
→ 不用整個團隊一次搬家,也能先體驗「agent 原生」的程式碼協作介面
```

每個代管的 codebase 會有自己的網址（例如 `cursor.com/codebase/acme-corp`），定位是替「agent 規模」的協作設計的介面，而不是照搬人類習慣的 PR 頁面。這次上線時機也很微妙——剛好在 GitHub 發生大規模服務中斷的同一週，被不少科技媒體解讀為 AI coding 工具鏈開始正面挑戰 GitHub 在版本控管領域地位的訊號，對持續在觀察「AI coding agent 生態系會不會連版本控管都重新洗牌」的前端團隊是值得留意的動向。

### 5. TanStack Router：router-core 效能優化，聚焦路由比對與快取路徑

`[React][Vue][Solid]` `[框架]` `[效能]`

TanStack Router 團隊這次的更新集中在 `router-core` 本身的效能——不是新功能，而是讓路由比對與快取判斷這兩件「每次導覽都要做」的事變得更快、更少浪費。具體做法包括優化 `buildLocation` 內部的路徑解析邏輯、跳過注定不會命中的 route mask 快取查詢，以及在 search 驗證被停用時直接跳過驗證流程，不做多餘的檢查：

```
修補前：每次導覽都完整跑一次 buildLocation 路徑解析，即使結果可預期
修補後：優化過的路徑解析邏輯減少重複運算，導覽路徑比對更快落地
```

這批更新同時涵蓋 `@tanstack/react-router`、`@tanstack/vue-router`、`@tanstack/solid-router` 以及對應的 Start 全端套件（共 22 個套件），再次印證 TanStack Router/Start 的路由核心是刻意設計成跨 React、Vue、Solid 三個框架共用同一套底層邏輯，而不是各自維護一份。對已經在用 TanStack Router 的團隊，這類底層效能優化通常不需要改任何程式碼就能直接吃到。

### 7. Rspack v2.2.0-beta.1：RSC 樣式改走 Flight 預初始化、SWC 升級到 77

`[Build工具]` `[React]`

Rspack 這個新 beta 版本有三項值得注意的變動。第一，React Server Components 的 Client Component CSS 處理方式改變：過去用「包一層 export、外掛 link element」的方式載入樣式，現在改成透過 Flight payload 做預初始化，好處是能保留 client-reference 的身分識別；這是一個 breaking change，需要搭配 `react-server-dom-rspack` 0.1.0 一起升級。

第二，底層編譯依賴 SWC 從 76 升級到 77，改變了 Wasm plugin 邊界的 AST 序列化格式（新增專屬的 `FunctionBody`／`ArrowFunctionBody` AST 節點），意味著自己寫的 SWC Wasm plugin 需要針對新版重新編譯，否則建置會直接因相容性錯誤而失敗。第三，CSS Modules 的 Unicode 識別字現在改依 CSS Syntax 標準處理，直接輸出原始字元而不是不必要的跳脫字元：

```css
/* 修補前：Unicode class name 會被轉成跳脫格式輸出 */
.style_modules_css-\1F60D  /* 對應到 😍 */

/* 修補後：CSS Modules 遵循 CSS Syntax 標準，直接輸出原始 Unicode 字元 */
.style_modules_css-😍
```

此外這版也加入以世代為單位的記憶體快取回收機制，並優化了 React Compiler 相關 crate 的體積。對已經在用 Rspack 搭配 RSC 或自訂 SWC plugin 的團隊，升級前建議先確認自己的 plugin 是否需要針對 SWC 77 重新編譯。
