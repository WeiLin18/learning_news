### 1. Upgrading Checkout Blocks app to Polaris web components

`[補收]` `[架構]` `[Web Components]` `[工程知識]`

Shopify 團隊記錄了一次「不只是換皮」的大型 UI 遷移：五個高流量的 Checkout Blocks 擴充功能（涵蓋約三分之一經客製化的結帳頁面），從舊有的 React + Remote UI bridge 架構，整個換成 remote-dom + Preact + Polaris web components，同時把程式碼庫整體改寫為 TypeScript。

最有說服力的是遷移前後的實測數據——這種「換底層渲染機制」的決策很少有團隊願意公開實際數字：

```
遷移前：React + Remote UI bridge（API 2025-07）
  → 每個擴充功能需要打包完整 React runtime + bridge 序列化層

遷移後：remote-dom + Preact + Polaris web components（API 2026-01）
  → bundle 大小下降 40%–85%
  → 每個擴充功能的載入速度提升 7%–8%
```

過程中團隊也踩了不少坑：Polaris web components 目前的樣式客製化彈性、跟原有元件 API 的落差，都需要跨團隊協作才解決得掉——這提醒任何想把「框架元件」換成「web components」的團隊，帳面上的效能數字背後藏著真實的協作成本。對正在評估要不要把大型既有 React 應用局部換成原生 web components 的前端團隊，是一篇有 before/after 真數據的參考案例。

### 2. Dogfooding at scale: migrating cdnjs to Cloudflare's Developer Platform

`[補收]` `[基礎設施]` `[工程知識]`

cdnjs 是幾乎每個前端專案都間接依賴過的公共函式庫 CDN，每天服務約 90 億次請求。這篇文章記錄 Cloudflare 團隊怎麼把 cdnjs 完全遷移到自家由 Workers、Workflows、R2、KV、Queues、Containers、Durable Objects 組成的 Developer Platform 上——是一次真正的「自己吃自己的狗糧」。

最有意思的地方是：cdnjs 的流量規模大到直接把 Cloudflare 平台既有的限制撞出裂縫，反過來推動了平台本身的改進：

```
遷移前發現的平台上限：
  每次 Worker 呼叫最多 1,000 次 subrequest
  每個 Workflow 最多 1,024 個 step
     ↓（cdnjs 的規模不斷撞到這兩個上限）
遷移後平台的改變：
  付費方案的 subrequest 上限一路提高到 1,000 萬次
```

另一個實際好處是資安面的簡化：舊架構要同時維護 Cloud Functions、git-sync VM、容器映像、GCS bucket 與 service-account 金鑰，光是這些元件本身就是持續要修補的資安表面；退役舊 pipeline 之後，等於一次關掉了所有跟這批舊元件相關、近期才開出的資安漏洞。對任何依賴 cdnjs 交付函式庫、或正在思考「要不要把大流量服務搬進自家 serverless 平台」的團隊，這是一篇有具體規模數據的實戰紀錄。

### 3. Next.js v16.3.1

`[Next.js]` `[React]` `[框架]`

Next.js 16.3 系列的例行維護 patch，一次修掉 19 個 PR（8 位貢獻者），修正範圍集中在 Turbopack、圖片優化與快取三個面向：Turbopack 的 async-module runtime 處理、embedded filesystem 設定、analyzer 的 promise 合併邏輯都有修正；`next/image` 修了「優化後的圖片回應沒被保留」的問題；`unstable_cache` 的編碼方式、tag revalidation 邏輯、快取項目的 TTL fallback 也一併改善。

其中一個具體情境是快取失效的修正：

```
修補前：unstable_cache 在某些情況下 tag revalidation 沒有正確觸發
  → 開發者呼叫 revalidateTag() 後，快取內容仍是舊的
修補後：tag revalidation 邏輯修正
  → revalidateTag() 呼叫後能正確拿到最新資料
```

另外也修了 HMR 對動態 import 的支援、樂觀路由預載（optimistic routing prefetch）的迴圈問題，以及 adapter 建置下 Pages Router SSR 遺失 styled-jsx 樣式的回歸。雖然都是維運性質的修正，但對正在營運 Next.js 16.3 生產環境、依賴 `next/image` 與 `unstable_cache` 的團隊，是值得優先更新的一批穩定性改善。

### 4. Remix 3 Beta Preview

`[框架]` `[React/Preact]` `[框架比較]`

Remix 團隊發布了 Remix 3 的 beta 預覽版，這不是漸進式升級，而是換底層執行模型的重新定位：Remix 3 把自己定義成完整的全端框架，將路由、request handler、middleware、session、auth、表單、上傳、資源、資料庫管理、UI 元件、主題、網路請求、測試全部收攏進同一個 `remix` 套件底下，由一組組合式的小套件組成（8/2 已收錄的「React Router v8」報導中曾提及 Remix 團隊的「Remix 3」實驗方向，這次是該方向正式進入 beta 的具體落地，並非重複報導同一件事）。

最大的架構轉向在前端執行模型：Remix 3 保留 JSX 語法，但把 React runtime 整個換成 fork 過的 Preact，並改用「命令式」心智模型——狀態不再是 hook 回傳值，而是一個普通變數，呼叫 `this.update()` 才通知畫面重繪：

```jsx
// Remix 2（React）：狀態是 hook 回傳值，setState 觸發重渲染
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

// Remix 3（forked Preact，命令式模型）：狀態是普通變數，
// 呼叫 this.update() 明確通知「畫面該重繪了」
class Counter {
  count = 0;
  render() {
    return <button onClick={() => { this.count++; this.update(); }}>{this.count}</button>;
  }
}
```

後端邏輯則完全建立在 Fetch API 上——路由本身就是 Fetch API 路由，controller 回傳的就是標準 `Response` 物件，表單直接送到 URL，讓伺服器完整擁有 request 生命週期的控制權，因此天生就能跑在 Node、Deno、Bun 或任何實作 Fetch 的執行環境上，不需要 runtime 專屬的 adapter。目前可用 `npx remix@next new my-remix-app` 嘗鮮，但官方明確標示還不是 production-ready。對想理解「React 生態系裡除了 signals 之外，還有沒有完全脫離 React runtime 的路」的框架比較讀者，是一個力度很大的具體案例。

### 5. React Native 0.87

`[React Native]` `[框架]`

React Native 0.87 把先前僅供預覽的 Strict TypeScript API 正式訂為所有專案的預設 JavaScript API（取代 0.80 版開始的選用式預覽），同時把最低工具鏈需求一次拉高：Node.js 22、Android Gradle Plugin 9、Kotlin 2.0+。

對日常開發體感影響最直接的是 Metro 的更新——這次號稱 source map 產生速度快 2 倍、記憶體用量減半：

```
修補前：Metro 產生 source map 時記憶體用量較高、耗時較長
修補後：source map 產生速度提升 2 倍，記憶體用量減半
  → 對大型 app 的 build/debug 迴圈影響最明顯
```

另外 iOS 端新增一個實驗性的 Swift Package Manager 選項，作為 CocoaPods 的替代方案——不用 Ruby、不用 Bundler，相依套件變更後也不需要重跑 `pod install`。這個版本總計有 265 個 commit、74 位貢獻者參與。對正在維護大型 React Native app、且 iOS 端相依管理長期被 CocoaPods 拖慢開發流程的團隊，SwiftPM 選項與 Metro 的效能提升都是值得規劃升級的具體理由。

### 6. Turborepo v2.10.11

`[Build工具]` `[Monorepo]`

Turborepo 這個例行 patch 版本共 14 個 commit，重點修正集中在快取行為的正確性：修了「沒有 git metadata 時無法正確尊重 `.gitignore` 規則」的問題（過去這種情況下 pruning 可能誤判該保留還是該排除哪些檔案）、修正並行執行多個 generator 設定時 config bundle 互相污染的問題，並讓對暫時性輸入檔案缺失的情況更寬容，不會因為短暫的檔案系統抖動就整個失敗。

功能面新增了對原生 uv（Python 套件管理工具）任務的快取支援：

```
修補前：uv 相關任務（例如用 uv 跑 Python 腳本）每次都重新執行，即使輸入完全沒變
修補後：Turborepo 能正確快取 uv 任務的輸出
  → 混合 Node.js／Python 的 monorepo，Python 那一側的任務也能吃到增量建置的好處
```

這個版本也重新設計了 Turborepo 官網首頁。雖然都是維運性質的小幅修正，但「快取正確性」正是 monorepo 建置工具最容易被使用者感受到問題的地方（快取失效或誤判都會直接拖慢日常開發），對已經在用 Turborepo 管理大型 monorepo、尤其是混合 Python 工具鏈的團隊，值得留意這批修正。
