### 1. Zod 4.5：用 `z.compile()` 讓 schema 解析速度提升 3–9 倍

`[工程知識]` `[TypeScript]` `[效能]`

Zod 4.5 的旗艦功能是 **`z.compile()`**——對任意 schema 呼叫一次，就能取得一個「預編譯版本」，解析速度提升 **3–9 倍**，物件、陣列、union 類型獲益最大。編譯是在 runtime 執行（不需要修改 build pipeline），API 與原本的 schema 完全一致：升級不需要改動其他程式碼。

額外亮點：每個 schema 的記憶體佔用減少最多 9 倍，對「一次定義大量 schema」的專案（例如表單驗證庫、API client）有感。

**範例一：在現有程式碼最小改動升級**

```ts
import { z } from "zod"

const UserSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  age: z.number().int().min(0),
})

// 只需加這一行，其餘 .parse() / .safeParse() 呼叫完全不需要改
const CompiledUser = z.compile(UserSchema)

// 使用方式與原本相同
const user = CompiledUser.parse({ id: "abc-123", name: "Alice", age: 30 })
// 但速度快了 3–9 倍 ✓
```

**範例二：適合高頻呼叫路徑（例如 API 入口）**

```ts
// 在模組層級編譯一次，在每個 request 複用
const BodySchema = z.compile(
  z.object({ query: z.string(), limit: z.number().default(10) })
)

export async function handler(req: Request) {
  const body = BodySchema.parse(await req.json()) // 高頻呼叫，享受快 9 倍的效能
  // ...
}
```

### 2. pnpm 12：用 Rust 重寫，warm cache 安裝快 30 倍

`[工程知識]` `[Build 工具]` `[效能]`

pnpm 12 是 pnpm 的 Rust 全面重寫版，效能數字驚人：在一個大型生產 monorepo 的測試中，**冷安裝從 8.2 秒降到 5 秒**，**warm cache 安裝從 472ms 降到 15ms**（約快 30 倍）。重寫將效能敏感的部分移到原生 Rust binary，去除 Node.js 啟動的 overhead 和大量 filesystem 操作的 JS layer。

相容性方面，pnpm 12 設計為零遷移成本：指令、flag、設定檔、lockfile 格式與 pnpm 11 完全相同，不需要修改 scripts 或 CI。目前 npm `latest` tag 仍指向 pnpm 11，需要明確安裝 pnpm 12。

**範例：安裝與驗證速度差異**

```bash
# 安裝 pnpm 12（目前在 next-12 tag）
pnpm self-update next-12

# 確認版本
pnpm --version
# 12.x.x

# warm cache 安裝：在同一台機器重複 install，速度從 472ms 降至 15ms
pnpm install
# Packages: +0 (all cached)
# Done in 15ms  ← 之前：472ms
```

**Before / After 比較**

| 情境 | pnpm 11 | pnpm 12 |
|------|---------|---------|
| 冷安裝（無快取） | 8.2 s | 5.0 s |
| warm cache 安裝 | 472 ms | 15 ms |

### 3. 247 bytes 的踩地雷：JavaScript code golf 教學

`[工程知識]` `[JavaScript]` `[優化]`

作者把踩地雷（Minesweeper）壓縮到 **247 bytes**，涵蓋完整功能：8×8 隨機棋盤、左鍵開格、右鍵插旗、零鄰雷遞迴展開、勝負判斷。這篇文章是實作細節的拆解，解說每一個壓縮技巧背後的思路，是學習 JavaScript 位元操作、Canvas 精簡渲染、事件處理合併的好材料。

核心技巧之一是用**一個整數儲存所有地雷位置**：100 個格子，每個 bit 代表一格是否有雷，整數操作比陣列快也省空間。另一個技巧是把左鍵和右鍵都綁在同一個 `onmouseup` 事件，用 `event.which` 分辨。

**範例一：用 bit 操作儲存和讀取地雷**

```js
// 初始化：在第 pos 格放雷
mines |= (1 << pos)   // 把第 pos 個 bit 設為 1

// 檢查：第 n 格是否有雷？
const isMine = (mines >> n) & 1   // 右移 n 位，取最低 bit
// 結果 1 = 有雷，0 = 沒雷
```

**範例二：合併左右鍵為單一事件**

```js
document.onmouseup = e => {
  const pos = getCell(e)
  if (e.which === 1) openCell(pos)   // 左鍵：開格
  if (e.which === 3) toggleFlag(pos) // 右鍵：插旗
}
// 省去兩個獨立的 listener，也省了函式名稱的字元數
```

### 4. magnitudedev/magnitude：在本地跑 AI 模型，OpenAI 相容 API，離線可用

`[GitHub Trending]` `[AI 輔助開發]` `[工具]`

**magnitude** 是一個開源本地 AI 推論伺服器（約 3,300+ ⭐，9 月上旬活躍），自動偵測硬體（CPU / GPU / Apple Silicon），下載合適的模型版本，然後啟動一個完全相容 OpenAI API 格式的本地端點。不需要帳號、不需要 API key，也不需要網路——適合在離線環境或需要資料隱私的場合使用。

對前端開發者最實際的用途是：讓 **Claude Code、Cline、Cursor、OpenCode** 等 AI 輔助開發工具指向本地端點，用免費的本地模型輔助寫程式，費用為零。Setup 只需兩條命令，完全不需要手動設定 CUDA、llama.cpp 或 Ollama。

**範例一：安裝與啟動**

```bash

# 啟動本地推論伺服器（自動偵測硬體並下載模型）

# ✓ 偵測到 Apple Silicon，下載 Qwen2.5-Coder-7B-Q4...
# ✓ 伺服器就緒：http://localhost:3000（OpenAI 相容 API）
```

### 5. Vitest 5.0：效能大幅提升，需要 Vite 6.4 和 Node.js 22

`[前端技術棧]` `[Testing]` `[Vitest]` `[效能]`

Vitest 5.0 在 2026-09-03 正式發布，主要聚焦效能：Browser Mode 和 vm-isolated 測試套件的速度都有明顯提升。這是一個 major 版本，有幾個需要注意的 breaking change；升級前建議逐一確認。

最低依賴要求：**Vite ≥ 6.4.0**、**Node.js ≥ 22.12.0**。主要 breaking change：`vitest list` 預設改為 static 模式（不再執行測試檔初始化）、`clearCache` 從 experimental 正式升格、coverage 改用 `@vitest/istanbuljs` 套件（需要手動安裝）。

**範例一：升級後需要確認的 breaking change**

```bash
# 1. 更新依賴
npm install vitest@5 vite@latest --save-dev

# 2. coverage 改用新套件（若有用 istanbul coverage）
npm install @vitest/istanbuljs --save-dev

# 3. 若 vitest list 行為改變（靜態模式），動態 test 命名可能需要調整
npx vitest list
# 現在：靜態列出測試名稱，不執行測試檔的 setup 邏輯
```

**範例二：Browser Mode 效能改善（before / after）**

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    browser: {
      enabled: true,
      name: "chromium",
    },
    // Vitest 5 在 Browser Mode 下的並行執行效率提升
    // 原本跑 300 個 browser 測試需要 ~45s，5.0 大約 ~18s

```

### 6. Playwright v1.63.0：Test Locks、跨 frame 定位器、`locator.visible()`

`[前端技術棧]` `[Testing]` `[Playwright]`

Playwright v1.63.0 在 2026-09-04 發布，最重要的新功能是 **Test Locks**：透過具名鎖讓存取共用資源（例如一個測試用帳號、一個有限授權的 sandbox）的測試不會並發衝突，其他測試照常並行，不影響整體速度。

另外兩個值得注意的小功能：`locator.visible()` 讓你明確拿到「只有可見元素」的 locator，替代之前的 `:visible` CSS 偽類；跨 frame 定位器現在不需要先找到 iframe 元素，直接搜尋整個子樹，更符合使用者視角。

**範例一：Test Locks 避免測試帳號被多個 worker 同時占用**

```ts
import { test } from "@playwright/test"

test("需要唯一 sandbox 帳號的測試", async ({ page }, testInfo) => {
  // acquireLock 確保同一時間只有一個 test 持有 "sandbox-account" 鎖
  // 其他 test 等待鎖釋放，不需要手動 sleep 或 retry
  await using _lock = await testInfo.acquireLock("sandbox-account")

  await page.goto("/dashboard")
  // 這段操作期間不會有其他 test 同時使用 sandbox 帳號
})
```

**範例二：`locator.visible()` 精確定位可見元素**

```ts
// 舊寫法：用 CSS 偽類（可能不穩定）
const btn = page.locator("button.submit:visible")

// 新寫法：明確要求只取可見的 submit button
const btn = page.locator("button.submit").visible()

// 更容易閱讀，也更符合 Playwright locator API 風格
await btn.click()
```

### 7. Biome v2.5.12：Astro / CSS / HTML parser 修復累積版

`[前端技術棧]` `[Build 工具]` `[Biome]`

Biome v2.5.12（2026-09-03）是 v2.5 minor 的第 12 個 patch，累積了 40+ 個針對 Astro、CSS、HTML 格式的 parser 修復——這三種格式是 v2.5 才正式加入支援的，初始版本難免有邊緣案例。如果你的專案包含 `.astro` 檔或 HTML 模板，這是一個值得升級的穩定點，之前遇到的奇怪格式化結果或誤報 lint 警告大多在這個版本修好。

這個版本也帶來 8 條新的 lint rule（新增至 nursery 階段）。對於正在評估是否從 ESLint + Prettier 切換到 Biome 的團隊，這個 patch 的穩定性提升讓它成為一個更好的試點起點。

**範例一：升級並驗證 Astro 檔格式化是否正常**

```bash
# 升級到最新版
npm install --save-dev @biomejs/biome@2.5.12

# 對 Astro 檔執行格式化（之前可能有 parser crash 或異常縮排）
npx biome format --write src/**/*.astro

# 執行 lint 確認沒有新的誤報
npx biome lint src/
```

**範例二：新的 nursery lint rule 預覽（需要手動 opt-in）**

```json
// biome.json — 啟用部分新 nursery rules
{
  "linter": {
    "rules": {
      "nursery": {
        "noUnusedFunctionParameters": "warn",
        "useConsistentMemberAccessibility": "warn"
      }
    }
  }
}
```
