### 1. Expose Your Design System to LLMs

`[工程知識]` `[AI輔助開發]` `[設計系統]`

AI coding tool 最常見的副作用之一：LLM 在沒有明確規範時，會直接幻想設計 token 的名稱和數值。Hardik Pandya（Atlassian 設計工程師）在這篇文章裡提出一套系統性解法——把設計系統從「人讀的文件」重構成「LLM 能直接讀的 spec」，讓每一次 vibe coding session 都能拿到一致的設計輸出。

核心做法分三層：**spec 檔**（把設計決策寫成結構化的 Markdown 或 JSON，在 system prompt 裡一次載入）、**封閉 token 層**（只允許 LLM 使用設計系統提供的 token，禁用魔法數字如 `16px`）、**自動稽核**（commit hook 掃描 LLM 輸出的程式碼是否有用到規範外的值）：

```json
// design-spec.json（放進 system prompt，每次 session 開頭載入）
{
  "spacing": {
    "4": "1rem",
    "8": "2rem",
    "12": "3rem"
  },
  "color": {
    "primary": "#0052CC",
    "surface": "#F4F5F7"
  },
  "rule": "Never use raw px values for spacing. Always reference tokens above."
}
```

```markdown
<!-- System prompt 範例：告訴 LLM 設計規則 -->
You have access to our design spec at design-spec.json.
Use ONLY those tokens. Reject any code using raw pixel values for spacing or color.
```

類比就像 API schema：你不會讓前端隨便猜後端的 endpoint 格式，同理也不應該讓 LLM 隨便猜你的設計規範。這篇對「已經在用 AI coding assistant 做 UI，但輸出常常不符合設計稿」的人最有直接幫助。

### 2. A developer's guide to designing AI-ready frontend architecture

`[工程知識]` `[AI輔助開發]` `[架構]`

過去設計元件和 API 只需要考慮「人怎麼用」，現在還要加上「AI agent 怎麼呼叫」。LogRocket 的這篇指南從架構層討論如何把 AI 當作一個真正的系統參與者設計介面，而不是事後貼一個 chatbot 上去。

最核心的洞察是：AI agent 跟人的差異在於「它不問問題，直接呼叫」。因此你的 API 和元件介面必須自己描述清楚——這就是 AI-ready 架構的出發點：

```typescript
// ❌ 不適合 AI agent 的設計：行為靠隱性慣例、沒有型別說明
function updateUser(data: any) { ... }

// ✅ AI-ready：schema 明確，LLM 呼叫後可自動驗證
type UserUpdate = {
  id: string;
  name?: string;
  email?: string;  // 選填欄位都明確標記
};
function updateUser(data: UserUpdate): Promise<void> { ... }
// agent 可以根據這個 type 精確組出合法的呼叫，不需要猜
```

```typescript
// 另一個模式：AI-friendly 的元件 props——避免過度隱性的 callback
// ❌ agent 不知道 onClick 的型別或副作用
<Button onClick={someHandler}>送出</Button>

// ✅ 明確的 action 標識，agent 可以根據 action 決定要不要呼叫
<Button action="submit-order" onAction={handleAction}>送出</Button>
```

文章也涵蓋了 agent 的 fallback 流程設計，以及如何在不改變既有 UI 邏輯的前提下，把 AI 接入設計成可以逐步啟用的 feature。對「正在把 AI 功能整合進現有專案」的團隊，這份指南的切入點比大多數泛泛的「AI 架構原則」更具體。

### 3. TypeScript at scale in 2026: What senior engineers should know

`[工程知識]` `[TypeScript]`

TypeScript 在 2026 年已經不只是「前端的靜態型別工具」，它同時活在 Node.js 服務、Cloudflare Workers 等 edge runtime、Next.js 的 server actions，以及透過 React Native 共用的跨平台 UI 套件裡。這篇文章是給「已經很熟 TypeScript 但正在面對多套系統共用型別」的進階工程師。

最重要的觀念轉換是：把 type 視為跨系統的**合約**，而不只是程式碼層的提示。放在 shared 套件裡的一個 `UserProfile` type，可以同時約束 Node API 的回傳格式和 React 元件的 props：

```typescript
// packages/shared/types.ts — 定義一次，跨系統共用
export type UserProfile = {
  id: string;
  name: string;
  plan: 'free' | 'pro';
};

// apps/api/src/users.ts（Node.js / Edge Runtime）
async function getProfile(id: string): Promise<UserProfile> {
  // 回傳格式受 UserProfile 約束，任何欄位缺漏或型別錯誤在 CI 就會被抓
  return db.users.findOne(id);
}

// apps/web/src/ProfileCard.tsx（React 元件）
import type { UserProfile } from '@shared/types';
function ProfileCard({ user }: { user: UserProfile }) { ... }
// 不需要在元件層重新定義同樣的 shape
```

文章特別強調 `satisfies` 運算子：它讓你在建立物件時做型別收窄，同時保留原始的字面量資訊，比 `as const` 更適合要跨系統傳遞的設定物件：

```typescript
// satisfies：型別安全 + 字面量保留
const theme = {
  primary: '#0052CC',
  spacing: { sm: 4, md: 8, lg: 16 },
} satisfies ThemeConfig;

theme.primary; // 型別是 '#0052CC'（字面量），不是 string
// 好處：IDE 補全時可以直接看到實際值，不用去查 ThemeConfig 定義
```

對正在把 monorepo 從「一包 JS 什麼都在一起」重構成「型別明確的多套件」架構的團隊，這篇是很好的參考起點。

### 4. ChromeDevTools/chrome-devtools-mcp

`[GitHub Trending]` `[AI輔助開發]` `[DevTools]`

Chrome DevTools 官方 MCP server——讓 Claude Code、Cursor、GitHub Copilot 等 AI coding agent 透過 MCP 協定直接操控 Chrome DevTools。9 月初登上 GitHub Trending，短短數天累積超過 5 萬 star，顯示 AI agent × 瀏覽器 debug 的需求已經相當迫切。

接入方式只需要在 MCP 設定裡加一條 server entry，之後 AI agent 就能在不需要截圖或手動描述的前提下，直接「看到」並操作瀏覽器狀態：

```json
// .mcp/config.json（或 Claude Code 的 mcpServers 設定）
{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",
      "args": ["@chrome-devtools/mcp"]
    }
  }
}
```

```
// 接入後，可以直接對 Claude Code 說：

// 場景 1：效能診斷
// "跑一下 /dashboard 頁面的 Lighthouse 報告，告訴我 LCP 的瓶頸在哪"

// 場景 2：記憶體洩漏
// "分析目前頁面的 JS heap，找出超過 10MB 的物件群"

// 場景 3：網路請求
// "錄製點擊「結帳」按鈕後的所有 network request，回傳 status code 非 200 的那些"
```

這不只是 debug 更方便——AI agent 現在可以以結構化資料的方式讀取瀏覽器狀態，對自動化測試、效能回歸檢測、甚至 PR CI 裡的視覺回歸都有潛在影響。

### 5. v2.0.0 RC — The Big <Reveal>

`[前端技術棧]` `[框架]` `[Solid.js]`

Solid.js 2.0 RC（2026 年 8 月）帶來整個反應式系統的架構翻新：**async 正式進入 reactive graph**。過去要讀非同步資料必須用專門的 `createResource`，現在普通的 `createMemo` 就能直接接受 Promise，Solid 自己負責解包和追蹤依賴。

before / after 對比：

```typescript
// ❌ Solid 1.x：非同步資料需要 createResource 才能進 reactive graph
const [data, { refetch }] = createResource(userId, fetchUser);
// data() 有 loading/error 狀態需要手動處理

// ✅ Solid 2.0 RC：createMemo 直接接 Promise，自動解包
const user = createMemo(() => fetchUser(userId()));
// user() 就是解包後的值，Suspense 自動處理 loading 狀態
```

同時移除的 API 還有 `batch`、`startTransition`——因為 Solid 2.0 的 async 更新自動在 microtask 批次，不需要手動標記。另一個大變化是 error boundary 現在是**自我修復**的，依賴 Signal 更新時會自動重試，不需要手動 reset。這是 breaking change 較大的版本，從 1.x 升級前需要仔細參閱 migration guide。

### 6. React is changing the game for streaming apps with the Activity component

`[前端技術棧]` `[React]` `[AI輔助開發]`

Mux 工程師從影片串流的角度解析 React 19.2 的 `<Activity>` 元件。`<Activity>` 讓你在「隱藏子樹」時不卸載元件——改用 CSS `display: none` 把畫面移除，但同時完整保留 DOM、state 與 effects（effects 會被暫停，DOM 不被銷毀）。對影音平台，這意味著使用者切換頁籤時，播放器不會因為 unmount 而重置進度、緩衝資料全部歸零。

```tsx
// ❌ 舊做法：切換 tab 時 VideoPlayer 被卸載，回來就要重新緩衝
{activeTab === 'video' && <VideoPlayer src={url} />}

// ✅ React 19.2 Activity：元件被隱藏但 state 完整保留
// mode="hidden" = display:none，不卸載 DOM
// mode="visible" = 正常顯示，effects 恢復執行
<Activity mode={activeTab === 'video' ? 'visible' : 'hidden'}>
  <VideoPlayer src={url} />
</Activity>
```

Mux 的使用情境：把「背景預讀下一集」的邏輯從複雜的 ref 管理中解放出來，用 hidden Activity 讓播放器在背景保持就緒。切換到該集時不需要重新初始化，延遲幾乎為零。

```tsx
// 實際模式：多個 VideoPlayer 同時存在，只有一個 visible
{playlist.map((episode) => (
  <Activity
    key={episode.id}
    mode={currentEpisode === episode.id ? 'visible' : 'hidden'}
  >
    <VideoPlayer src={episode.url} />
  </Activity>
))}
// 切換集數 = 改 currentEpisode，不 remount，下一集已在背景準備好
```

這個 pattern 對 tab 界面、wizard、modal 等「要保留狀態的切換場景」同樣適用，不限於影音。

### 7. Astro 7.2 [補收]

`[前端技術棧]` `[框架]` `[補收]`

Astro 7.2 帶來實驗性的**增量靜態建置**（Incremental Static Builds）：第一次 build 之後，後續只重新渲染「module graph hash 或 `cacheKey` 有變化」的頁面，其餘直接沿用快取，快取存在 `node_modules/.astro/` 下。

```ts
// astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  experimental: {
    incrementalBuild: true,  // 只重建有變動的頁面
  },
});
```

對有 1,000 頁的部落格或文件站，這代表「改一篇文章只需重建 1 頁而非 1,000 頁」，build 時間可從數分鐘縮短到數秒。要讓 CI 跨 job 也能用快取，只需把 `node_modules/.astro/` 納入 cache key：

```yaml
# GitHub Actions：快取 Astro 增量建置結果
- uses: actions/cache@v4
  with:
    path: node_modules/.astro
    key: astro-incremental-${{ hashFiles('src/**', 'astro.config.mjs') }}
```

同版本也加了 `astro preview --watch` 背景模式（讓 preview server 跑在後台不阻塞終端），以及給插件作者用的自訂 logger helper。

### 8. GoogleChromeLabs/use-webmcp-tool [補收]

`[前端技術棧]` `[AI輔助開發]` `[補收]`

WebMCP 是 Google Chrome Labs 的瀏覽器端 MCP 整合方案——讓**網頁本身**宣告支援哪些 MCP tool，再讓 AI coding agent 透過瀏覽器擴充套件發現並直接呼叫。`use-webmcp-tool` 是對應的 React hook，用宣告式語法把元件的 MCP 介面暴露出去：

```tsx
// 網頁元件宣告「讀取目前表單資料」的 MCP tool
const CheckoutForm = () => {
  const [values, setValues] = useState({ name: '', email: '' });

  useWebMcpTool({
    name: "getFormData",
    description: "Returns the current values of the checkout form fields",
    execute: () => values,  // agent 呼叫時直接拿到結構化資料
  });

  return <form>...</form>;
};

// AI agent 在編輯器裡就能說：
// "讀取結帳表單的目前欄位值，幫我補上測試資料並驗證格式是否正確"
// agent 呼叫 getFormData tool，拿到 { name: '', email: '' }，
// 再比對驗證邏輯，全程不需要截圖
```

```tsx
// 進階：暴露頁面狀態讓 agent 在除錯時可以直接讀取
useWebMcpTool({
  name: "getCartState",
  description: "Returns the current cart items and total",
  execute: () => ({
    items: cart.items,
    total: cart.total,
    couponApplied: cart.coupon ?? null,
  }),
});
```

這是把 AI agent 的能力從「程式碼層」延伸到「執行期畫面層」的關鍵橋梁——agent 不再需要靠截圖或手動描述來理解頁面狀態，可以直接用結構化資料操作。
