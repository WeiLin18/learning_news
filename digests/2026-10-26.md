### 1. What's New in Chrome DevTools — November 2026（Chrome 155–156）

`[工程知識]` `[Chrome DevTools]` `[AI輔助開發]`

Chrome for Developers 在 10 月 20 日發布的 November DevTools 更新涵蓋 Chrome 155 與 156 兩個版本，這次的改動有兩條主線：一是讓 DevTools 更友善 AI agent 使用，二是新增 CSS anchor positioning 的視覺化工具。

**AI agent 那條線：** DevTools Protocol 的 `get_css_styles` 工具加入 pagination 參數（`pageSize`、`pageIdx`），解決了大型頁面 CSS 回傳量爆炸的問題——以前一個樣式複雜的頁面，agent 可能一次收到幾千行 CSS，根本沒法處理；分頁後 agent 可以按需取用。工具也新增了 inherited rules、pseudo-elements、`@keyframes` 和 `@rules` 的格式化輸出，讓 agent 解析 CSS 的結構變得更容易：

```javascript
// DevTools Protocol 呼叫示意（agent 分頁取得樣式）
const styles = await session.send('CSS.getMatchedStylesForNode', {
  nodeId: targetNode,
  pageSize: 50,      // 每次最多回傳 50 條規則
  pageIdx: 0,        // 從第 0 頁開始
});
// 後續 agent 視需要取 pageIdx: 1, 2, …
```

**開發者工具那條線：** Elements 面板新增了互動式的 CSS anchor positioning 編輯器，可以用滑鼠拖曳 `position-area` 的格子，即時預覽錨定元素定位，省去反覆 trial-and-error 的時間。另外 Sensors 面板加入了 `navigator.cpuPerformance` 的 override 開關，方便模擬低階裝置。

在 Network 面板，Early Hints 的 preload 警告和 persistent overrides 現在可以直接在面板裡看到，Performance timeline 的滾動也更順暢。

### 2. TypeScript 7.1 Beta：Go 原生編譯器 API、Content Mappers、es2026 支援

`[工程知識]` `[TypeScript]` `[DX]` `[工具]`

TypeScript 7.1 Beta 於 10 月 20 日釋出，延續 7.0 引入的 Go 原生編譯器路線，這次的重點是「讓工具生態能在穩定 API 上建立」——也就是說，Volar、ts-morph、ts-migrate 這類工具以後不再只能靠不穩定的私有 API 運作。

**最大改動：新的 API 架構**

7.1 把 TypeScript 的 API 重組成多個入口點，每個入口點的穩定性等級不同：

```typescript
// 以前：一包 import，所有功能都從同一個地方取
import ts from 'typescript';

// 7.1 之後：按用途分開 import，穩定性更清楚
import { createProject } from 'typescript/sync';    // 同步 API（穩定）
import { Project }       from 'typescript/async';   // 非同步 API（穩定）
import type { Node, SourceFile } from 'typescript/types'; // 型別（穩定）
// 以前 /unstable 路徑裡的 API 逐步搬入對應的穩定命名空間
```

**Content Mappers：讓 TypeScript 看懂 Vue SFC 和 MDX**

Content Mappers 是一個插件機制，讓工具（如 Volar、next-mdx-remote）把嵌入格式（`.vue`、`.mdx`）裡的程式碼「對應」給 TypeScript 的語言服務，TypeScript 就能直接對這些嵌入的 TS/JS 提供型別檢查和補全：

```json
// tsconfig.json 啟用方式（注意：tsc 執行時需要 --allow-content-mappers 旗標）
{
  "compilerOptions": {
    "contentMappers": ["@vue/content-mapper"]
  }
}
```

**效能數字：** 在 MUI 文件專案上，型別檢查時間從 22.2 秒降到 11.9 秒（-46%），記憶體用量下降 49.6%。

**其他語言新功能：** Ambient modules 現在可以靠 import attributes 匹配（例如 `import data with { type: "json" }`，TypeScript 能給出正確型別）。`--lib esnext` 加入 `Promise.allKeyed`、`Iterator.zip`、`Iterator.prototype.chunks` 等新的 ECMAScript 提案方法。

RC 預計 2026-11-10，Stable 預計 2026-11-24。

### 3. HTML-in-Canvas API 更新：Origin Trial 延展至 Chrome 160，API 有重大改版

`[工程知識]` `[Web Platform]` `[WebGPU]`

Chrome 的 HTML-in-Canvas API 是過去 20 年前端開發一個懸而未決的問題的答案：**你一直無法在 `<canvas>`、WebGL 或 WebGPU context 裡渲染真實的 HTML DOM**——傳統做法要嘛是截圖（html2canvas）、要嘛是 foreignObject 的種種限制，且兩種方法都沒有原生的無障礙支援。

這個 Origin Trial 現在延展到 Chrome 160（預計 2027 年初），並且在 Chrome 155 帶來了幾個重大 API 變更：

```javascript
// Before（Chrome 148–154 的舊 API）：
const source = new HTMLSource(document.querySelector('.my-card'));
ctx.drawSource(source, 0, 0, 400, 300);

// After（Chrome 155+ 的新 API）：屬性和方法重新命名
const source = new HTMLImageSource(document.querySelector('.my-card'));
// 要求明確預分配材質記憶體（避免 lazy allocation 造成的掉幀）
await source.allocateTextureMemory(400, 300);
ctx.drawImage(source, 0, 0, 400, 300);  // 跟 Canvas 2D 的 drawImage 統一
```

**為什麼要求 allocateTextureMemory？** 舊版在首次 render 時才分配 GPU 記憶體，如果在動畫循環裡使用，第一幀會有明顯延遲（hitching）。新版要求開發者先宣告大小，GPU 記憶體提前備好，動畫就順暢了。

**已知限制與注意事項：** 目前只有 Chrome 支援（Firefox 和 Safari 尚未承諾實作）；開發者需要更新 Origin Trial token 才能繼續使用（token 不會自動續期）；部分互動事件（如 click）在 canvas context 裡的行為還在規格討論中。

這個功能在 HN 10 月 23 日的頭版獲得 120 點、61 則討論，說明社群對它的高關注度。

📖 [Chrome for Developers](https://developer.chrome.com/blog/html-in-canvas-ot-changes) ｜ 2026-10（Origin Trial 更新）｜ 優先來源（chrome.dev）

### 4. assistant-ui/assistant-ui — 可組合的 React AI 聊天 UI 元件庫（12,500+ stars）

`[GitHub Trending]` `[AI輔助開發]` `[React]`

`assistant-ui` 解決的問題是：打造 AI chat UI 時，你要嘛用一個很死板的整包元件（風格難以客製），要嘛從零手刻（又耗時）。它的設計理念是「composable primitives」——把 AI 聊天 UI 拆成細粒度的 headless 元件，你用 CSS 或 Tailwind 自己決定外觀：

```tsx
import {
  Thread,
  ThreadMessages,
  MessageInput,
  useAssistantRuntime,
} from '@assistant-ui/react';
import { OpenAIAdapter } from '@assistant-ui/ai-sdk';

// 最簡單的 chat UI 骨架：三個組合元件搭出一個完整對話介面
function MyChatUI() {
  const runtime = useAssistantRuntime(new OpenAIAdapter({ model: 'claude-sonnet-5-5' }));
  
  return (
    <Thread runtime={runtime}>
      <ThreadMessages />   {/* 訊息列表 */}
      <MessageInput />     {/* 輸入框 + 送出按鈕 */}
    </Thread>
  );
}
```

整個套件對各種 AI backend 都是開放的——支援 Vercel AI SDK v7、LangGraph、Mastra，也可以接自訂 streaming 協定。目前 `@assistant-ui/react` 在 0.15.x，整合不同 backend 的 adapter 包獨立發行。

Before/After 對比：

- **Before（自己從頭手刻）**：需要處理 streaming token 的 UI 更新、訊息 scroll-to-bottom、多輪對話狀態管理、中斷重試機制，一個完整 chat UI 大概要花 2–3 天。
- **After（assistant-ui）**：上面的 6 行程式碼就有一個可以用的 chat 介面，所有 streaming 和狀態都在 runtime 裡處理好了，你只需要把精力放在業務邏輯上。

月下載量超過 10 萬次，10 月在 GitHub Trending 持續出現，星數本月成長顯著。

### 5. TanStack Start 1.0 正式 Stable：React 生態裡的另一條全端路線

`[前端技術棧]` `[React]` `[框架]` `[全端]`

TanStack Start 1.0 在 10 月 13 日宣告正式 stable，是 React 生態除 Next.js 和 Remix/React Router 以外，第一個達到生產可用狀態的全端框架替代方案。創作者 Tanner Linsley 把它定位為「client-first」——在伺服器端渲染和 data fetching 上，它不像 Next.js 那樣預設 server-first，而是讓你明確決定每個路由和資料取用的策略。

**設計哲學上的差異（vs Next.js）：**

```
Next.js（server-first）：
  預設一切跑在 server，需要 client 的才明確標 'use client'
  Data fetching 在 server component 裡直接 await
  Router = Nested layout + file-based routing

TanStack Start（client-first）：
  預設 client，server functions 要明確用 createServerFn() 宣告
  Data fetching 整合 TanStack Query 的 client-side cache
  Router = TanStack Router（型別安全、不依賴 file-based convention）
```

**實際程式碼對比——server function 的宣告方式：**

```typescript
// TanStack Start 的 server function（明確宣告「這段跑在 server」）
import { createServerFn } from '@tanstack/react-start';

const getUser = createServerFn({ method: 'GET' })
  .validator((userId: string) => userId)  // 輸入驗證
  .handler(async ({ data: userId }) => {
    return await db.users.findById(userId);
  });

// client 端呼叫和普通函式一樣，型別是全端安全的
const user = await getUser({ data: '123' });
```

**注意事項：** React Server Components 支援在 1.0 裡仍是實驗性（預設關閉）。需要 Vite 8+ 和 TanStack Router 1.x。已移除的 deprecated API 包括 `.inputValidator()`（改用 `.validator()`）。

SSR throughput 經官方 benchmark 宣稱較舊版提升約 5.5 倍，但這是在特定工作負載下的數字，使用前建議自行驗證。

### 6. Next.js 緊急安全修補：兩個 Critical RCE + 一個 High DoS（請立即更新至 16.4.1 / 15.5.28）

`[前端技術棧]` `[Next.js]` `[安全]` `[緊急]`

Vercel 於 10 月 14 日發布了 Next.js 的帶外安全修補（out-of-band security update），修復兩個 Critical 等級和一個 High 等級的漏洞。目前 **沒有公開的漏洞利用報告**，但修補應盡快完成。

**三個漏洞快速摘要：**

| 漏洞 | 等級 | 影響版本 | 成因 |
|------|------|----------|------|
| CVE-2026-96889 | Critical (CVSS 9.5) | 16.x < 16.4.1 | librsvg SVG 處理路徑，未認證 RCE |
| GHSA-xqc2-xf4c-x3h3 | Critical | 16.0–16.4.0 | React Server Components + use cache 返回多個 TypedArray 時 RCE |
| GHSA-h3gv-c5rc-p453 | High | 16.x | Server Functions 過大輸入造成 DoS |

**最快的修補動作：**

```bash
# 升級 Next.js（同時修三個漏洞）
npm update next
# 或指定版本
npm install next@16.4.1

# 如果短期內無法升級，可先升 Sharp 作為 CVE-2026-96889 的緩解措施
npm install sharp@0.35.5
```

**RSC 漏洞的觸發條件：** GHSA-xqc2-xf4c-x3h3 只在 App Router + Cache Components 啟用、且 `use cache` 函式回傳**超過一個** TypedArray（如 `Uint8Array`、`Float32Array`）時才暴露。多數應用不會觸發這個條件，但只要有一個 cache function 回傳 buffer 陣列就要當心。

如果你的專案直接管理 React Server Components 套件（不透過 Next.js 的 bundled 版本），也要同步更新 React 到 19.0.9、19.1.10、19.2.9 或 19.3.1。

### 8. CSS random()：Chrome 156 讓 CSS 原生生成隨機值，Smashing Magazine 深度講解

`[Web Platform]` `[CSS]` `[瀏覽器新 API]`

CSS `random()` 函式跟著 Chrome 156（10 月 20 日 stable）正式登場，Safari 更早實作，Firefox 的支援也快了——這是一個讓 CSS 不需要 JavaScript 就能生成隨機值的新原語。Smashing Magazine 以「擁抱有意識的不完美」為主題，用幾個生動的 demo 說明它最有價值的使用場景：隨機化排版讓頁面感覺更「有機」，而不像機械複製。

**基本語法：**

```css
/* random(min, max) 在每次 layout 時產生一個 min ~ max 之間的隨機值 */
.card {
  /* 每張卡片隨機旋轉 -3deg 到 +3deg，像手放的感覺 */
  rotate: random(-3deg, 3deg);
  /* 每張卡片隨機縮放 0.95 到 1.05 */
  scale: random(0.95, 1.05);
}
```

**before/after：不用 JS 就能讓文字字母各自微微傾斜**

```css
/* Before：每個字母都完全一樣，像印刷品 */
.letter { rotate: 0deg; }

/* After：每個字母各自有隨機的微小旋轉，像手寫字體 */
.letter { rotate: random(-2deg, 2deg); }
/* 不需要 JS 生成 n 個 CSS custom properties、不需要建立 n 個 CSS class */
```

**目前的相容性與使用限制：**
- Chrome 156：已 stable（但 caniuse 資料可能有一點延遲）
- Safari：已支援
- Firefox 159：預計支援，目前 Positive signals 但尚未推出
- 漸進增強寫法：`@supports (rotate: random(-2deg, 2deg)) { … }`

每次 layout 重新計算才會得到新的隨機值（不是每幀），所以不會影響動畫效能。這個函式的定位不是「取代 JS 做複雜的互動隨機性」，而是「讓靜態佈局有細微的自然感」。
