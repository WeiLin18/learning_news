### 1. How Turbopack Chunks Your JavaScript

`[工程知識]` `[Next.js]` `[效能]` `[Turbopack]`

Turbopack 在分割 JavaScript 時面臨一個矛盾：切越多塊，請求數越多；切越少塊，跨頁的程式碼就越難共用。
這篇是 Vercel 工程師對 Turbopack 分塊演算法的完整解析，說明為何「直覺上切越多越快」其實不對。

核心概念是 **chunk group**——每個路由（如 `/home`、`/blog`）會對應一個 chunk group，Turbopack 把這個路由需要的所有模組歸到同一組，再決定哪些小塊可以合併。

```
# 範例：nextjs.org 實測數字
# 不合併：355 個請求，程式碼量最小
# 預設合併：~170 個請求（少一半），程式碼量幾乎不變
# 最大合併：更少請求，但程式碼多 10%（因為合併後的塊要跨頁面全部載入）
```

Before/After 對比：在 nextjs.org 實測，預設設定讓請求數砍半，而程式碼量幾乎不增加；但若一味追求「請求數最少」，反而會因為塊太大、跨頁複用率下降，總傳輸量多了 10%。新版 Next.js 也開放實驗性選項讓你手動調整分塊策略。

📖 [Next.js Blog](https://nextjs.org/blog/turbopack-chunking) ｜ 2026-09-03 ｜ 優先來源

### 2. Chrome 153 Beta：Self-Profiling API、空間音訊與記憶體安全 XML 解析

`[工程知識]` `[Chrome]` `[Web 平台]` `[效能]`

Chrome 153 是首個採用**兩週發布週期**的穩定版（9/8 正式推出），這期 beta 帶了三個對開發者影響較大的功能。

**JS Self-Profiling API** 讓你可以在真實裝置上對主執行緒取樣堆疊，找出 GC、layout、paint 各自佔用的時間，不用只靠 DevTools 手動錄製：

```javascript
// 開始取樣（每 10ms 一個樣本）
const profiler = await performance.profile({ sampleInterval: 10, maxBufferSize: 500 });

// 跑你想量測的程式碼...
await doSomeHeavyWork();

const trace = await profiler.stop();
// trace.samples → 每個時間點的呼叫堆疊
console.log(trace.samples[0].stackId); // 找出哪條路徑最耗時
```

另外，XML 解析引擎換成 Rust 實作（記憶體安全），預防過去常見的 use-after-free 類漏洞；`overflow: scroll clip` 也讓 `position: sticky` 能分別被不同祖先的捲軸容器限制，不用再靠 JS hack。

📖 [Chrome for Developers](https://developer.chrome.com/blog/chrome-153-beta) ｜ 2026-09-08 ｜ 優先來源

### 3. Signals 贏了框架戰，但 React 例外——Runes 與細粒度響應式完全指南

`[工程知識]` `[框架比較]` `[Signals]` `[React]` `[Svelte]`

Vue 3、Solid、Angular 22、Svelte 5、Preact Signals——除了 React 之外，2026 年幾乎每個主流框架都改採信號（signals）模型。傳統的 VDOM 差異比對整棵樹，而 signals 的細粒度更新只碰「真正改變的那個節點」。

用 Svelte 5 Runes 來舉例，差異最直接：

```svelte
<!-- Svelte 4（舊）：改 user.name 會重新渲染整個元件 -->
<script>
  let user = { name: 'Alice', age: 30 };
</script>
<p>{user.name}</p>

<!-- Svelte 5 Runes（新）：$state 讓依賴追蹤到「表達式」層級
     改 user.name 只更新這個 <p>，其他節點完全不動 -->
<script>
  let user = $state({ name: 'Alice', age: 30 });
</script>
<p>{user.name}</p>
```

Before/After 效能對比：有數據的 admin dashboard 案例顯示，細粒度更新讓重新渲染時間降低 30–60%。React 為什麼例外？因為 React 的設計假設是「整棵樹可以重新計算」，而 React Compiler 正在試圖用靜態分析達到類似效果，但架構上仍是 VDOM 模型。

### 4. HyperFrames：Write HTML. Render Video. Built for Agents.

`[GitHub Trending]` `[AI輔助開發]` `[工具]`

HyperFrames 是 HeyGen 開源的影片渲染框架，核心概念很直觀：你寫普通的 HTML + CSS + JS，它把每一幀渲染成影片。最初是為 AI agent 設計的（讓 agent 能「寫網頁→輸出影片」），但其實一般開發者也能用。

```bash
# 用 CLI 預覽或渲染
npx hyperframes preview ./my-scene/index.html
npx hyperframes render ./my-scene/index.html --output out.mp4
```

```html
<!-- index.html 長這樣──跟平常寫 landing page 完全一樣 -->
<div style="background:#0f0f23; color:#fff; font-size:48px; display:flex; align-items:center; justify-content:center; height:100vh;">
  Hello, HyperFrames
</div>
```

使用情境：product launch 影片、changelog 動畫、AI agent 自動生成示意圖。GitHub 目前 47K+ stars，`hyperframes-launches` 子 repo 裡有 HeyGen 自家產品發布影片的完整原始碼可以拆解學習。

## 前端技術棧 + 更廣泛 Web 平台

### 5. Vercel Fluid Compute：Serverless 函式現在能同時處理多個請求

`[前端技術棧]` `[Serverless]` `[Vercel]` `[效能]`

傳統 serverless 每個請求都佔一個完整的函式實例；Fluid Compute 讓同一個溫熱實例可以**同時**承接多個請求（in-function concurrency）。對 AI 串流回應、長尾 API 呼叫的成本影響很顯著。

```
# 傳統 serverless 模型
請求A → 實例1（等待 I/O 時閒置）
請求B → 實例2（另起一個，冷啟動 if needed）

# Fluid Compute 模型
請求A → 實例1 ┐
請求B → 實例1 ┘（共享同一個溫熱實例，I/O 等待期間彼此填充）
```

除了並發，Fluid Compute 還加了兩個特性：**bytecode caching**（在同一實例上跨請求保留已編譯的 JS，不用每次重新解析）、**post-response 背景處理**（回應已發送後繼續跑任務，不佔計費時間）。適合現在跑 AI 推論、LLM 呼叫的 Next.js / Edge 函式應用。

📖 [Vercel Blog](https://vercel.com/blog/fluid-compute-takes-any-shape) ｜ 2026-09-01 ｜ 開放搜尋補充

### 6. React Router v8：刻意「無聊」的大版本——ESM-only、Middleware 預設開啟

`[前端技術棧]` `[React]` `[React Router]`

React Router v8 的設計哲學是「boring major release」——它把 v7 的四個 future flags 直接轉正，
但幾乎沒有破壞性改動，從 v7 升到 v8 的 migration 被設計成 non-breaking。

主要變化一覽：

```
# 新 baseline（不符合就要升）
Node.js: 22.22.0+
React:   19.2.7+
Vite:    7+

# ESM-only：不再輸出 CJS 格式
import { createBrowserRouter } from 'react-router'; // ✅
const { createBrowserRouter } = require('react-router'); // ❌ v8 起不支援
```

Middleware 在 v8 成為預設路徑，讓身份驗證、請求 logging、自訂 headers 可以集中在一個地方處理，而不是散在每個 Route 的 loader 裡。這是 v8 的主要架構推力：「把橫切關注點（cross-cutting concerns）集中在 middleware 層」。

### 7. TanStack Start RSC vs Next.js RSC：效能、DX 與生產就緒度比較

`[前端技術棧]` `[React]` `[TanStack]` `[Next.js]` `[框架比較]`

TanStack Start 和 Next.js 都支援 React Server Components，但兩者的渲染模型差異很大。
LogRocket 這篇用同樣的 demo app 對比了關鍵數字，適合在選擇框架時參考。

效能數字對比（同一個 demo）：

```
                  TanStack Start    Next.js
Client JS (gzip)     116 KB         193 KB   ← TanStack 少 40%
Production Build      1.3 秒         5.1 秒   ← TanStack 快 4x
```

架構設計的核心差異：TanStack Start 把 RSC 當成「資料 primitive」，client 依然掌控元件樹，server 工作透過明確的 `createServerFn` 呼叫進行；Next.js 則讓 RSC 成為渲染模型的中心，每個元件預設是 Server Component，需要互動時才加 `'use client'`。作者結論：TanStack Start 在 2026 年已可用於生產，但 Next.js 的 RSC 生態更成熟；內容型網站傾向 Next.js，需要精細控制 client bundle 的 SaaS 傾向 TanStack Start。

📖 [LogRocket Blog](https://blog.logrocket.com/tanstack-start-rsc-vs-next-js-rsc-performance-dx-production-readiness/) ｜ 2026-06-26（較早，約 10 週前）｜ 開放搜尋補充

### 8. shadcn/ui：cn 套件取代本地 utils，新增 Questionnaire 元件

`[前端技術棧]` `[React]` `[UI Library]` `[shadcn/ui]`

shadcn/ui 的 September 2026 更新做了一個小而影響廣的改動：元件內部改成從 `cn` 套件 import `cn()`，不再依賴每個專案自己維護的 `lib/utils.ts`。

Before/After 對比：

```typescript
// Before（舊版）：每個專案要自備這個檔案
// lib/utils.ts
import { clsx } from 'clsx';
import { twMerge } from 'tailwind-merge';
export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}

// After（新版）：直接裝 cn 套件就好，utils.ts 簡化成一行
// lib/utils.ts（由 npx shadcn init 自動生成）
export { cn } from 'cn';
```

另外新增了 **Questionnaire** 元件，支援多步驟問答流程（intake form、agent clarification prompt、onboarding survey），適用於 Base UI、React Aria、Radix，八種樣式都有。現有專案不需強制升級，新裝的元件會自動用新的 cn 套件，舊的 lib/utils.ts 仍然相容。
