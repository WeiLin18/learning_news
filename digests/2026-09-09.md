### 1. React 19.3 正式釋出：View Transitions、Fragment Refs、Activity 全數穩定

`[工程知識]` `[React]` `[新版本]`

React 19.3 在今天（2026-09-09）正式釋出，最大亮點是三個實驗性 API 同步轉為穩定：`<ViewTransition>` 讓 UI 過場動畫直接用瀏覽器原生 View Transitions API 驅動，不需要額外的動畫函式庫；`<Activity>` 讓你能「隱藏但不卸載」組件，使用者切分頁時保留草稿與 scroll 位置；Fragment Refs 則讓 `ref` 可以附加到沒有 DOM 節點的 `<Fragment>` 上，方便量測組件邊界而不必在外層多包一個 `<div>`。

這個版本的設計哲學很清楚：讓瀏覽器原生能力成為首選，而不是用 JS 模擬。View Transitions 不需要你自己管 `document.startViewTransition()`，React 在 `startTransition` 更新時自動呼叫；Activity 也不需要手動管理 CSS `visibility`，框架直接接管隱藏/顯示的時序。

**範例一（ViewTransition 最小寫法）**：

```jsx
import { startTransition, useState } from 'react';

function Gallery({ photos }) {
  const [idx, setIdx] = useState(0);

  return (
    // 用 ViewTransition 包住要做動畫的區域
    <ViewTransition>
      <img key={idx} src={photos[idx]} alt="" />
    </ViewTransition>
  );
}

// 觸發 state 更新時呼叫 startTransition → React 自動執行瀏覽器 View Transition
// 舊圖片淡出、新圖片淡入，不需要任何 CSS keyframe
function next() { startTransition(() => setIdx(i => i + 1)); }
```

**範例二（Activity：隱藏分頁不卸載）**：使用者把「草稿」分頁切走再切回，若元件用 `<Activity mode="hidden">` 包住，input 的文字和 scroll 位置原封不動保留；比卸載後重新 fetch + 重新掛載快很多，因為 DOM 從未被移除。

### 2. TanStack Router Navigation Lanes：讓並行路由跳轉不再打架

`[工程知識]` `[TanStack Router]` `[路由]` `[補收]`

TanStack Router 引入「Navigation Lanes（導航車道）」概念，把並行的路由跳轉分到不同的獨立佇列，解決快速連點不同連結時的競態問題。過去若使用者在短時間內連點 Tab A → Tab B → Tab A，後發出的請求可能先完成，讓 URL 和頁面內容對不上；Lane 機制確保每個車道內的跳轉按序完成，車道之間互不影響。

文章用「高速公路車道」做類比：「快速道」給 Tab 切換（希望即時響應）、「一般道」給頁面內連結（可以等 loader 跑完），兩個車道各走各的、互不阻塞。核心 API 只是在 `<Link>` 上加一個 prop。

**範例一（指定 Lane）**：

```tsx
// Tab 切換的連結指定到 'fast' lane
// → 使用者點第二個 Tab 時，第一個 Tab 的 pending navigation 直接取消
<Link to="/messages" navigationLane="fast">訊息</Link>
<Link to="/settings" navigationLane="fast">設定</Link>

// 頁面內的「下一篇文章」連結走預設 lane，等 loader fetch 完才轉
<Link to={`/post/${id}`}>下一篇</Link>
```

**範例二（Before/After）**：修正前，快速按「訊息→設定→訊息」，有時停在「設定」（因為設定的 loader 回得更快）；加上 `navigationLane="fast"` 後，最後點的 Tab 永遠是最終畫面，不再受 loader 時序影響。

### 3. 用 React 19.3 的 View Transitions + Activity 做 AirBnB 式頁面過場動畫

`[工程知識]` `[React]` `[View Transitions]` `[教學]`

LogRocket 這篇教學以 AirBnB 風格的「房源列表→房源詳情」為場景，一步步示範 React 19.3 兩個新 API 的搭配用法：`<ViewTransition>` 搭配 CSS `view-transition-name` 讓同一張圖片在兩個頁面之間做「連貫動畫」（縮圖擴展成全頁大圖，不閃爍、不消失）；`<Activity>` 讓詳情頁在使用者 hover 到連結時預先 fetch 資料但不渲染，點擊後幾乎零等待感。

重點是 `view-transition-name` 的命名策略：列表頁和詳情頁若給同一個元素完全相同的 name，瀏覽器會自動在兩者之間建立「Shared Element Transition」，這個效果過去要靠 Framer Motion 的 `layoutId` 才能做到，現在用瀏覽器原生就夠了。

**範例（Shared Element Transition）**：

```jsx
// 列表頁：給圖片加 view-transition-name（每張圖的 name 要唯一）
function ListingCard({ id, photo }) {
  return (
    <ViewTransition name={`listing-photo-${id}`}>
      {/* 點擊前：小張縮圖 */}
      <img src={photo} className="card-thumb" />
    </ViewTransition>
  );
}

// 詳情頁：用完全相同的 name
function ListingDetail({ id, photo }) {
  return (
    <ViewTransition name={`listing-photo-${id}`}>
      {/* 點擊後：全頁大圖，瀏覽器自動做兩者之間的過場動畫 */}
      <img src={photo} className="hero-image" />
    </ViewTransition>
  );
}
// → 視覺效果：縮圖「飛進」詳情頁變成大圖，跟原生 App 一樣流暢
```

這篇適合已經會用 `startTransition` 的人，不需要另外安裝動畫函式庫，直接用瀏覽器原生能力。

### 5. ChatGPT 前端解剖：從 Next.js 到 React Router 7 的遷移路徑與效能數字

`[前端技術棧]` `[React]` `[效能]` `[架構分析]` `[補收]`

performance.dev 對 ChatGPT 網頁版做了徹底的逆向工程分析，追蹤了它從 Next.js 到 Remix 再到 React Router 7 的完整遷移歷程，以及每次遷移背後的技術原因。文章透過實測拿到具體數字：初始 DOM 節點數 548、TTFB 50–65 ms、首屏 LCP 約 1.2 s。每次遷移的核心驅動都是同一件事：OpenAI 工程師需要更細粒度的 Suspense 控制和更好的 streaming SSR 支援——這些在 Next.js App Router 的 conventions 下難以客製化。

文章也分析他們如何把主 JS bundle 壓到 < 80 KB（gzipped）——主要靠三件事：route-based code splitting、把 markdown rendering 的 library 移到動態 import、以及把與 UI 無關的 WebSocket 邏輯移到 Web Worker。

**範例一（preconnect 最佳化）**：

```html
<!-- ChatGPT 前端實際使用的 link 組合 -->
<link rel="preconnect" href="https://api.openai.com" crossorigin>
<!-- preconnect = 提前完成 DNS + TLS 握手，第一個 API 請求省掉整段連線時間 -->

<link rel="dns-prefetch" href="https://cdn.oaistatic.com">
<!-- dns-prefetch = 只做 DNS（成本更低），用於次要資源 -->
```

**範例二（動態 import 減少初始 bundle）**：

```js
// 把 markdown 渲染函式庫延遲到使用者真的開啟訊息後才載入
// → 初始 bundle 省掉 ~35 KB
const { marked } = await import('marked');
const html = marked(content);
```

### 6. Remix 3.0 RC：脫離 React、單一依賴、純 Web 標準

`[前端技術棧]` `[Remix]` `[React]` `[新版本]`

Remix 3.0 RC 最大的架構變動是**把 React 從 hard dependency 降為 optional peer dependency**——你可以用 Remix 搭配 Preact，或完全不用 UI 框架，直接操作 Web 標準的 `Request`/`Response` 物件。整個框架的依賴數量從以前的 6–8 個 `@remix-run/*` 套件砍到只剩一個 `remix`，安裝和升級流程大幅簡化。另一個亮點是「零配置的 Prerender」：在 `remix.config.ts` 指定哪些路由要靜態預渲染，build 時自動產出 HTML，不需要額外工具。

這個方向和 Remix → React Router 的合併背景相符：框架層只負責路由和資料加載，UI 渲染讓開發者自己選。

**範例一（安裝對比）**：

```bash
# Remix 2.x：要裝一整排套件
npm install @remix-run/react @remix-run/node @remix-run/server-runtime @remix-run/express

# Remix 3.0 RC：一個套件搞定，全部都在裡面
npm install remix@3.0.0-rc.1
```

**範例二（不依賴 React 的 loader 寫法）**：

```ts
// Remix 3.0 的 loader 只回傳標準 Web API，跟 UI 框架完全無關
export async function loader({ request }: LoaderArgs) {
  const data = await db.posts.findMany();
  // 直接回傳瀏覽器原生 Response，不需要 import 任何 Remix helper
  return new Response(JSON.stringify(data), {
    headers: { 'Content-Type': 'application/json' },
  });
}
```

### 7. SvelteKit 3 進入 RC：新增 SvelteMap 方法、sv CLI 整合 ai-tools

`[前端技術棧]` `[Svelte]` `[SvelteKit]` `[新版本]`

Svelte 官方部落格的 9 月更新帶來兩個重點：SvelteKit 3 釋出 RC 版（同時附自動遷移工具 `sv@next task sveltekit-3`），以及 Svelte 5.57 為 `SvelteMap` 新增 `getOrSet()` 等便利方法，讓響應式 Map 操作更精簡。SvelteKit 3 最受矚目的改善是 `load` 函式的型別推斷：以前 server load 回傳的資料傳到頁面時型別會丟失（全變成 `any`），現在能全程保留，搭配 TypeScript 的體驗大幅提升。

`sv` CLI 也新增了 `ai-tools` add-on，一鍵在專案裡加入對主流 AI coding agent 友好的設定（AGENTS.md 模板 + 工具設定），省去手動查各家文件的工夫。

**範例一（SvelteMap.getOrSet 新方法）**：

```svelte
<script>
  import { SvelteMap } from 'svelte/reactivity';

  // SvelteMap 的狀態是響應式的——修改它就會觸發畫面重新渲染
  const cart = new SvelteMap<string, number>();

  // Svelte 5.57 新增：getOrSet()
  // 如果 key 已存在就直接回傳現有值，不覆蓋；不存在才設預設值
  function addToCart(productId: string) {
    const qty = cart.getOrSet(productId, 0);
    cart.set(productId, qty + 1);
  }
  // 比先 has() 判斷再 set() 的寫法少一行，意圖也更清楚
</script>
```

**範例二（自動遷移指令）**：`npx sv@next task sveltekit-3` 會分析你的 SvelteKit 2.x 專案並自動套用 breaking change 修正（例如 import 路徑、config 格式的調整），比對著 changelog 手動改快很多。

### 8. Next.js 16.3 Instant Navigations：Dev 記憶體省 90%、CI Build 快 5.5×

`[前端技術棧]` `[Next.js]` `[效能]` `[新版本]`

Next.js 16.3 的兩個主要效能數字：長時間跑 dev server 時記憶體使用量最多省 90%（用 weak reference 重寫了部分 module cache，不再把所有已載入模組全部常駐記憶體）；開啟 disk caching 的 `next build` 在 CI 上最多快 5.5 倍——特別是只改動少數檔案的 incremental build，因為 Turbopack 的中間產物現在可以跨 build 複用。「Instant Navigations」指的是 App Router 點連結後幾乎感受不到等待：prefetch 的 RSC payload 暫存在 in-memory cache，點擊時直接拿，不用再發一次網路請求。

這版也新增了 glob import（wildcard import），讓你一次 import 整個資料夾下的所有 MDX 或 JSON 檔，不需要手動列清單，對 content-driven 的網站（部落格、文件站）特別有用。

**範例一（開啟 disk cache 讓 CI 快 5.5×）**：

```ts
// next.config.ts
const config = {
  experimental: {
    turbo: {
      // 把 Turbopack 的中間產物（AST、型別資訊）寫到磁碟
      // CI 把 .next/cache 目錄快取起來，之後的 build 只重新編譯改動的檔案
      persistentCaching: true,
    },
  },
};
export default config;
```

**範例二（Glob Import）**：

```ts
// 一次讀入 content/ 下所有 .mdx 檔，不用逐一 import
const posts = import.meta.glob('../content/**/*.mdx', { eager: true });

// → posts['../content/2026-09-remix-intro.mdx'] = { default: <MDXComponent/>, ... }
// 過去要維護一個手動的 index.ts 清單，現在不用了
```
