### 1. NoLoJS：把手風琴、輪播、Lazy Load 這些「順手」的 JS 需求還給 HTML 和 CSS

`[工程知識]` `[效能]` `[實務指南]`

Web 效能架構師 Aaron T. Grogg 在 Smashing Magazine 發表文章，整理了一份叫 NoLoJS 的清單：手風琴（accordion）、導覽選單、圖片延遲載入、輪播（carousel）這些幾乎每個網站都會做的互動效果，其實很多都不需要真的寫 JS——瀏覽器原生的 HTML/CSS 這幾年已經悄悄補上了這塊。他的說法很直接：「JS 不是不好，只是它有更重要的事要做，不該拿來管你的手風琴跟導覽選單」。

最好懂的例子是原生 `<details>`／`<summary>` 取代手寫手風琴：

```html
<!-- 過去:要寫 JS 監聽點擊、切換 class、算高度做展開動畫 -->
<!-- 現在:瀏覽器原生就有「展開/收合」語意,連鍵盤操作都內建 -->
<details>
  <summary>常見問題：退貨政策是什麼？</summary>
  <p>七天內都可以無條件退貨。</p>
</details>
```

輪播效果則可以用 CSS Scroll Snap 做出來，不用載入任何輪播套件：

```css
/* 沒有一行 JS,滑動/拖曳就能自然「卡」在每一張圖片上 */
.carousel { display: flex; overflow-x: auto; scroll-snap-type: x mandatory; }
.carousel img { scroll-snap-align: center; }
```

專案本身是一個開放的 GitHub repo，每個模式都附上 `component.html`／`styles.css`／`script.js`（只在真的需要時才有）三個檔案並列對照，方便直接複製貼上；README 也引用了 Jeremy Keith、Chris Ferdinandi、Kevin Powell 等長期主張「先用平台原生能力，JS 當最後手段」的工程師的文章，顯示這不是單一作者的個人偏好，而是一個持續有人在推的工程文化。對正在做效能優化、想砍掉不必要的 JS bundle 體積的前端團隊，這是一份可以直接拿來對照自己專案的檢查清單。

📖 [Smashing Magazine](https://www.smashingmagazine.com/2026/08/nolojs-overview-common-javascript-patterns-replaced-html-css/)（開放搜尋交叉比對，原始頁面因出網政策無法直接開啟；GitHub repo [aarontgrogg/NoLoJS](https://github.com/aarontgrogg/NoLoJS) 已直接開啟驗證內容）｜ 2026-08-12（較早，約 6 天前）｜ 優先來源（Smashing Magazine）

### 2. Building Tactile UX：一個不用物理引擎的「捏捏樂」互動玩具是怎麼做出來的

`[工程知識]` `[互動設計]` `[Web平台]`

Smashing Magazine 這篇由 Alexey Kopytin 撰寫的文章，記錄團隊打造一個網頁版「解壓捏捏樂」互動玩具時的架構抉擇：一般人做這種互動效果的第一直覺是上物理引擎（例如 Matter.js）或 WebGL，但團隊實測後發現物理引擎只能產生「看起來合理」的動作，而設計師真正想要的是「精準到每一格畫面」的**刻意設計動作**——例如角色被重壓後要先蓄力再彈開,這種節奏感是物理模擬算不出來的。於是團隊整個放棄物理引擎,改用 Lottie（播放設計師手繪的向量動畫 JSON）搭配原生 DOM 事件與距離運算,直接掌控每一段動畫要在什麼條件下播放。

核心概念很好懂——把「使用者按了多久、按得多用力」換算成「該播哪一段預先做好的動畫片段」：

```js
// 用按壓時間長度決定要播放哪一段預先設計好的 Lottie 動畫片段
// 而不是讓物理引擎「模擬」出一個看起來差不多的效果
function onSqueeze(pressDuration) {
  if (pressDuration > 1500) {
    lottiePlayer.playSegments([0, 181], true); // 「終極大擠」:精準的 181 格蓄力+釋放動畫
  } else {
    lottiePlayer.playSegments([182, 220], true); // 一般輕捏反應
  }
}
```

另一個關鍵是用滑鼠/觸控座標跟角色中心點的距離,來決定「捏」的部位跟強度,讓同一個角色在不同位置被觸碰時有不同反應,但整套邏輯都只是 DOM 事件監聽加基本的距離公式,沒有任何 canvas 或 WebGL 渲染。

這篇文章對「什麼時候該用物理引擎、什麼時候該用手工動畫」給出一個具體的判斷依據：**如果動作需要精準符合設計師的意圖（而不是「差不多合理」就好）,手工動畫反而比物理模擬更好控制**,對做品牌互動、遊戲化元素的前端工程師是很扎實的架構取捨案例。

### 3. Cloudflare OS：把「作業系統」的概念重新設計成給 AI agent 用的工作平台

`[工程知識]` `[架構]` `[AI輔助開發]`

Cloudflare 在自家「Agents Week」活動中開源了 Cloudflare OS——它不是 Linux／Windows 這種傳統作業系統，而是一個讓組織自行架設（self-host）的開放框架，把「AI agent」「應用程式」「組織內部工作流程」統一放進同一套執行環境管理。設計上分三個支柱：agent 專屬的隔離執行環境（agent 可以在裡面寫程式碼並執行）、內建安全治理框架（權限控管 agent 能碰到哪些內部資料/服務），以及可自訂的「micro-app」（讓非工程背景的員工也能拼出小工具）。整套系統跑在 Cloudflare Workers 上，出自 Kenton Varda 之手——他形容這是自己更早以前做的 Sandstorm.io（一個「精神類似」但更早期的自架平台專案）的精神續作。

最有說服力的不是技術規格，而是內部真實採用數據：Cloudflare 從今年 5 月開始讓全公司員工試用第一版，到 8 月時已經有「數千名」員工（不只是工程師）每天用它寫文件、拼投影片、把重複性雜務自動化、兜出內部小工具，例如：

```
情境示範（非工程背景員工的典型用法）：
行銷同事想要一個「每週自動彙整客戶回饋」的小工具
→ 在 Cloudflare OS 的 micro-app 環境裡，用對話方式描述需求
→ agent 在隔離執行環境裡直接寫程式、跑起來，權限被治理框架限制在「只能讀取指定的回饋表單」
→ 不需要工程團隊排期支援，也不會意外碰到不該碰的內部系統
```

對正在思考「AI agent 要怎麼安全地融入日常工作流程，而不是只做聊天視窗裡的問答」的技術主管，這是一個附帶大規模內部真實採用數據、而非純概念展示的具體案例；原始碼與文件已在 GitHub 上公開，Apache 2.0 授權。

### 4. stablyai/orca：把多個 coding agent 當一支艦隊來管理的桌面/手機/VPS 平台

`[GitHub Trending]` `[AI輔助開發]`

Orca 定位是「Agent Development Environment（ADE）」——不是又一個 coding agent，而是讓你同時開好幾個 coding agent（Claude Code、Codex、OpenCode、Cursor、Grok CLI 等 20 多種）各自在獨立的 git worktree 裡平行工作，並用一個介面統一追蹤、比較、review 它們的產出。目前約 47.3k star，MIT 授權，是本次調查中成長最快的 AI 輔助開發基礎設施類專案之一。

安裝與典型使用情境都很直接：

```bash
# macOS 用 Homebrew 一行裝好
brew install --cask stablyai/orca/orca
```

```
情境:同一個 bug,你想比較 Claude Code 跟 Codex 誰處理得更好
→ 在 Orca 裡開兩個平行 worktree,同一個 prompt 分別餵給兩個 agent
→ 兩邊各自獨立工作,互不干擾檔案狀態
→ 完成後在同一個介面裡逐行比較 diff、留言,選一個 review 通過就直接 commit
```

比較特別的是手機端整合：agent 跑到一半你不用守在電腦前，手機 app 會在 agent 完成或卡住時通知你，你可以直接在手機上看 diff、留言、丟後續指令；也支援把 agent 丟到遠端 VPS 上跑（"beefy remote box"），保有完整的檔案編輯、git、終端機能力，斷線後自動重連。對已經同時開多個 AI coding agent 平行工作、又覺得「視窗切來切去很亂」的前端工程師，這是目前這個方向裡功能最完整的單一收斂介面。

### 5. Vue 3.6.0-rc.4：Vapor Mode 收斂 Transition 與巢狀 v-for 的邊界案例

`[Vue]` `[框架]` `[Build工具]`

Vue 3.6 仍在 RC 階段，這個 rc.4 延續 rc.1～rc.3 一路在做的事：把 Vapor Mode（跳過 Virtual DOM、編譯期直接產出 DOM 操作指令的新編譯策略）在真實場景裡撞到的邊界案例逐一修掉。這一版重點修正集中在**元件狀態該在什麼時候被保留、什麼時候該被釋放**：例如巢狀 `v-for` 裡的元件被移除時，沒有正確把它從父層 scope 釋放掉；`Transition` 包裹的元件根節點，屬性繼承（`inheritAttrs`）的歸屬對象判斷有誤；以及巢狀分支被拆解重組時，本該保留的輸入框內容 effect 意外被清空。

其中一個具體例子——`v-for` 搭配 key 變化時，子元件的狀態該跟著哪個 key 走：

```html
<!-- 修補前:某些巢狀 fragment 情況下,子元件的 key 沒被正確保留,
     導致 Vue 誤判成「這是新元件」而重新建立,使用者輸入的內容意外消失 -->
<!-- 修補後:巢狀 fragment 裡的 key 正確傳遞,狀態能跟著對的元件走 -->
<TransitionGroup>
  <Item v-for="item in list" :key="item.id" v-model="item.value" />
</TransitionGroup>
```

因為 Vapor Mode 是元件層級的漸進式 opt-in（一個專案裡可以讓部分元件用 Vapor、其餘維持傳統模式），這一系列 RC 修正主要是讓「混用兩種模式」這個過渡期場景更穩定，不影響完全沒用到 Vapor 的既有專案。對已經在測 Vue 3.6 RC、準備等正式版就升級的團隊，這是持續追蹤 Vapor Mode 穩定度的例行進度。

### 6. Vite v8.2.1：修正 worker HMR 與 rebuild 後的整頁 reload 退化

`[Build工具][Vite]` `[框架]`

Vite 8 大版號重寫成 Rolldown 底層之後的例行修補版，這次的修正集中在開發體驗的細節：worker 檔案更新後，HMR（Hot Module Replacement）現在能正確被接受並套用，不會像修補前那樣不小心退回「整頁重新載入」這個較重的 fallback 路徑；同時新增 `server.fs.allow` 對 `input` 選項的支援，讓建置設定裡宣告的進入點檔案自動被視為允許存取的路徑，不用額外手動列一次白名單。

概念示意（HMR 判斷邏輯的修正）：

```
修補前:worker.ts 內容變更 → HMR 嘗試套用 → 判斷失敗 → 退回整頁 reload（連同主執行緒的畫面一起重新載入）
修補後:worker.ts 內容變更 → HMR 正確識別並只重建 worker 本身 → 主執行緒畫面不受影響,保留當前狀態
```

```js
// vite.config.ts —— input 指定的進入點現在自動納入允許存取清單
export default defineConfig({
  build: { rollupOptions: { input: 'src/main.ts' } },
  server: { fs: { allow: ['src'] } }, // 不用再手動把 input 對應的路徑也加進來
});
```

雖然都是維運性質的小修正，但「worker 檔案改一行卻要等整頁重新載入」在開發大型應用時是很常見的體感痛點，對重度使用 Web Worker 做運算分離的專案，這版能直接省掉不少等待時間。

### 7. Rspack v2.1.10：降低診斷噪音，並修補 rkyv 相依套件的資安漏洞

`[Build工具]` `[資安]`

Rspack 這個新 patch 主要做了兩件事：一是把前一版（2.1.9）新增的「未知 `import.meta` 屬性警告」收斂得更精準——原本的警告規則在真實專案的建置場景下太容易誤報，變成「一堆你不用管的噪音」，這版重新調整判斷邏輯，只在真正可疑的情況才跳警告；二是修補了內部相依的 Rust 序列化函式庫 `rkyv` 的兩個資安漏洞（RUSTSEC-2026-0233／0235）。範例概念（噪音收斂前後對比）：

```js
// 修補前 (v2.1.9):任何看起來不熟悉的 import.meta.xxx 都跳警告,
// 包含框架自己合法使用的內部屬性,導致 console 被大量無關警告淹沒
import.meta.hot // 某些框架合法用法,卻被誤判成「未知屬性」而跳警告

// 修補後 (v2.1.10):警告邏輯更精準,只在真正打錯字/確實未知的情況才提示
```

此外這版也新增了 ExternalModule 的 `chunkCondition` hook（讓開發者更細緻地控制哪些外部模組要進哪個 chunk），並修了 URL target 的 scope hoisting、字串 context 正規化等邊界案例，共 11 個合併的 PR、8 位貢獻者參與。對已經在用 Rspack 的團隊，資安修補（即使是間接相依）建議優先更新；噪音收斂則是直接改善日常開發時 console 的可讀性。

### 8. Angular v22.1.2：擋下偽裝成 SVG 的惡意 script host，並修正 i18n 屬性重命名下的安全檢查

`[Angular]` `[框架]` `[資安]`

這個修補版本裡最值得注意的是兩項資安相關修正：一是在核心渲染邏輯裡，明確拒絕「帶命名空間前綴的 SVG script host」——避免有人利用 SVG 內可以夾帶 `<script>` 的特性，用命名空間繞過既有的清理機制夾帶惡意腳本；二是修正 i18n 工具函式裡 `hasOwnProperty` 的檢查方式，改成能抵抗「屬性被打包工具重新命名」的寫法（例如某些打包工具的 mangle 選項會把物件屬性名稱改短，原本天真的字串比對可能因此被繞過）。

概念示意（i18n 安全檢查修正的邏輯）：

```ts
// 修補前:直接用字串比對物件屬性名稱,若打包工具重新命名了這個屬性,
// 檢查邏輯可能被繞過而誤判
if (obj.hasOwnProperty('someKey')) { ... }

// 修補後:改用不受屬性重新命名影響的方式做檢查
// 即使打包工具 mangle 了屬性名稱,安全檢查依然正確生效
```

另外也修正了表單模組裡 radio input 值變更時沒有正確同步的問題，以及 Router 把「協定相對 URL（protocol-relative URL，例如 `//evil.com/path`）」的特殊處理限縮到只在序列化情境生效，避免這類 URL 在其他地方被誤判成安全的內部路徑。對正在營運 Angular 生產環境、且有處理使用者輸入 SVG 或走 i18n 流程的團隊，這批修正建議優先確認並更新。
