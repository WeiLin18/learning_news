### [Next.js][資安][框架] August 2026 Security Release：AVIF 影像解析 RCE 與 Windows 路徑穿越 RCE，需立即升版

Next.js 在 2026-08-25 釋出 v16.3.3 與 v15.5.24，修補兩個 Critical severity 漏洞。第一個是 **AVIF 影像解析 RCE**：`<Image>` 元件在處理 AVIF 格式圖片時，底層的 libheif/sharp 存在任意程式碼執行漏洞；只要應用程式接受用戶上傳圖片或從外部載入 AVIF，均受影響。第二個是 **Windows 路徑穿越 RCE**：Windows 環境下攻擊者可透過構造特殊路徑繞過目錄限制，讀取或執行任意檔案。

升版方式只需更新 Next.js 版本，無需修改程式碼。若短期內無法升版，官方建議先停用 AVIF 支援並嚴格限制允許的圖片來源。

```js
// next.config.js — 緊急緩解方案：停用 AVIF 以規避 libheif 漏洞
module.exports = {
  images: {
    // 移除 'image/avif'，只保留 webp
    formats: ['image/webp'],
    remotePatterns: [
      // 只允許信任的圖片來源，不開放任意 hostname
      { protocol: 'https', hostname: 'your-cdn.example.com' },
    ],
  },
}
```

根治方式則是直接升版：`npm install next@latest` 或指定 v16.3.3 / v15.5.24。

### [Bun][工具鏈] Bun v1.4：核心從 Zig 改寫為 Rust，啟動快 50%、記憶體少 35%，帶來大量全新 API

Bun v1.4 是這一年最大的版本更新，把約一百萬行的核心從 Zig 完整改寫為 Rust。所有 benchmark 維持持平或超越 v1.3，binary 縮小約 20%、Linux 上啟動速度快 50%、記憶體用量減少 35%、閒置時 CPU 使用率降低 5 倍。新增 API 相當豐富：`Bun.Image`（影像處理）、`Bun.WebView`（內嵌瀏覽器視窗）、`Bun.markdown`（Markdown 解析渲染）、`Bun.cron()`（排程任務）、`Bun.Terminal`（終端模擬），以及 `bun run --parallel` 讓多個腳本並行執行。

Node.js 相容性同樣大躍進：單次新增 +1,517 個 Node.js 官方測試，是 Bun 1.0 以來最大進步；相容目標從 Node 24.3.0 提升至 26.3.0。新的解析工具（`Bun.JSON5`、`Bun.JSONL`、`Bun.JSONC`、`Bun.XML`、`Bun.TOML`）讓 Bun 直接處理帶有註解的 JSON、串流 JSON 及 XML，不需要額外安裝套件。

```ts
// 過去：需要安裝 json5 套件才能解析帶有 // 註解的 JSON
// import JSON5 from 'json5';

// Bun v1.4：直接內建，零依賴
const config = Bun.JSON5.parse(`{
  // 可以寫註解的 JSON5 格式
  port: 3000,
  host: "localhost",
}`);

// 內建 cron 排程，不需要 node-cron
Bun.cron("0 9 * * 1", () => {
  console.log("每週一早上九點自動觸發");
});

// 並行執行多個 npm scripts
// $ bun run --parallel build lint test
// 三個任務同時跑，總時間 = 最慢那個
```

### [GitHub Copilot][AI 開發] GitHub Copilot 進駐 Slack：在頻道內直接發派 coding 任務、開 PR、分流 bug

GitHub 在 2026-08-21 宣布將 GitHub Copilot 整合進 Slack（公開預覽），讓開發者可以直接在 Slack 頻道中 @GitHub，觸發 Copilot 執行程式碼相關任務：調查問題、分流 bug 報告、建立並標記 Issue、或在安全雲端沙箱環境中實作程式碼變更並開 PR——所有操作都保留人類審核步驟，並沿用現有的 GitHub 權限設定。

GitHub 同時作為 **Slack Code** 的首批啟動夥伴，Slack Code 是 Slack 新推出的頻道類型，專為 AI 代理協作而設計，讓「規劃 → 實作 → review」整個工作流程都可以在 Slack 內非同步完成，不需要在 Slack 和 IDE 之間切換。

**具體使用情境：**

```
# 在 Slack 的 #incident 頻道貼上錯誤訊息並輸入：
@GitHub TypeError: Cannot read properties of undefined (reading 'map')
       at UserList.tsx:42
       幫我找到相關 Issue，如果沒有就開一個並加上 priority:high 標籤

# Copilot 會：
# 1. 搜尋 repo 中相關的 Issue / PR
# 2. 如果沒有，建立新 Issue 並自動加標籤
# 3. 把結果連結回覆在同一則討論串
```

### [AI SDK][框架工具] Vercel AI SDK 支援 ACP（Agent Client Protocol）：一個 adapter 接所有 coding agent

Vercel 在 2026-08-13 推出 `@ai-sdk/harness-acp` 套件，讓 AI SDK 的 `HarnessAgent` 透過 **Agent Client Protocol（ACP）** 標準協定來執行任意 coding harness。過去若要支援 Claude Code、Codex、OpenCode 等不同 coding agent，每個都需要各自的 wrapper 套件；現在只要 harness 提供 ACP 相容套件，一個「meta adapter」即可統一處理，讓開發者在不改任何業務邏輯的情況下自由切換底層 agent。

這個設計的核心概念是「包裝協定而非工具」：`@ai-sdk/harness-acp` 適配的是 ACP 這個協定本身，而非特定工具——就像 HTTP 讓你換瀏覽器而不需要重寫網頁。目前 ACP v1 屬於實驗版本，尚缺乏 per-step token 計量與 mid-turn steering 等進階功能，但基礎 agent 執行流程已可正常運作。

```ts
// 過去：每個 agent 需要個別 adapter，切換成本高
// import { ClaudeCodeHarness } from '@ai-sdk/harness-claudecode';

// 現在：透過 ACP 統一介面
import { AcpHarness } from '@ai-sdk/harness-acp';
import { openCodeAcpPackage } from 'opencode-acp'; // opencode 提供的 ACP 套件

const agent = new HarnessAgent({
  harness: new AcpHarness(openCodeAcpPackage),
});

// 換成 Claude Code 只需改這一行，其他程式碼完全不動：
// harness: new AcpHarness(claudeCodeAcpPackage),
```

### ⬆️ 補收 [TanStack Router][框架架構][工程知識] Inside a TanStack Router Navigation：路由導覽的幕後機制全解析

*本篇補收自已關閉未合併的 PR #19（2026-08-16 日報）。*

TanStack Router 核心團隊在這篇文章中，以「navigation lane（導覽車道）」的概念解說路由器如何處理同時發生的多個導覽請求。路由器把導覽分成數個 lane，依 `push`、`replace`、`redirect` 等類型分開排隊，確保最新的用戶操作可以取消舊的 pending navigation，而不會互相污染——這解決了 SPA 中的一個經典 race condition：用戶快速點擊兩個連結，最終渲染的頁面不應該由哪個 fetch 先完成來決定，而應由哪個點擊最後發生來決定。

文章同時說明 `redirect`（由 server 或 loader 觸發）和 `replace`（直接替換 history stack）如何在各自獨立的 lane 中運作，避免不同類型的導覽互相干擾，對於有複雜 auth redirect 或多步驟 wizard 流程的應用特別有幫助。

```ts
// 問題情境：用戶快速連點兩個連結
// 沒有 lane 機制時，最終結果取決於哪個 fetch 先回來（race condition）

// TanStack Router 的 lane 機制：
// 同一 lane 的新導覽會自動取消舊的 pending 導覽
router.navigate({ to: '/posts' });   // 觸發 push navigation，進入排隊
router.navigate({ to: '/profile' }); // 同一 lane，取消 /posts，只保留 /profile

// 不同類型的導覽走不同 lane，互不影響：
// auth guard 的 redirect 和用戶的 push 不會互相取消
// → 結果更可預測，不會出現「點了 A 卻到了 B」的詭異行為
```

### ⬆️ 補收 [Cloudflare][AI 輔助工程][工程知識] How Cloudflare Enforces Engineering Standards Using AI：用 LLM 自動化 code review 規範審查

*本篇補收自已關閉未合併的 PR #16（2026-08-14 日報）。*

Cloudflare 工程團隊描述了他們如何用 AI 把工程規範審查（engineering standards enforcement）自動化。過去需要人工 code review 才能確認的規範——如錯誤處理模式、日誌格式、安全性 pattern、內部 API 使用規則——現在由 LLM 在 PR 建立時自動掃描並給出具體建議。這個系統並非取代人工 review，而是「人看之前先過一關 AI」，讓 reviewer 可以把精力放在業務邏輯，而非重複指出同樣的規範問題。

系統的核心作法是把工程規範文件轉為 LLM prompt，再讓模型對著 PR diff 逐條比對。任何有明確、可文字化定義的規則都可以用這個模式處理：命名慣例、測試覆蓋率要求、文件格式等。

```txt
[工程規範 → LLM prompt 概念示意]

規則：所有呼叫外部 API 的程式碼必須處理 timeout，
      且 timeout 值必須從設定檔讀取，不可硬編碼。

LLM 掃描 PR diff，標記：
  ❌ fetch(url, { timeout: 5000 })       ← magic number，違規
  ✅ fetch(url, { timeout: config.api.timeout })  ← 從設定讀取，合規

自動在 PR 留下建議回覆，附上正確範例與違規位置（檔案名 + 行號）
```

對想導入 AI code review 的團隊，這篇文章提供了從規則定義到 prompt 設計的完整思路，且 Cloudflare 的案例規模夠大，能說明這個方法在實際生產環境的可行性。
