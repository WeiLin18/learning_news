### 1. React Activity：一個讓 useEffect「消失」的隱藏模式

`[工程知識]` `[React]`

React 19.3 引入的實驗性 `<Activity>` 元件，可以把一段 UI 切換成「hidden」狀態——元件保留在記憶體裡但不渲染，重新 visible 時不用重新掛載。這聽起來像效能最佳化的好工具，但也帶來一個違反直覺的陷阱：在 `mode="hidden"` 期間，`useEffect` 的 cleanup 會被呼叫，但 setup 不保證立即重跑。

一句話總結：「一次 render 不再對應一次 effect」——這條 React 開發者習以為常的預設假設，在 Activity 模式下失效了。

**典型的坑（WebSocket 連線）**：

```jsx
// ❌ 這段邏輯在 <Activity mode="hidden"> 時會出問題
useEffect(() => {
  const ws = new WebSocket('wss://example.com');
  return () => ws.close(); // hidden 時 cleanup 跑了 → 連線被關掉
}, []);
// 但 visible 時 setup 不一定馬上重跑 → 連線可能永遠不恢復

// ✅ 改法：讓副作用「可重入」，能被中斷再恢復
useEffect(() => {
  let ws = null;
  function connect() {
    ws = new WebSocket('wss://example.com');
    ws.onclose = () => { if (ws) connect(); }; // 斷線後自動重連
  }
  connect();
  return () => { ws?.close(); ws = null; };
}, []);
```

**另一個好懂的類比**：想像你在看 YouTube，切到其他分頁（hidden），播放停止（cleanup）；切回來（visible），但播放器要緩衝一下才恢復（setup 延遲）——這段空窗就是 Activity 帶來的新狀態空間。

### 2. Next.js 16.3.6 緊急安全更新：修補 next/og 的 RCE 漏洞

`[工程知識]` `[Next.js]` `[安全性]`

Next.js 在 2026-09-22 發布 16.3.6，修補一個透過 `next/og`（Open Graph 圖片生成）觸發的遠端程式碼執行（RCE）漏洞。根本原因：底層 Satori 在渲染 SVG 時，對特定 XML 輸入的 escaping 不完整，若攻擊者能控制傳入 OG 圖片的內容（如動態標題、使用者名稱），就可能注入惡意內容並在伺服器端執行。

**影響範圍**：使用 `next/og` 且接受使用者可控輸入（URL 參數、資料庫欄位）作為圖片內容的 Next.js 應用。若你的 OG 圖片是純靜態字串，不受影響。

**Before/After 示範**：

```ts
// ❌ 升版前的危險用法：使用者傳入的 title 未經處理就進 SVG
export async function GET(req: Request) {
  const title = new URL(req.url).searchParams.get('title') ?? '';
  return new ImageResponse(<div>{title}</div>);
  // title 若含有特定 SVG entity 字串，Satori 舊版本可能執行它
}

// ✅ 升版到 16.3.6 後 Satori 已修補，官方同時建議加應用層防護
export async function GET(req: Request) {
  const raw = new URL(req.url).searchParams.get('title') ?? '';
  // 長度限制 + 去除可疑字元，減少攻擊面
  const title = raw.slice(0, 100).replace(/[<>"'&]/g, '');
  return new ImageResponse(<div>{title}</div>);
}
```

如果你的 Next.js 版本低於 16.3.6 且有對外開放的 OG 圖片 API（帶使用者輸入），建議本週內升版。

### 3. @astrojs/react 7.0：JSX 底層換成 Oxc、React Compiler 更容易啟用

`[工程知識]` `[Astro]` `[React]` `[建置工具]`

`@astrojs/react` 7.0 把 JSX 轉換的底層從 Babel 換成 Oxc（Rust 實作的 JS 工具鏈），帶來明顯的冷啟動與 HMR 速度提升，同時把 React Compiler 的設定路徑簡化成一個 flag，不再需要另裝 Babel plugin。

速度差異有多大？以中型 Astro 專案（約 200 個 React island 元件）為例：Babel 冷啟動約 4–6 秒，換成 Oxc 後降到 1–2 秒；HMR 更新也從約 800ms 降到 200ms 左右。

**React Compiler opt-in（升版後的設定方式）**：

```ts
// astro.config.ts
import { defineConfig } from 'astro/config';
import react from '@astrojs/react';

export default defineConfig({
  integrations: [
    react({
      // 7.0 新增：直接在 integration 設定啟用，不需另裝 babel-plugin-react-compiler
      experimentalReactCompiler: true,
    }),
  ],
});
```

**升版注意事項**：如果你有自訂 Babel plugins（例如 `babel-plugin-styled-components`），換 Oxc 後這些 plugin 不再生效，需要找 Oxc 對應的替代方案或改寫。遷移前先檢查 `babel.config.*` 裡有沒有自訂 plugin。

### 4. Addy Osmani：Agentic Skill Decay——AI 時代的技術退化警示

`[Blog]` `[AI輔助開發]` `[實務指南]`

Addy Osmani（Google Chrome 工程師）提出「Agentic Skill Decay」：當你越來越習慣把任務丟給 AI agent，你對某些技術細節的掌握度會慢慢退化——不是因為你變笨，而是缺少了「親自解決問題」帶來的隱性學習。他用肌肉萎縮做類比：不使用就慢慢退化，而且是無感的、漸進的。

三個月後某次工具斷線，你才發現自己對某些基礎操作的直覺已經模糊——這是文章想預防的場景。

**可以直接照做的對策清單**：

1. **刻意練習無 AI 模式**：每週至少一個下午不開 Copilot/Cursor，用純手工解決一個真實問題。
2. **先思考再問 AI**：哪怕只想 5 分鐘，讓大腦先啟動再外包——避免直接跳到「複製貼上 AI 答案」。
3. **讀懂 AI 給的每一行**：貼上之前能解釋這段程式碼為什麼這樣寫，不是貼上就跑。
4. **定期「盲測」自己**：每個月找一個「用 AI 很容易解」的題目，不用 AI 解一次，感受落差。

適合正在建立 AI 使用規範的團隊 lead，或已大量使用 AI 工具但想保持技術成長曲線的工程師。帶新人的情境尤其值得參考——初學者的 Skill Decay 速度比資深工程師快很多。

### 5. HyperFrames：用 HTML 寫腳本、直接渲染成影片（專為 AI agent 設計）

`[GitHub Trending]` `[AI輔助開發]` `[工具]`

HyperFrames 是 HeyGen 開源的影片製作框架，讓你用 HTML + CSS 描述每一幀的畫面，再直接渲染成影片。它的設計動機是：AI agent 很擅長寫 HTML，但不擅長操作時間軸型的影片編輯 UI——所以把影片的描述格式改成 HTML，讓 agent 可以直接產出。

概念上很像「Puppeteer 截圖 × N 幀 → 串成影片」，但 HyperFrames 加了時間軸語法、補間動畫，以及針對 agent 優化的 DSL。

**最簡單的範例（文字淡入的 2 秒影片）**：

```html
<!-- HyperFrames DSL：描述 2 秒影片，fps 30，1280×720 -->
<hyperframes duration="2s" fps="30" width="1280" height="720">
  <frame at="0s">
    <!-- 0 秒：文字全透明 -->
    <div style="opacity: 0; font-size: 48px; color: white;">Hello, World!</div>
  </frame>
  <frame at="1s">
    <!-- 1 秒：文字完全顯示，HyperFrames 自動補 opacity 漸變動畫 -->
    <div style="opacity: 1; font-size: 48px; color: white;">Hello, World!</div>
  </frame>
</hyperframes>
```

**Before/After 對比**：
- Before：設計師用 After Effects 拖拉時間軸，2 分鐘短影片需要 30 分鐘製作。
- After：工程師（或 AI）寫 HTML 腳本，HyperFrames 渲染，整個流程可程式化、版本控制、CI 自動產出。

### 7. JavaScript Weekly #803：tinyjs 進精選、TC39 Iterator flatMap 獲瀏覽器支援

`[JavaScript]` `[週報]` `[TC39]`

JS Weekly #803（2026-09-22）有兩個亮點：tinyjsapp（本期第 8 則）進入編輯精選，引發社群對「要多小才算輕量桌面 app」的討論；TC39 Stage 3 的 `Iterator.prototype.flatMap` 獲得 Chrome 128 / Firefox 133 的初步支援聲明，JS 原生的 lazy iteration 組合即將可以不靠 polyfill 使用。

**`Iterator.prototype.flatMap` 的好懂範例**：

```js
// 傳統做法：先展開成陣列再 flatMap，大資料集時吃記憶體
const bigArray = [1, 2, 3 /*, ...10 萬筆 */];
const result = bigArray.flatMap(x => [x, x * 2]);
// → 建立了一個兩倍長度的中間陣列，全部放進記憶體

// Iterator.prototype.flatMap：lazy，不建立中間陣列
function* range(n) { for (let i = 1; i <= n; i++) yield i; }
const result = range(100000).flatMap(x => [x, x * 2]);
// → 只有在 iterate 時才計算，記憶體用量是 O(1)
for (const val of result) {
  process(val); // 逐個處理，不建立整個結果陣列
}
```

這期還有 Deno 2 vs Node.js ESM 相容性的深度對比，適合正在評估換 runtime 的團隊。

### 8. tinyjsapp：5MB 以內的 JavaScript 原生桌面應用骨架

`[工具]` `[JavaScript]` `[桌面應用]`

tinyjsapp 是一個實驗性的桌面應用 skeleton，讓你用 JavaScript 寫 native 桌面 app，但整個執行檔（含 runtime）壓在 5MB 以內。比起 Electron app 動輒 100–150MB 的大小，差距非常驚人。

它的做法是捨棄 Chromium，改用各 OS 內建的 WebView（macOS 用 WKWebView、Windows 用 WebView2、Linux 用 GTK WebKit）搭配精簡 JS bridge。代價是無法鎖定瀏覽器版本，渲染行為會因 OS 而異——適合工具型 app（不需複雜動畫），且目標使用者 OS 比較新的場景。

**快速上手（最簡單的視窗）**：

```js
// main.js — 5 行建立一個原生視窗
import { createWindow } from 'tinyjsapp';

const win = createWindow({
  title: 'My App',
  width: 800,
  height: 600,
  html: '<h1>Hello from native!</h1>', // 直接給 HTML 字串或本地路徑
});

win.show();
```

**大小對比（同等功能的 app）**：

```
Electron app：~120 MB
tinyjsapp 打包結果：
  macOS：~3.2 MB
  Windows：~4.8 MB（含 WebView2 bootstrap）
  Linux：~2.8 MB
差異：縮小約 25–40 倍
```
