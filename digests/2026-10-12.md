### 1. What's New in Chrome DevTools — October 2026

`[工程知識]` `[Chrome DevTools]` `[AI輔助開發]`

Chrome DevTools 的 October 2026 更新（Chrome 153–154）帶來幾個對 AI agent 開發者特別實用的功能：`--no-javascript-evaluation` 旗標可在 AI 自動化腳本進行頁面檢查時暫停所有 JS 執行，避免 agent 在抓 DOM 時意外觸發副作用（例如送出表單、觸發追蹤事件）。Performance Insights 面板現在完整支援 soft navigation，SPA 的每次路由切換都能獨立計算 LCP 和 INP，不再只看整頁首次載入。

Agent Plugins 1.0 API 正式定案，讓第三方工具可以直接注入到 DevTools Protocol。舉例來說，錯誤追蹤工具（Sentry、Datadog 等）現在可以在 DevTools 裡新增自訂面板，不必要求使用者在瀏覽器外另開分頁：

```javascript
// Agent Plugins API 示意（插件在 service worker 裡宣告能力）
chrome.devtools.agent.registerPlugin({
  name: 'MyErrorTracker',
  capabilities: ['network', 'console'],
  // DevTools 打開時自動掛載，不需使用者手動啟用擴充功能
  onActivate: () => console.log('plugin ready'),
});
```

適合想在 CI/CD pipeline 裡整合 DevTools 自動化，或正在打造 AI coding agent 的開發者。

📖 [Chrome for Developers](https://developer.chrome.com/blog/new-in-devtools-october-2026) ｜ 2026-10-08 ｜ 優先來源（chrome.dev）

### 2. Chrome 155 正式支援 JPEG XL：比 JPEG 再省 30–50% 空間

`[工程知識]` `[Web平台]` `[效能]`

Chrome 155 開始原生解碼 JPEG XL（.jxl），底層使用 jxl-rs（純 Rust 實作的解碼器），Firefox v157 也宣布同步跟進，讓 JPEG XL 進入「主流瀏覽器全覆蓋」的里程碑。JPEG XL 最大的賣點是兩個方向都做到位：壓縮率比 JPEG 高 30–50%，也支援無損壓縮（比 PNG 小很多）、HDR 色域。

最特別的是「JPEG 無損轉碼」模式——把既有的 .jpg 無損轉成 .jxl，轉碼後的 .jxl 體積比原始 JPEG 還小約 20%，且能完全還原回原始 JPEG，不多不少。對已有大量舊照片的內容平台來說，不需要重新壓縮就能省空間：

```bash
# 把既有 JPEG 無損轉為 JPEG XL（可 100% 還原回原始 JPEG）
cjxl input.jpg output.jxl --lossless_jpeg=1
# 轉回 JPEG，位元組與原始完全相同
djxl output.jxl restored.jpg --jpeg_reconstruction_crc_check

# 壓縮一張風景照（有損，但視覺差異幾乎不可見）
# 800KB JPEG → 約 480KB JPEG XL
cjxl landscape.jpg landscape.jxl -q 90
```

Chrome 在 2022 年曾短暫下架 JPEG XL 支援，這次透過 Interop 2026 重新推進，算是「回頭路」正式走完。要注意的是目前多數 CDN 和 `<picture>` 元素的 `srcset` 已可搭配使用，但 Edge 的支援時程尚未公布。

📖 [Chrome for Developers](https://developer.chrome.com/blog/jpeg-xl-in-chrome) ｜ 2026-10-06 ｜ 優先來源（chrome.dev）

### 3. SvelteKit 3 正式發布

`[工程知識]` `[Svelte]` `[框架]`

SvelteKit 3 是 Svelte 生態最大的架構調整之一：設定檔從 `svelte.config.js` 整個搬進 `vite.config.ts`，`$lib` 別名也改為符合 Node.js Subpath Imports 標準的 `#lib`（好處是不需要額外的 bundler 設定就能讓編輯器和工具認識這個路徑）。建置工具升級到 Vite 8（底層換用 Rolldown，取代 Rollup），官方提供 migration CLI 一鍵處理大多數改動：

```bash
# 自動遷移：把 svelte.config.js 的設定搬進 vite.config.ts，更新 $lib → #lib
npx sv migrate sveltekit-3
```

Before / After 對比——路徑別名的寫法：

```typescript
// Before（SvelteKit 2）：$lib 是 SvelteKit 自定義的虛擬別名
import { Button } from '$lib/components/Button.svelte';

// After（SvelteKit 3）：#lib 是 Node.js 標準的 subpath import
// 需要在 package.json 加上 "imports": { "#lib/*": "./src/lib/*" }
import { Button } from '#lib/components/Button.svelte';
```

Remote Functions（在 server side 定義、client 可直接呼叫的型別安全函式，類似 SvelteKit 版的 Next.js Server Actions）已進入 SvelteKit 3，但目前標示為實驗性，官方建議暫時不要在正式環境使用。

📖 [Svelte Blog](https://svelte.dev/blog/sveltekit-3-is-here) ｜ 2026-10-01 ｜ 優先來源（svelte.dev）

### 4. shader-effects-inc/shaders — 跨框架 WebGPU shader 視覺效果元件庫

`[GitHub Trending]` `[WebGPU]` `[框架]`

`shaders` 提供超過 200 種視覺特效（漸層、噪點、毛玻璃、游標跟隨動畫等），封裝成 React、Vue、Svelte、Solid 和 plain JS 都可以直接用的元件，而且各框架的 props API 完全一致——把一個效果從 React 移植到 Svelte 只需要換一行 import：

```jsx
// React 版本
import { GlassEffect } from '@shaders/react';
<GlassEffect blur={12} tint="rgba(255,255,255,0.1)" />

// Svelte 版本（props 完全一樣，只換 import 來源）
import GlassEffect from '@shaders/svelte/GlassEffect.svelte';
<GlassEffect blur={12} tint="rgba(255,255,255,0.1)" />
```

v4.0.1 新增了一個 MCP server，讓 AI coding agent（Cursor、Claude Code 等）可以透過工具呼叫直接套用特效，不需要讀懂 WebGPU shader 語法——AI 只要呼叫 `add_shader_effect(component: "GlassEffect", props: {...})` 就能把效果塞進元件。這個 repo 從 10 月初到現在累積了約 2,700 顆新星，在 Trending 名單上持續出現。

📖 [GitHub](https://github.com/shader-effects-inc/shaders) ｜ 2026-10 ｜ 開放搜尋補充

### 5. Next.js 16.4 正式發布

`[前端技術棧]` `[Next.js]` `[效能]`

Next.js 16.4 主打開發體驗與建置速度：Lazy Compilation 讓 dev server 啟動時只編譯首頁，其他路由點進去才即時編譯（等待時間從「整個 app 的 compile time」縮短為「這條路由的 compile time」），在大型 monorepo 裡效果最明顯。Turbopack 的 on-disk cache 格式重寫，冷啟動快一倍。

React 19.3 打包進來後帶了兩個立即可用的新功能：

```tsx
// View Transitions API — 路由切換時加上過場動畫
import { unstable_ViewTransition as ViewTransition } from 'react';

// 包住頁面元件，切換時自動觸發瀏覽器原生過場
<ViewTransition>
  <Page />
</ViewTransition>

// 搭配 CSS 定義動畫
// ::view-transition-old 是舊頁面的快照
::view-transition-old(root) { animation: slide-out 300ms ease; }
// ::view-transition-new 是新頁面的快照
::view-transition-new(root) { animation: slide-in 300ms ease; }
```

```tsx
// browser() API — 明確標記「只在 client 執行」，Server Components 裡呼叫不會報錯
// 適合把第三方 SDK（analytics、chat widget）包起來，避免 SSR 時 window is not defined
const analytics = browser(() => import('./analytics-sdk'));
```

Cache Components 現在對新建立的 Next.js 專案預設開啟（React Server Component 的輸出自動快取到 CDN），舊專案需要自行 opt-in。

### 6. pbakaus/impeccable — 給 AI coding agent 的設計語言規格工具

`[前端技術棧]` `[AI輔助開發]`

Impeccable 解決的問題：讓 AI coding agent 生成 UI 時，輸出的元件跟設計系統保持一致。做法是維護一份結構化的規格檔（`.impeccable.yml`），裡面定義品牌顏色、字體、元件命名規則、間距系統，AI 工具讀這份檔後生成的 UI 就不會每次都用不同的 blue：

```yaml
# .impeccable.yml 範例
brand:
  primary: "#6366F1"    # 主色：所有 CTA button 用這個，不要用 indigo-500 或 #4F46E5
  text: "#1F2937"       # 正文字色

components:
  Button:
    variants: [primary, secondary, ghost]
    border_radius: 8px
    font_weight: 600    # 按鈕文字固定 semibold，不要用 bold

spacing:
  base_unit: 4px        # 所有間距都是 4 的倍數（4、8、12、16…）
```

Before / After 對比：

- **Before（沒有 impeccable）**：AI 可能在同一個頁面用 `#4F46E5`、`#6366F1`、`indigo-500` 三種寫法指向同一個品牌色，每次生成 button 的 border-radius 都不一樣。
- **After（有 impeccable）**：AI 工具讀到規格後，統一套用 `brand.primary`，生成的程式碼裡出現一致的 token，也不需要每次在 prompt 裡重複解釋設計規範。

本月在 GitHub Trending 累積約 6,400 顆新星。Cursor 和 Claude Code 的整合是直接在 project instructions / `CLAUDE.md` 裡加一行 `@.impeccable.yml` 引用。

### 8. The Code Nobody Reads — Addy Osmani 論 AI 時代的 code review

`[知名部落格]` `[AI輔助開發]` `[實務指南]`

Addy Osmani（Google Chrome 開發者關係）在這篇文章裡提出一個讓人不舒服的問題：在 AI 大量生成程式碼的今天，很多程式碼根本沒有人真的讀——PR 通過了、CI 綠了，但沒有人逐行理解那些邏輯。他把這種現象叫做「無人閱讀的程式碼」（the code nobody reads），並認為這才是 AI coding 真正的風險：不是「AI 寫錯」，而是「人沒有讀」。

他提出的因應方式不是「回去要求每行都 review」，而是建立新的信任模型：根據程式碼的「位置」和「風險等級」分配 review 深度：

```
Before — 以前的 review 文化：
  每個 PR 花差不多的時間，逐行確認語法和邏輯

After — 新的優先序：
  低風險（工具函式、有充分測試覆蓋）→ 只看測試，AI 生成可直接合併
  中風險（UI 元件、API 串接）       → 看輸入輸出邊界，確認錯誤處理
  高風險（auth 邏輯、資料寫入路徑） → 逐字讀，要求 AI 解釋每一行的假設
```

換句話說，AI 讓我們有能力生成更多程式碼，但也讓我們需要更清楚地知道「哪些程式碼值得花人的注意力讀」。文章裡有一張依風險層級分類的矩陣，可以直接拿來當 team review guideline 的起點。
