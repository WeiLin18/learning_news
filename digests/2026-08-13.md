1. **[Web平台][Baseline][工程知識] How Baseline Can Help You Ship Less JavaScript**
   Smashing Magazine 這篇文章主張，隨著 Baseline（記錄跨瀏覽器都已穩定支援的 Web API 的計畫）持續擴大覆蓋範圍，「你需要一個函式庫才能做到這件事」跟「瀏覽器本身就做得到」之間的差距正快速縮小。文章提出具體做法：列出專案所有依賴，逐一比對 Baseline 現況，能用瀏覽器原生 API 取代的就直接移除，例如日期/數字格式化可用 `Intl.DateTimeFormat`/`Intl.NumberFormat` 取代 moment.js/numeral.js、深拷貝可用結構化複製取代 lodash `cloneDeep`。文章估計一般中型 JS 應用可以省下 60–90KB（壓縮後）的依賴體積。範例：
   ```js
   // 舊寫法：引入整包 lodash 只為了深拷貝與分組
   import cloneDeep from 'lodash/cloneDeep';
   import groupBy from 'lodash/groupBy';

   // Baseline 現況：瀏覽器原生就做得到
   const cloned = structuredClone(original);
   const grouped = Object.groupBy(items, item => item.category);
   ```
   文章建議養成每季做一次這種「依賴健檢」的習慣。

2. **[資安][工程知識][supply chain] ChainDrop：keyv 與 cacheable npm 套件遭劫持，蠕蟲式攻擊波及逾 2,200 個套件版本**
   2026 年 8 月 4 日，npm 上被廣泛依賴的 `keyv`、`cacheable` 等套件維護者的 GitHub 帳號遭入侵，攻擊者直接把惡意程式碼推上主分支，讓每次 `npm install` 觸發的 preinstall script 竊取 npm、GitHub、雲端與 CI/CD 憑證。這個被稱為 ChainDrop（Shai-Hulud 家族的後續變種）的自我複製蠕蟲，會用偷到的 npm 發布權限自動把惡意版本回灌到維護者名下的其他套件，最終波及超過 450 個套件、逾 2,200 個版本，合計每月下載量超過 20 億次，受影響組織包括 Deliveroo、Qlik、ServiceTitan 等。技術上最特別的一點是攻擊者用一份 Ethereum 智能合約動態存放 C2 網域，只要發一筆鏈上交易就能整批換掉惡意基礎設施，完全不必更新已經散布出去的惡意程式本身，payload 還會植入 Claude Code 與 VS Code 的 hook 以求長期潛伏。範例情境：
   ```
   npm install（安裝一個間接依賴到 keyv/cacheable 的專案）
   → preinstall script 下載一個獨立 Bun runtime 執行第二階段惡意程式
   → 竊取 npm/GitHub/AWS/HashiCorp Vault 憑證
   → 用偷到的 npm 權限，把惡意版本發布到維護者名下其他套件
   ```
   由於這幾個套件是許多常見工具鏈的間接依賴，多數團隊從未「主動選擇」安裝過它們，建議立即檢查 `npm ls keyv cacheable cacheable-request file-entry-cache flat-cache`，並全面輪換暴露過的憑證。

3. **[AI輔助開發][實務指南][工程知識] AI coding tools still suck at context — here's how to work around it**
   LogRocket 這篇文章直指目前 AI coding assistant 最大的痛點不是「模型不夠聰明」，而是「上下文管理」：把 AI 當成「什麼都記得的朋友」而不是「專科醫生」，是最常見的錯誤用法。具體建議是每次切換任務類型（例如從除錯一小時後要改寫文件）就開一個全新對話，而不是在同一個超長對話裡不斷累積不相關的上下文，避免模型把舊任務的假設錯誤帶進新任務；也建議把專案的關鍵慣例（命名規則、目錄結構、禁止的寫法）寫成一份精簡的上下文文件，每次開新對話先貼給模型，取代讓模型自己從整個 repo 裡「猜」慣例。範例情境：
   ```
   情境：剛用 AI 修完一個複雜的效能 bug，對話已經 40 輪
   接下來要請 AI 寫一份完全不相關的 API 文件
   → 錯誤做法：在同一個對話繼續問，模型會被前面的除錯上下文汙染回答
   → 建議做法：開新對話，只貼「這份專案的文件寫作慣例.md」，重新開始
   ```
   對日常大量使用 AI coding agent、又覺得「回答品質時好時壞」的前端工程師，這是一份很實際的除錯清單。
   來源：LogRocket Blog（開放搜尋補充）｜https://blog.logrocket.com/fixing-ai-context-problem/

4. **[TypeScript][框架比較][工程知識] Why Angular, Vue, and ESLint Can't Upgrade to TypeScript 7.0 (Yet) — And Why TS 7.1 Changes Everything**
   TypeScript 7.0（代號 tsgo，把編譯器整個移植成 Go）在 7 月正式穩定，號稱型別檢查速度提升 8–12 倍，但這篇文章指出：如果今天直接把 Angular 22、Vue、Svelte 或 ESLint 專案升級到 TypeScript 7.0，建置會直接因為 peer dependency 版本鎖死（`ERESOLVE`）而失敗。根本原因是這些框架與工具長期依賴 TypeScript 舊版 Compiler API 做自訂 AST 轉換（例如 Angular 的樣板型別檢查、Vue 的 SFC 編譯、ESLint 的型別感知規則），而 tsgo 目前還沒有提供對等的原生 Compiler API。文章說明微軟與 Angular 團隊（對應 GitHub issue #69719）已在共同制定 TS 7.1 的 Compiler API 規格，預計 2026 秋季發布，屆時這些框架才能真正吃到 tsgo 的建置速度紅利。範例概念：
   ```
   現況（TS 7.0）：
   Angular/Vue/ESLint 專案 → npm install typescript@7 → ERESOLVE peer dependency 衝突

   TS 7.1 之後（預期）：
   框架透過新的 Compiler API 接上 tsgo → 保留自訂 AST 轉換能力 → 同時吃到原生編譯器速度
   ```
   對正在評估「要不要現在就升級到 TypeScript 7」的團隊，這篇提供了具體會卡在哪裡的技術原因，而不是只講「建議等等」。
   來源：DEV Community（開放搜尋補充，作者 the-modern-web）｜https://dev.to/the-modern-web/why-angular-vue-and-eslint-cant-upgrade-to-typescript-70-yet-and-why-ts-71-changes-441g
   發布日期：2026-08-05 前後（較早，約 1 週前）

5. **[AI輔助開發][框架比較][架構][工程知識] Taming the Blackbox: How Agentic Coding Brings Quality and Stability to the Autonomous Migration of a Frontend**
   德國顧問公司 mgm technology partners 在 K5 Future Retail 2026 大會上發表一個內部驗證專案：用 agentic coding 把一個電商前端從 SvelteKit 遷移到 React/Next.js，只用一名工程師、不超過 10 個人力工作日就完成一個可運作的版本，而這兩個框架在心智模型上並不相容。他們採用兩階段做法：第一階段先讓專職 AI agent 用「技術中立」的方式，擷取每個元件的行為、結構與外觀（而不是直接照抄 SvelteKit 的程式碼）；第二階段再讓另一組 agent 根據這份中立描述，用 React/Next.js 的慣例重新生成元件。這跟常見的「把程式碼整段丟給 AI 翻譯」做法不同，能避免把 SvelteKit 特有的寫法硬翻譯成語法正確、但不符合 React 慣例的怪異程式碼。範例概念：
   ```
   傳統做法：SvelteKit 元件原始碼 → 直接請 AI「翻譯成 React」→ 容易產出語法對但慣例怪的程式碼
   mgm 做法：SvelteKit 元件 → agent 擷取成技術中立描述（行為/結構/外觀）
           → 另一組 agent 依 React/Next.js 慣例重新生成 → 更貼近人類工程師會寫的版本
   ```
   對正在評估「換框架的成本是不是真的能靠 AI 大幅縮短時程」的技術主管，這是一個附帶具體人力天數的實測案例。

Comeau 詳細記錄他把自己部落格重寫成第二版的技術決策：前端維持 Next.js/React，但把 CSS-in-JS 換成 Linaria（編譯期抽出真正的 CSS，不用背負執行期 CSS-in-JS 的效能代價），語法高亮改用 Shiki（用真正的 TextMate 語法規則，而不是正規表達式湊出來的高亮），資料庫則選用 MongoDB 儲存文章內容與互動資料（例如留言、按讚）。文章特別解釋為什麼從「執行期 CSS-in-JS」換成「編譯期抽出 CSS」——前者每次 render 都要在瀏覽器重新計算 class name 與樣式，後者在 build time 就把最終 CSS 產出成靜態檔案，執行期零開銷。範例概念：
   ```jsx
   // 執行期 CSS-in-JS（舊版）：每次 render 都要計算樣式
   const StyledButton = styled.button`color: red;`;

   // Linaria（新版）：build time 就抽成純 CSS 檔，執行期跟寫一般 class 一樣
   import styles from './Button.module.css';
   <button className={styles.button}>Click</button>
   ```
   對正在評估「要不要從執行期 CSS-in-JS 換成編譯期方案」的前端工程師，這是一篇有具體取捨理由的實戰記錄。
   來源：Josh W. Comeau 個人部落格（AGENTS.md 指定名單內的工程師）｜https://www.joshwcomeau.com/blog/how-i-built-my-blog-v2/

7. **[GitHub Trending][AI輔助開發][測試] web-infra-dev/midscene**
   Midscene.js 是一個「視覺優先」的 UI 自動化框架，不像傳統 Playwright/Cypress 測試那樣依賴容易因改版而壞掉的 DOM selector，而是直接讓多模態視覺模型（支援 Qwen、Doubao、GLM-4V 等）「看」畫面截圖來定位元素，測試案例可以直接用自然語言描述。它可以整合進現有的 Playwright/Vitest 測試套件，也能讓 AI agent 完全自主執行測試，並支援 Web、Android、iOS、HarmonyOS、桌面應用等跨平台自動化，連沒有語意標記的 canvas 元素、自訂控制項、跨網域 iframe 都能定位。約 14.6k star、1.1k fork，持續有活躍開發。範例概念：
   ```js
   import { PlaywrightAgent } from '@midscene/web/playwright';
   const agent = new PlaywrightAgent(page);
   await agent.aiAction('在搜尋框輸入「筆電」並按下搜尋按鈕');
   await agent.aiAssert('畫面上應該出現至少 5 筆商品結果');
   ```
   對正在被「改版一次就要重寫一堆 selector」困擾的前端測試工程師，是一個值得評估的新測試路線。
   來源：GitHub Trending（TypeScript 分類，直接開啟驗證）｜https://github.com/web-infra-dev/midscene
