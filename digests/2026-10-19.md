### 1. A Practical Guide to Naming Things：UI 元件與設計 token 的命名方法論

`[工程知識]` `[設計系統]` `[實務指南]`

在 Smashing Magazine 的這篇文章裡，作者系統性地整理了命名 UI 元件、功能旗標與設計 token 時最常踩的坑，以及可以直接套用的策略。核心觀點是：命名是「給未來的自己和隊友找到這個東西」，而不只是「給這個東西貼標籤」。

最實用的參考來自 Iain Bean 的 Component Gallery，裡面收錄了超過 50 種常見 UI 元件，以及它們在不同設計系統（Material、Spectrum、Carbon）裡的各種別名——同一個「下拉選單」可能叫 Select、Dropdown、Picker、Combobox，命名前先查一下能省掉很多以後的溝通成本：

```text
元件別名對照（部分）：
  Accordion  → Collapsible / Disclosure / Expandable
  Breadcrumb → Breadcrumbs / PagePath
  Combobox   → Select / Autocomplete / Typeahead / Picker
  Modal      → Dialog / Overlay / Popup / Lightbox
  Toast      → Snackbar / Notification / Alert / Banner
```

設計 token 的命名則建議用語義層（`color-action-primary`）而非色彩層（`blue-500`），讓同一個 token 在亮/暗模式都不需要改名。

### 2. Vite+ 1.0 Stable：一個 `vp` 指令取代 ESLint、tsup、Husky

`[工程知識]` `[建置工具]` `[DX]`

Vite+ 1.0 正式 stable，目標是把前端工具鏈的安裝/設定成本降到幾乎為零：一個 `vp` CLI 統一處理 lint、typecheck、test、bundle、git hooks，不再需要個別設定 ESLint、tsup、Husky。底層依賴是 Vite 8.3.4、Vitest 5.0.4、Rolldown 1.2.13、Oxlint 1.88.0。

從零到有的體感差距很明顯：

```bash
# Before：光是把工具裝起來就要跑這些
npm install --save-dev eslint @typescript-eslint/parser vitest tsup husky lint-staged
# 還要逐一設定 .eslintrc, vitest.config.ts, build.config.ts, .husky/…

# After：Vite+ 一行搞定，全部有預設值
npm install --save-dev vite-plus
# 執行 lint + typecheck + test + build
vp check
# 打包成 library
vp build
```

1.0 新增了 GitLab CI 模板和 Docker 支援，讓 CI/CD 整合更直接。背景補充：Cloudflare 在 2026 年 6 月收購了 Vite+ 的母公司 VoidZero（也就是 Vite、Vitest、Rolldown 的主要維護方）。

### 3. JavaScript Weekly #805：為什麼開發者不「用平台本身的能力」？

`[工程知識]` `[Web平台]` `[週報]`

這期 JavaScript Weekly 的主打文是一篇分析文：瀏覽器已經原生提供路由（History API）、對話框（`<dialog>`）、拖放（Drag and Drop API）、滾動行為（`scroll-behavior`）、表單驗證……但開發者還是習慣裝套件重新造輪子。作者的論點不是「套件全都不該用」，而是「大多數人從來沒有認真評估過原生能不能做到」。

這個問題具體到什麼程度？

```javascript
// 許多人裝 smooth-scroll 套件來做這件事——
document.getElementById('section').scrollIntoView({ behavior: 'smooth' });
// 但直接寫 CSS 就夠了，瀏覽器支援已經很完整：
// html { scroll-behavior: smooth; }

// <dialog> 也常被 Modal 套件取代，但原生版本支援：
//   Escape 鍵關閉、focus-trap、backdrop 點擊、無障礙角色
document.querySelector('dialog').showModal();
// 關閉：
document.querySelector('dialog').close();
```

這篇引發了 HN 上的廣泛討論，正反意見都有——有人認為「套件提供一致的跨瀏覽器行為」，有人反駁「現在 Baseline 覆蓋率已經很高，這個理由越來越站不住腳」。

📖 [JavaScript Weekly](https://javascriptweekly.com/issues/805) ｜ 2026-10-06 ｜ 優先來源（JavaScript Weekly）

### 4. tester-army/e2e — 用自然語言描述測試目標的 AI 驅動 e2e 框架

`[GitHub Trending]` `[AI輔助開發]` `[測試]`

`e2e` 讓你在 TypeScript 測試裡混用兩種步驟：用自然語言描述「你想達到什麼目標」（交給 AI agent 決定怎麼操作），以及傳統的 Playwright 斷言（你自己寫定位器確認結果）。一旦 AI 步驟跑過一次、被驗證正確，後續可以「不啟動模型直接重播」，讓 CI 裡的測試速度和成本不受 AI 呼叫拖累。

實際的測試長這樣：

```typescript
import { test, ai, expect } from '@tester-army/e2e';

test('結帳流程', async ({ page }) => {
  await page.goto('https://my-shop.com');

  // AI 步驟：自然語言，不需要自己找定位器
  await ai('把第一個商品加入購物車，然後前往結帳頁');
  await ai('填入測試信用卡資訊並送出訂單');

  // 傳統 Playwright 斷言：你自己確認結果，AI 不介入這裡
  await expect(page.getByRole('heading')).toContainText('訂單已成立');
});
```

初始化只需要 `npx e2e init`。目前 v0.18.0，尚未 1.0（有 breaking change 風險），10 月初單日新增約 1,700 顆星，在 GitHub Trending 持續出現。

📖 [GitHub](https://github.com/tester-army/e2e) ｜ 2026-10-06 ｜ 開放搜尋補充

### 5. Deno 整個團隊加入 Cloudflare：獨立 runtime 將在 2027 年關閉

`[前端技術棧]` `[Web平台]` `[Node.js生態]`

Cloudflare 宣布收購 Deno，整個團隊（包含 Ryan Dahl 和 Bert Belder）並入 Cloudflare。時間線：Deno 獨立 runtime 繼續提供 bug fix 與安全性更新一年（到 2027 年），之後關閉；Deno Deploy 在六個月內關閉；JSR（JavaScript Registry）繼續在 Cloudflare 基礎設施上運營。Ryan Dahl 主導的下一步是把 Deno 的 `celld` 沙盒技術整合進 Cloudflare 的 `workerd`。

這個消息的衝擊在於：Deno 一直被定位成「修正版 Node.js」，它的關閉等於一條獨立路線的終結：

```text
Before（2026 年 10 月以前）：三條競爭路線
  Node.js → npm, CommonJS 歷史包袱，最多人用
  Deno    → 原生 ESM、Web 標準 API、內建 TypeScript
  Bun     → Node 相容、速度極快

After（收購之後）：格局改變
  Node.js → 繼續存在
  Deno    → 技術併入 Cloudflare Workers，獨立 runtime 消失
  Bun     → 目前仍獨立，成為事實上的「另一個 Node 替代品」
  JSR     → 繼續在 Cloudflare 維運
```

社群反應兩極：部分人擔心 runtime 生態被雲端廠商壟斷，也有人認為 Deno 的技術在 Workers 平台上會活得比獨立時更好。

### 6. Cloudflare Void SDK 開源：把 Vite 全端 app 部署到 Workers 只需一行指令

`[前端技術棧]` `[AI輔助開發]` `[建置工具]`

Cloudflare 在 ViteConf 2026 宣布開源 Void Platform、Void SDK 和 Void CLI，三個產品合在一起解決的問題是：讓開發者不需要了解 Cloudflare Workers 的設定細節，就能把全端 Vite app（前端 + API routes）部署上去。MIT 授權。

實際的使用流程極短：

```bash
# 初始化（自動偵測框架：Next.js、Nuxt、SvelteKit、Astro 等都支援）
npm install void
npx void init

# 部署（自動處理 build、bundle、Workers 設定）
npx void deploy
```

Void SDK 本身是可組合的 JavaScript SDK，可以只用其中的 `void/storage`、`void/queue`、`void/cache` 等模組，不一定要整包用。The New Stack 的報導角度有意思：「員工開始用 AI vibe-code 內部工具，IT 需要一個統一管理這些 app 部署的入口——Void 就是那個入口」。

📖 [Cloudflare Blog](https://blog.cloudflare.com/deploy-with-void/) ｜ 2026-10-15 ｜ 開放搜尋補充

### 7. Nuxt 4.6：Vue Vapor Mode 支援 + 伺服器架構解耦 + Nuxt CLI v4

`[前端技術棧]` `[Vue]` `[框架]`

Nuxt 4.6 是 v4.5.2 以來改動最多的小版本（420+ commits），三個主要方向：Vue Vapor Mode 互通（非破壞性，可選 opt-in，Vapor 元件和現有 Options/Composition API 元件並存）；`nuxt/server` 新 import surface（server 層解耦，理論上支援非 Nitro 的 backend，讓 Nuxt 可以部署到更多環境）；Nuxt CLI v4 要求 Node 22.21+，帶來全新互動式終端 UI（方向鍵切換路由、按鍵呼叫 build/lint）。

Cookie session 現在有官方加密方案：

```typescript
// nuxt.config.ts：設定 appSecret，useSession() 自動用 Iron encryption 加密 cookie
export default defineNuxtConfig({
  runtimeConfig: {
    // 環境變數，48 位元以上的隨機字串
    appSecret: process.env.NUXT_APP_SECRET,
  },
});

// server/api/login.post.ts：不需要裝 iron-session 等第三方套件
export default defineEventHandler(async (event) => {
  const session = await useSession(event, {
    password: useRuntimeConfig().appSecret,
  });
  await session.update({ userId: 42 });
  return { ok: true };
});
```

補充：Nuxt 3 已於 2026 年 7 月 31 日 EOL，若還在用 Nuxt 3 要盡快規劃遷移。

### 8. React Router v8：ESM-only、Middleware 預設開啟、社群開始評估 TanStack

`[前端技術棧]` `[React]` `[框架]`

React Router v8（2026 年 6 月 17 日發布）帶來幾個破壞性改動：純 ESM（不再支援 CommonJS）；`react-router-dom` 套件移除，import 路徑改成 `react-router/dom`；Middleware 預設開啟。最低要求是 Node 22.22.0+、React 19.2.7+、Vite 7+。

Migration 的痛點集中在兩個地方：

```javascript
// Before（v7）：
import { BrowserRouter, Route, Link } from 'react-router-dom';

// After（v8）：react-router-dom 套件消失，改從 react-router/dom import
import { BrowserRouter, Route, Link } from 'react-router/dom';

// 如果你的專案還在用 CommonJS (require)，v8 直接無法使用——
// 必須先遷移到 ESM 才能升級 React Router
```

InfoQ 的 August 2026 報導另外記錄了社群反應：部分團隊藉這次機會評估換到 TanStack Router（型別安全、內建 SWR 式快取、不依賴 Remix 的 API 設計），算是一次強迫再評估的時機點。
