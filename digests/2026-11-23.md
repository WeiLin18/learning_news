### 1. AI 在網頁開發中常犯的 10 大錯誤：Chrome 實測資料

`[工程知識]` `[AI輔助開發]` `[DX工具]`

Chrome 開發者團隊分析了 AI coding agent 在實際 Web 開發中最常犯的錯誤，並用可量化的指標呈現改善幅度：在「沒有任何引導」的情況下，AI 通過現代 Web 最佳實踐評測的比率只有 51%；安裝 Chrome Modern Web Guidance 技能包後，同一批評測的通過率跳到 91%。這篇文章整理了最常被 AI 踩到的陷阱類型。

最典型的兩類問題，一是**呼叫已廢棄 API**，二是**搭配安全標頭的模式不完整**：

```js
// ❌ AI 常見寫法：用 document.write（已廢棄且會阻塞 parser）
document.write('<script src="analytics.js"></script>');

// ✅ 現代替代：動態插入 script 元素
const script = document.createElement('script');
script.src = 'analytics.js';
document.head.appendChild(script);
```

```js
// ❌ AI 常見寫法：fetch 沒有帶 credentials 設定和 CSRF token
fetch('/api/delete-account', { method: 'POST' });

// ✅ 完整安全模式：加 credentials、CSRF header
fetch('/api/delete-account', {
  method: 'POST',
  credentials: 'same-origin',       // ← 帶上 cookie
  headers: { 'X-CSRF-Token': getToken() }  // ← 防 CSRF
});
```

這篇文章適合用來建立「AI 程式碼哪些地方最危險」的直覺清單。比起抽象的「AI 程式碼要 review」，Chrome 給出的是有資料支撐的具體類別——搭配 Modern Web Guidance 技能包一起裝，可以讓 AI 在源頭就少犯這些錯。

### 2. Angular TypeScript 7 Rust-based 預處理器 ngp Beta：Angular 編譯器速度翻倍

`[工程知識]` `[Angular]` `[建置工具]` `[TypeScript]`

Angular 編譯器團隊在 TypeScript 7（以 Go 重寫）正式落地後，釋出了一個 Rust-based 的 Angular 專屬預處理層，代號 **ngp（Angular Next-gen Preprocessor）**。它夾在 Angular template 語法解析與 TypeScript 7 Go 編譯器之間，把 Angular decorator、template binding 的「分析 + 轉換」這一步移到 Rust 執行，讓 Angular CLI 的冷建置時間在中型專案上縮短約 60%。

啟用方式是在 `angular.json` 裡多加一個 flag，不需要動應用程式程式碼：

```json
// angular.json — 啟用 ngp 預處理器（Beta）
{
  "projects": {
    "my-app": {
      "architect": {
        "build": {
          "builder": "@angular-devkit/build-angular:application",
          "options": {
            "experimentalPreprocessor": "ngp"
          }
        }
      }
    }
  }
}
```

效果是透明的——同樣的 TypeScript 型別、同樣的 Angular template、同樣的輸出，只是快了很多。

Before/after 範例（官方基準，大型 mono repo）：

```
Before（Angular 預設 TypeScript 7 編譯）：
  冷建置  53 秒
  增量建置 4.2 秒

After（啟用 ngp）：
  冷建置  21 秒 ← 縮短 60%
  增量建置 1.8 秒 ← 縮短 57%
```

目前是 Beta，建議先在 CI 環境試水溫，回報問題給 Angular team。若你的 Angular 專案已升到 TypeScript 7，這個 flag 是目前成本最低的加速方式之一。

### 3. Smashing Newsletter #585：Figma-to-code 工作流程 + Dragology 原生拖曳新方式

`[工程知識]` `[DX工具]` `[JavaScript]`

本期 Smashing Newsletter（2026-11-17）聚焦在兩個很有意思的主題。第一個是 **Figma-to-code 工作流程**——AI 工具把 Figma 設計稿轉成可用程式碼的過程已經成熟到可以當正式流程使用，這期整理了幾種不同的接法：直接用 AI plugin 匯出、搭配 design token 中間層、或把 Figma 當 AI context 的輸入源。

第二個是 **Dragology**，一個基於原生 HTML Drag and Drop API 的聲明式封裝，讓原本需要監聽 `dragstart` / `dragover` / `drop` 三個事件的邏輯，可以用幾個 HTML attribute 完成：

```html
<!-- 舊方式：三個事件、自己管資料傳遞 -->
<div id="item" draggable="true">...</div>

<script>
  item.addEventListener('dragstart', e => e.dataTransfer.setData('id', '1'));
  target.addEventListener('dragover', e => e.preventDefault());
  target.addEventListener('drop', e => {
    const id = e.dataTransfer.getData('id');
    // 自己寫移動邏輯...
  });
</script>
```

```html
<!-- Dragology：聲明式，不用寫事件監聽器 -->
<div data-drag-id="item-1" draggable="true">拖曳我</div>

<ul data-drag-target="list">
  <!-- dragology 自動處理排序、資料傳遞、動畫 -->
</ul>

<script type="module">
  import { Dragology } from 'dragology';
  Dragology.init();  // ← 掃描頁面上所有 data-drag-* 屬性、自動設定好
</script>
```

Figma-to-code 的部分適合正在建立 AI 輔助設計→開發流程的團隊；Dragology 則適合任何覺得原生 Drag and Drop API 太繁瑣的人，特別是需要做清單排序、看板拖曳的場景。

### 4. heydamir/unslop：讓 AI 生成的 UI 不再像 AI 生成的 Claude Code 技能包

`[GitHub Trending]` `[AI輔助開發]` `[DX工具]` `[UI設計]`

這是本週 GitHub Trending 增速最快的 repo 之一（~1,900 stars），由設計師 @heydamir 製作的 Claude Code 技能包。核心出發點很直覺：AI coding agent 生成的 UI 通常有一種「一眼就看出來是 AI 做的」的感覺——按鈕等大、圓角全一致、色調藍色、間距機械式等距。**unslop** 在 Claude Code 裡加掛一套設計規則，讓 AI 在產出 UI 程式碼時自動套用更像「人設計的」視覺語言。

安裝只需一行：

```bash
# 在 Claude Code 裡安裝 unslop 技能包
/plugin marketplace add heydamir/unslop

# 安裝後，要求 AI 生成 UI 時直接說 /unslop 或在 prompt 裡提
# "按照 unslop 設計原則" 就會觸發
```

Before/After 對比（同一個 login form，AI 預設 vs unslop 調整後）：

```
Before（AI 預設）：
  - 所有按鈕同樣大小、同樣藍色
  - 圓角統一 8px
  - 間距全部 16px
  - 只有一個視覺層次

After（unslop 套用）：
  - 主要動作（Submit）大且突出，次要動作（Cancel）小且低調
  - 色調有變化：主要用品牌色、次要用 neutral
  - 圓角跟隨功能：表單欄位較小圓角、CTA 按鈕較大圓角
  - 間距有節奏：section 之間間距大、元素之間間距小
```

適合常用 Claude Code 生成前端元件、但對產出的「AI 感」不滿意的工程師。這個技能包的本質是把設計師的視覺判斷力「注入」到 AI 的 UI 生成流程裡，不需要設計稿、不需要設計師介入。

### 5. SolidJS 2.0 穩定版：非同步進入響應式核心，等了五年的大版本

`[前端技術棧]` `[SolidJS]` `[框架]`

SolidJS 2.0 在 2026-11-16 正式穩定（v1.0 是 2021 年），這次最大的突破是**把非同步（async）直接整進響應式核心**——原本用 `createResource` 包裝非同步資料的做法不再是唯一選項，signal 本身就能承載非同步值，框架自動處理 loading / error 狀態。另一個 breaking change 是把 `<Suspense>` 改名為 `<Loading>`，讓語意更直觀。

SolidJS 1.x vs 2.0 的對比：

```jsx
// SolidJS 1.x — 需要 createResource 包裝，Suspense 處理 loading
import { createResource, Suspense } from 'solid-js';

const [user] = createResource(() => fetchUser(userId()));
//     ↑ 要另外建 Resource，signal 本身不懂 async

function UserCard() {
  return (
    <Suspense fallback={<p>載入中...</p>}>
      <div>{user()?.name}</div>   {/* user() 是 Resource，不是普通 signal */}
    </Suspense>
  );
}
```

```jsx
// SolidJS 2.0 — signal 直接包 async，<Loading> 取代 <Suspense>
import { signal, Loading } from 'solid-js';

// signal 可以傳入 async 函式，SolidJS 2.0 自動追蹤 loading/error 狀態
const user = signal(async () => fetchUser(userId()));

function UserCard() {
  return (
    <Loading fallback={<p>載入中...</p>}>
      {/* 寫法跟同步 signal 完全一樣，框架在背後處理非同步 */}
      <div>{user()?.name}</div>
    </Loading>
  );
}
```

遷移成本方面：官方提供 codemod，大多數的 `createResource` 呼叫可以自動轉換，但 `Suspense → Loading` 的改名需要手動搜尋替換（codemod 也會提示）。SolidJS 2.0 只支援 Node.js 20+。

### 6. New in Vue: November 2026——Vue 生態系 11 月重點整理

`[前端技術棧]` `[Vue]` `[Nuxt]` `[月報]`

這是 Vue 社群每月整理動態的系列文，11 月版本涵蓋了 **Vue 3.6 RC 進度更新**、**Vapor 模式的穩定路線圖**、以及幾個值得注意的生態系工具更新。Vue 3.6 的核心賣點之一——Vapor 模式（跳過 Virtual DOM 直接操作真實 DOM）——在這期裡有較具體的里程碑說明。

Vapor 模式 vs 一般模式的基本對比：

```vue
<!-- 一般 Vue 元件（有 Virtual DOM）-->
<script setup>
import { ref } from 'vue'
const count = ref(0)
</script>

<template>
  <button @click="count++">{{ count }}</button>
  <!-- 更新時：VNode diff → 真實 DOM patch -->
</template>
```

```vue
<!-- Vapor 模式（無 Virtual DOM，直接操作 DOM）-->
<script setup vapor>
<!--  ↑ vapor 關鍵字讓這個元件走 Vapor 編譯路徑 -->
import { ref } from 'vue'
const count = ref(0)
</script>

<template>
  <button @click="count++">{{ count }}</button>
  <!-- 更新時：直接 targetElement.textContent = count — 沒有 diff 過程 -->
</template>
```

API 層面兩者完全一樣，Vapor 是純編譯器最佳化，你不需要改寫任何邏輯。這期文章也整理了 Nuxt 4.6.4 的安全性修補（2026-11-02 release），以及幾個社群推薦的 Vue 3.6 升級注意事項。

### 7. TanStack DB 1.0 RC1：Going All In on Oracles

`[前端技術棧]` `[React]` `[狀態管理]` `[TanStack]`

TanStack DB 在 2026-10-29 釋出 1.0 RC1，結束了約 18 個月的 Beta 測試期，API 宣告穩定。它的定位是 TanStack Query 的「在地層」：Query 負責從 server 拉資料，DB 負責在 client 端管理那些資料的本地副本，讓你可以做即時響應的 filter/sort/group，而不需要 round-trip 回 server。名稱裡的「Oracles」是他們對測試模式的重新詮釋——用 `oracle` 描述「這份資料應該長什麼樣子」，測試不再 mock API，而是驗證響應式資料圖的狀態。

最簡單的 React 整合範例：

```ts
// 建立 collection（相當於 client-side 的一張表）
import { createDatabase, createCollection } from '@tanstack/db'

const db = createDatabase()

export const todos = createCollection(db, {
  name: 'todos',
  schema: { id: 'number', text: 'string', done: 'boolean' },
  // 資料來源接 TanStack Query，自動 sync
})
```

```tsx
// React 元件：用 useLiveQuery 拿響應式資料
import { useLiveQuery } from '@tanstack/react-db'
import { todos } from './db'

function TodoList() {
  // useLiveQuery：todos 任何一筆更新，元件自動 re-render
  // 注意：只有 filter 條件內的資料變動才觸發，不是全量 re-render
  const pending = useLiveQuery(todos.filter(t => !t.done))

  return (
    <ul>
      {pending.map(t => (
        <li key={t.id}>
          {t.text}
          <button onClick={() => todos.update(t.id, { done: true })}>
            完成
          </button>
        </li>
      ))}
    </ul>
  )
}
```

TanStack DB 比 TanStack Query 更適合「本地資料需要即時互動」的場景（例如看板、表格 inline 編輯、多 tab 同步）；比 Redux/Zustand 更適合「資料來自 server 且有複雜 filter 需求」的場景。RC1 的遷移指南說 Beta → RC1 的 breaking change 主要在 `createCollection` 的 schema 定義語法。

### 8. This Week In React #306：Vercel UI SDK、React Virtualized 10.0、Dragology

`[前端技術棧]` `[React]` `[週報]`

本期 React 社群週報（#305 的下一期，約 11/18 發出）本週最值得點進去看的是兩個：**Vercel UI SDK** 和 **React Virtualized 10.0** 的 TypeScript 大改寫。Vercel UI SDK 的概念是「headless behaviors」——把按鈕、輸入框、模態框的**行為邏輯**（鍵盤導覽、ARIA 屬性、focus 管理）打包成 hook，你只負責決定外觀，讓 AI agent 組合 behavior 來生成元件。

```tsx
// Vercel UI SDK — 行為與樣式完全解耦
import { usePressable, useTextField } from '@vercel/ui-sdk'

// usePressable 給你「像按鈕一樣運作」的所有屬性，不管你包什麼 DOM
function MyButton({ children, onPress }) {
  const { pressProps } = usePressable({ onPress })
  //     ↑ 包含：onClick、onKeyDown（Enter/Space）、role="button"、
  //            disabled state、active/hover state 管理
  return (
    <span {...pressProps} className="my-custom-button">
      {children}
    </span>  // ← DOM 元素跟樣式 100% 由你決定
  )
}
```

React Virtualized 10.0 則是把這個社群常用的超長列表渲染庫**從 Class Component 完全改寫成 TypeScript + Function Component + Hooks**，API 因此大幅簡化：

```tsx
// React Virtualized 10.0 — 新 hook 寫法（不再需要 FixedSizeList wrapper）
import { useVirtualizer } from 'react-virtualized'

function HugeList({ items }) {
  const ref = React.useRef(null)
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => ref.current,
    estimateSize: () => 48,   // ← 每列預估高度，支援動態高度
  })

  return (
    <div ref={ref} style={{ height: 400, overflow: 'auto' }}>
      <div style={{ height: virtualizer.getTotalSize() }}>
        {virtualizer.getVirtualItems().map(row => (
          <div key={row.key} style={{ position: 'absolute', top: row.start, height: row.size }}>
            {items[row.index]}
          </div>
        ))}
      </div>
    </div>
  )
}
```
