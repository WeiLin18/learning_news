### 1. React Compiler 2026：它真正自動記憶哪些？（哪些又會跳過？）

`[工程知識]` `[React]` `[編譯器]`

React Compiler（前稱 React Forget）自動 memoization 已在 React 19 進入正式生產環境，但許多開發者仍不清楚「編譯器到底在幫誰做什麼決定」。這篇文章從 AST 分析出發，列出編譯器主動介入的七個模式——包含 pure render 函式、靜態 props 傳遞、stable callback reference——以及三個它會直接跳過的情境：有 side effects 的 render、依賴 mutable ref 的 render、以及未經 `memo` 包裹卻用了 context value 的元件。

了解這些規則後，你就能讓元件「對 Compiler 友善」，在不需要的地方省去手動加 `useMemo`。Meta 將 Compiler 推廣到整個 codebase 後回報：初始載入快 12%、互動速度提升 2.5×、不必要的重渲染減少 30–40%。

```jsx
// ❌ Compiler 難以介入：有 side effect 的 render
function OrderStatus({ orderId }) {
  console.log('rendering', orderId)  // side effect → 編譯器不敢動這裡
  return <div>{orderId}</div>
}

// ✅ Compiler 友善：純粹 render，無 side effects
function OrderStatus({ orderId }) {
  return <div>{orderId}</div>
  // 等同於自動加上 React.memo(OrderStatus, ...)
}
```

```jsx
// ❌ Compiler 跳過：inline 物件每次 render 都是新參考
<Chart config={{ color: 'red', size: 100 }} />

// ✅ 提升到模組層級 → Compiler 可辨識為 stable reference
const CHART_CONFIG = { color: 'red', size: 100 }
<Chart config={CHART_CONFIG} />
```

適合正在導入 React Compiler 的團隊對照現有 codebase，確認哪些元件需要調整才能讓編譯器發揮最大效果。

### 2. RSC 實戰指南 2026：正確模式、常見地雷、何時才該用 Server Component

`[工程知識]` `[React]` `[RSC]`

React Server Components 推出一年多後，社群累積了足夠的生產踩雷紀錄。jsmanifest 這篇文章整理出一套決策框架：Server Component 負責靜態結構＋資料取得，Client Component 負責互動邏輯——最大的陷阱是在 Client 元件樹深處塞入 Server Component（React 19 不支援），或者每個層級都加 `"use client"` 導致伺服器優勢消失殆盡。

40% 的 JS bundle 縮減是可量化的好處，但文章也點出一個效能迷思：如果 API 需要 2 秒才回應，改用 RSC 串流 HTML 沒有魔法——根本問題是後端查詢沒優化。文章附有決策流程圖，可直接複製到專案的架構文件中。

```jsx
// ✅ 正確模式：Server Component 做資料取得，Client 做互動
// app/products/page.tsx — 不加 "use client"，直接查 DB
async function ProductsPage() {
  const products = await db.products.findMany()  // 無需 fetch API，直接資料庫
  return (
    <div>
      {products.map(p => <ProductCard key={p.id} product={p} />)}
      <AddToCartButton />  {/* 需要 onClick → 這個才是 Client Component */}
    </div>
  )
}
```

```jsx
// ❌ 常見地雷：在 Client Component 內直接放 async Server Component
"use client"
function ShoppingCart() {
  return (
    <div>
      <CartItems />  {/* ❌ 若 CartItems 是 async Server Component，React 會報錯 */}
    </div>
  )
}

// ✅ 解法：把 Server Component 當作 children 從外層傳入
"use client"
function ShoppingCart({ children }) {   // children = <CartItems /> 由 Server 提供
  const [open, setOpen] = useState(false)
  return <div>{open && children}</div>
}
```

適合用 Next.js App Router 但對 Server Component 邊界仍感到困惑的開發者。

### 3. React 19 useTransition & useActionState 完整指南：async 非阻塞 UI 的正確姿勢

`[工程知識]` `[React]` `[Concurrent]`

React 19 最重要的 concurrent 升級之一：`useTransition` 現在原生支援 async 函式，`isPending` 會在整個非同步操作期間保持 `true`（包含網路請求等待）。配合新 hook `useActionState`，可以在完全不引入外部狀態管理套件的情況下，打造流暢的表單送出與資料載入體驗。

這篇 2026 年指南還提供了「useTransition vs useDeferredValue 怎麼選」的決策樹：需要「標記某個 setState 為低優先度更新」→ `useTransition`；需要「延遲顯示舊值同時等待新值」（例如即時搜尋）→ `useDeferredValue`。兩者都是 React Compiler 友善的設計，組合使用效果更佳。

```jsx
// React 19：useTransition 現在支援 async 函式
function CheckoutForm() {
  const [isPending, startTransition] = useTransition()

  const handleSubmit = (e) => {
    e.preventDefault()
    startTransition(async () => {       // ✅ React 19 新增 async 支援
      await submitOrder(formData)       // isPending = true 整段等待期間
      router.push('/confirmation')      // 完成後才設 isPending = false
    })
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="card" disabled={isPending} />
      <button disabled={isPending}>
        {isPending ? '處理中⋯' : '確認付款'}  {/* UI 不凍結，頁面仍可捲動 */}
      </button>
    </form>
  )
}
```

```jsx
// useDeferredValue：輸入框立即更新，清單延遲等待
function ProductSearch() {
  const [query, setQuery] = useState('')
  const deferredQuery = useDeferredValue(query)   // query 先行，清單晚一拍

  const filtered = useMemo(
    () => products.filter(p => p.name.includes(deferredQuery)),
    [deferredQuery]  // 過濾用 deferred 版本，不會卡住輸入框
  )

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {/* 輸入時顯示舊結果，新結果算好了再換 */}
      <ProductList items={filtered} stale={query !== deferredQuery} />
    </>
  )
}
```

### 7. Svelte 5 最佳實踐 2026：用 Runes、Snippets 打造可擴展的生產應用

`[Svelte]` `[最佳實踐]` `[框架]`

Svelte 5 的 Runes 系統（`$state`、`$derived`、`$effect`、`$props`）穩定超過一年，這篇生產實戰指南針對「從 Svelte 4 遷移後的常見踩雷」做了系統性整理。最關鍵的轉變：舊版的 `writable store` 現在可以用 `.svelte.ts` 模組中的 `$state` 取代——reactive 狀態不再限定在 `.svelte` 元件檔裡，可以寫進任何 TypeScript 模組並 export 出去。

另一個重點是 Snippets（`{#snippet}`）的正確使用時機：它不是 React slots 的直接對應，而是「帶參數的 content projection」。文章給出明確判斷規則——只需要客製化某段 UI 模板但不需要獨立狀態時用 snippet；需要自己的 lifecycle 和邏輯時，才拆成獨立 component。

```ts
// ✅ Svelte 5：在 .svelte.ts 裡定義可共用的 reactive store
// cart.svelte.ts
let items = $state<CartItem[]>([])
let total = $derived(items.reduce((sum, i) => sum + i.price, 0))

export function addItem(item: CartItem) {
  items.push(item)  // 直接 mutate，$state 會追蹤深層變更
}
export { items, total }  // 在任何元件 import 都保有 reactivity
```

```svelte
<!-- ✅ Snippets：彈性 UI 模板，比新增元件成本更低 -->
<!-- DataTable.svelte -->
<script>
  let { rows, renderCell } = $props()
</script>

<table>
  {#each rows as row}
    <tr>
      {#each Object.values(row) as cell}
        <td>{@render renderCell(cell)}</td>
      {/each}
    </tr>
  {/each}
</table>

<!-- 使用端：傳入客製渲染邏輯，無需另建元件 -->
<DataTable rows={products}>
  {#snippet renderCell(value)}
    <strong class="text-blue-600">{value}</strong>
  {/snippet}
</DataTable>
```

### 8. 現代前端架構比較：React 19 vs Svelte 5 的效能模式與 INP 優化

`[框架比較]` `[React]` `[Svelte]` `[效能]`

這篇文章把 React 19 Concurrent 渲染與 Svelte 5 Runes fine-grained reactivity 放在同一個 INP（Interaction to Next Paint）指標框架下對比，給出「哪個架構決策最划算」的實測結論。核心發現：React 的 `useTransition` 對「已有大型元件樹」的應用收益最大（讓複雜更新降為低優先度）；Svelte 5 的 `$derived` 則讓計算性 state 天生是 lazy 的，不需要手動 memoize。

文章特別比較「即時篩選清單」功能在兩個框架的實作策略——這是說明心智模型差異最直觀的例子：React 端需要額外加 `useDeferredValue` 才能讓輸入框不卡頓；Svelte 端因為只有被讀取的 `$derived` 才重算，天然就不會有全樹重渲問題。這不是誰輸誰贏，而是兩種不同的設計取捨，理解差異才能做出適合專案的選擇。

```jsx
// React 19：「即時篩選清單」避免輸入框卡頓需要額外 hook
function ProductSearch({ products }) {
  const [query, setQuery] = useState('')
  const deferredQuery = useDeferredValue(query)  // 輸入快，過濾慢，分開處理

  // 1000 筆過濾，但 useDeferredValue 確保不阻塞輸入框
  const filtered = useMemo(
    () => products.filter(p => p.name.includes(deferredQuery)),
    [deferredQuery]
  )

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ProductList items={filtered} />
    </>
  )
}
```

```svelte
<!-- Svelte 5：同樣功能，天然不卡頓，無需額外 hook -->
<script>
  let { products } = $props()
  let query = $state('')

  // $derived 是 lazy 的：只有 ProductList 被渲染時才重算
  // 輸入框更新和過濾計算天然就在不同的更新批次中
  let filtered = $derived(
    products.filter(p => p.name.includes(query))
  )
</script>

<input bind:value={query} />
<ProductList items={filtered} />
<!-- 輸入框不卡頓，無需 useDeferredValue / useTransition -->
```
