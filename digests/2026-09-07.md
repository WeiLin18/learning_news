### 1. Oxc 發布 React Compiler 的 Rust Native 移植版，速度超越 React 官方

`React` `React Compiler` `Rust` `Oxc` `效能`

React Compiler 原本以 JavaScript 寫成，效能受限。Oxc 團隊在 2026 年 8 月 4 日發布 `oxc-transform-react` v0.0.1，這是用 Rust 重寫的 React Compiler，封裝成 Node.js native bindings。相比 Babel 的 JS 實作快 12–15 倍，甚至比 React 官方自己的 Rust 移植還快 2 倍——Oxc 團隊在超過 100 個熱門開源 repo 的 10 萬個以上原始檔上驗證過相容性。

`@vitejs/plugin-react` v6.1.0 同步釋出，加入 `compiler: true` 選項，讓 Vite 專案一行設定即可切換到 Rust native 版本。Bun 也在同一時間整合了這個工具鏈，讓 React 開發者多一個零設定的選擇。

```js
// vite.config.js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [
    react({
      compiler: true, // 啟用 Oxc 的 Rust 版 React Compiler（實驗性）
    }),
  ],
})
```

```bash
# 效能對比（同一個大型 codebase）
# Babel（JS，舊）：  編譯 10 萬個檔案 ≈ 45s
# Oxc（Rust，新）：  編譯 10 萬個檔案 ≈ 3–4s  （12–15× 加速）
```

### 2. Container Timing API：第一個能量測「任意元件渲染時間」的瀏覽器原生 API

`Web Platform` `Performance` `Browser API` `Chrome`

現有的 `LargestContentfulPaint`（LCP）只量測頁面上最大的單一元素，沒辦法知道「你定義的某個元件」究竟什麼時候完成渲染。Container Timing API 是 Bloomberg 與 Igalia 共同提案、目前在 Chrome 進行 origin trial 的新 API，讓你用一個 HTML 屬性標注任意 DOM 區塊，就能透過 `PerformanceObserver` 收到那個區塊「第一個有內容的子元素出現」的時間點。

實際使用場景：商品列表要等 API 回來才有圖片，過去只能靠 `performance.mark()` 手動打點；現在直接在容器上加屬性，瀏覽器幫你自動量測。SSR 框架也能受益，因為量測的是實際渲染到畫面的時間，不是 JS 執行的時間——這是現有手動打點做不到的。

```html
<!-- 在要量測的區塊加上 containertiming 屬性 -->
<ul containertiming="product-list">
  <li><img src="..." /><span>商品 A</span></li>
  <li><img src="..." /><span>商品 B</span></li>
</ul>
```

```js
// 用 PerformanceObserver 接收量測結果
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // entry.identifier === "product-list"
    // entry.renderTime：第一個有內容的子元素出現在畫面上的時間（ms）
    console.log(`${entry.identifier} 首次內容繪製：${entry.renderTime.toFixed(1)}ms`)
  }
})
observer.observe({ type: 'container-timing', buffered: true })
```

### 4. This Week in React #295：StyleX 回歸話題、Rust 版 React Compiler 進 Vite 與 Bun

`React` `週報` `StyleX` `React Compiler` `This Week in React`

本週 React 社群最熱的話題是 Meta 的原子化 CSS-in-JS 方案 **StyleX** 突然在 X 上大量曝光——多篇實際整合心得同時出現，讓原本小眾的工具重回討論焦點。StyleX 的核心賣點：CSS-in-JS 的開發體驗（型別安全、co-location）、零 runtime 開銷（編譯時轉成原子 class）、最終 CSS bundle 極小（每個屬性各自是獨立 class，高度可複用）。

另一重點是 React Compiler 的 Rust 版本（對應本期第 1 則）現在可透過 Vite 和 Bun 原生使用，本期週報做了整合說明。`ReactDOM browser()` API 也被重點介紹（見本期第 5 則）。其他更新包含：Zod 4.5、pnpm 12.0、Remix 3.0 RC、Rspack 與 Webpack 最新動態。

```jsx
// StyleX 使用範例：樣式定義在 .stylex.ts 裡
import * as stylex from '@stylexjs/stylex'

const styles = stylex.create({
  // 每個屬性各自成一個原子 class，高度可在整個 app 複用
  button: {
    backgroundColor: 'blue',
    color: 'white',
    padding: '8px 16px',
    borderRadius: '4px',
  },
  danger: {
    backgroundColor: 'red', // 只覆蓋這一個屬性的 class
  },
})

function Button({ variant, children }) {
  return (
    // 組合多個樣式，StyleX 自動處理優先順序
    <button {...stylex.props(styles.button, variant === 'danger' && styles.danger)}>
      {children}
    </button>
  )
}
```

### 5. ReactDOM browser()：讓元件明確宣告「我只在瀏覽器端跑」

`React` `React Canary` `SSR` `新 API`

React Canary 新增 `browser()` 函式，搭配 `use()` hook 使用，讓元件宣告「此元件只在瀏覽器端渲染」。在 SSR 階段，React 遇到含 `use(browser())` 的元件，會直接把最近的 `<Suspense>` fallback 輸出到 HTML，不嘗試在 server 渲染；等到瀏覽器端 hydrate，`use(browser())` 回傳 `undefined`，元件正常執行。

這個 API 的設計目的是給**資料請求函式庫**使用：當函式庫在 server 端沒有初始資料時，可以直接把渲染推遲到 client，而不需要在 library 內部自行實作複雜的 SSR 判斷邏輯。相比現有做法（`typeof window !== 'undefined'` 判斷、`useEffect` 延遲渲染），`use(browser())` 是宣告式的，React 在 server 端就能正確處理，不需要在 client 補一次 re-render。

```jsx
import { use, Suspense } from 'react'
import { browser } from 'react-dom'

// 這個元件在 SSR 時會顯示 Suspense 的 fallback，
// 瀏覽器端才正常渲染主體
function WeatherWidget() {
  use(browser()) // 宣告：我只在 browser 端執行

  const data = useWeatherData() // 只在 client 呼叫，不用考慮 SSR
  return <div>{data.temp}°C，{data.condition}</div>
}

// 使用時包一層 Suspense
function App() {
  return (
    <Suspense fallback={<div>天氣載入中...</div>}>
      {/* SSR 輸出 fallback，browser 才跑 WeatherWidget 本體 */}
      <WeatherWidget />
    </Suspense>
  )
}
```

```jsx
// 對比：舊的做法（容易出現 hydration mismatch）
function OldWeatherWidget() {
  const [mounted, setMounted] = useState(false)
  useEffect(() => setMounted(true), [])
  if (!mounted) return <div>天氣載入中...</div>
  return <div>{useWeatherData().temp}°C</div>
  // 問題：server 和 client 第一次渲染結果不同，React 會警告
}
```

### 6. Chrome 148 Origin Trial：Declarative Partial Updates 讓 server 直接串流 HTML 片段

`Chrome` `Web Platform` `HTML Streaming` `Origin Trial`

瀏覽器一直有個限制：頁面載入完成後，server 想更新 DOM，只能靠 JavaScript（SSE + `innerHTML`、WebSocket + 手動操作）。Chrome 148 的 Origin Trial 功能「Declarative Partial Updates」提供了兩組新 API：一組讓 server 以 out-of-order 方式直接串流 HTML 到指定節點，另一組提供新的 JS API 讓動態注入 HTML 變得更安全、更簡潔。

現在的前端框架（Astro、Remix、Next.js）都有自己的 streaming 實作，但底層還是靠 JS 做 DOM patch；Declarative Partial Updates 把這個邏輯下沉到瀏覽器原生層。對 HTMX、Alpine.js 這類「少一點 JS」的框架受益最大，也讓純 HTML + server-side rendering 的架構有機會做到接近 SPA 的局部更新體驗。

```html
<!-- 舊做法：server → SSE → JS 更新 DOM（需要 JS runtime） -->
<div id="live-score">載入中...</div>
<script>
  const es = new EventSource('/score-stream')
  // 必須用 JS 把收到的資料塞進 DOM
  es.onmessage = e => document.getElementById('live-score').innerHTML = e.data
</script>
```

```html
<!-- 新做法（Declarative Partial Updates，實驗性）：
     把節點標記為可更新目標，server 直接串流帶有目標 id 的 HTML 片段，
     瀏覽器原生處理注入，不需要 JS -->
<div id="live-score" targetable>載入中...</div>

<!-- Server 端只需要串流這樣的 HTML 片段（不需要額外 JS）：
     <update target="live-score">台北 3 : 2 高雄</update> -->
```

可透過 `chrome://flags/#enable-experimental-web-platform-features` 在 Chrome 148 試用。

### 7. VoidZero 八月更新：Vitest 5 RC 上線、Rolldown 屬性壓縮正式開放

`Vite` `Vitest` `Rolldown` `VoidZero` `工具鏈`

Oxc minifier 也有更新，改進了常見的 dead code elimination 模式。VoidZero 的整合工具 `vp` 持續迭代，讓一個指令管理 Vite + Vitest + Rolldown + Oxc 的全家桶。


```ts
export default {
```

### 8. Oxlint v1.70 原生支援 React Compiler Lint 規則，比 ESLint 快 3.2×

`React` `Oxlint` `Linting` `Rust` `React Compiler` `工具鏈`

oxlint v1.70.0（六月釋出）新增了 `react/react-compiler` nursery 規則，直接在 lint 階段執行 React Compiler 的靜態分析，報告違反 Rules of React 的地方——過去需要在 ESLint 裡安裝 `eslint-plugin-react-compiler` 並跑 Babel 管道，速度慢且設定繁瑣。切換到 oxlint 之後，同一個 lint 任務從約 29.2 秒降到 9.1 秒，降幅達 **3.2 倍**，完全來自 Rust 原生實作的優勢。

更大的收益出現在同時啟用 oxc-transform-react（本期第 1 則）的團隊：一個擁有 1,036 個 React Router 原始檔的 codebase，把 lint + compile 流程全部切換到 oxc 工具鏈後，編譯器那段快了約 **17.6 倍**。oxlint 整體已內建 695 條規則，在不需要任何外掛的情況下比 ESLint 快 50–100 倍。

```json
// .oxlintrc.json
{
  "plugins": ["react"],
  "rules": {
    // nursery 規則：啟用 React Compiler 的靜態分析
    // 會報告違反 Rules of React 的問題
    // 例如：在 render 函式裡呼叫帶有副作用的函式、mutate props 等
    "react/react-compiler": "warn"
  }
}
```

```bash
# 安裝與執行
npm install oxlint --save-dev
npx oxlint src/   # 掃描整個 src 目錄

# ── 實際量測結果（同一個 codebase）──────────────────────────
# ESLint + eslint-plugin-react-compiler：  ~29.2s
# oxlint v1.70（react/react-compiler）：    ~9.1s  ← 3.2× 加速
```
