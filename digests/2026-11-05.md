### 1. X Engineering：從零重建 x.com 的全站前端架構

`[工程知識]` `[效能]` `[架構]`

X（前 Twitter）工程團隊在 11 月 4 日發表了一篇重量級技術文章，詳細說明從零重建 x.com 前端架構的過程：在慢速連線（2G 模擬）下，首屏載入時間從 22 秒壓縮至 2.7 秒；舊版未登入首頁需要經過 3 台後端伺服器，重建後只需 1 台。今年 8 月 1 日，自研 SSR 引擎 Jetfuel 正式下線，完成了新舊架構的完整切換，整個遷移採用國家分批灰度上線的策略降低風險。

技術選型的核心思路是「減少 round-trip、回歸平台原生」：

```
// 重建前的載入路徑（概念示意）
瀏覽器請求
  → 前端 BFF
    → Jetfuel SSR 服務
      → 資料服務
（3 台不同角色的伺服器各自負責一層）

// 重建後的載入路徑
瀏覽器請求
  → 單一邊緣服務（整合 SSR + 資料 + 快取）
（1 台伺服器，大幅減少 round-trip 次數）
```

另一個值得注意的細節：X Chat 被拆分到獨立的 chat.x.com subdomain，讓主站的 JavaScript bundle 更輕。這篇文章對正在規劃「舊前端架構現代化」的團隊很有參考價值，特別是 SSR 引擎自研後的遷移痛點分析，以及如何設計灰度策略讓大規模上線的衝擊可控。

### 2. React 19 useTransition 與 useActionState 完全指南 `[補收]`

`[工程知識]` `[React]` `[補收]`

React 19 把 `useTransition` 和 `useActionState` 升級成處理非同步邏輯的一等公民，這篇指南是目前說明這兩個 hook 實際用法最清楚的文章之一。`useTransition` 讓你把耗時的狀態更新標記為「低優先度」，UI 在等待期間仍能響應使用者操作；React 19 的新版更進一步支援傳入 async function，讓 data fetching 也能直接放進 transition。`useActionState` 則是專為表單設計的 hook，把「送出狀態」、「錯誤訊息」和「回傳資料」打包在一起，不用再自己管理三個獨立的 state。

Before / After 對比——處理搜尋輸入的卡頓問題：

```tsx
// Before（React 18）：每次輸入都立即觸發 filter，畫面卡頓
const [query, setQuery] = useState('');
const results = expensiveFilter(allData, query); // 每次渲染都重跑

// After（React 19 useTransition）：輸入更新高優先度，filter 更新低優先度
const [isPending, startTransition] = useTransition();
const [results, setResults] = useState([]);

const handleChange = (e) => {
  setQuery(e.target.value); // 立即更新輸入框（高優先度）
  startTransition(async () => {
    // React 19：transition 內可以直接 await async 函式
    const data = await fetchSearchResults(e.target.value);
    setResults(data); // 資料回來後才更新結果（低優先度）
  });
};
```

```tsx
// useActionState：表單送出的三合一管理（送出狀態 + 錯誤 + 回傳資料）
const [state, submitAction, isPending] = useActionState(
  async (prevState, formData) => {
    try {
      const result = await submitForm(formData);
      return { success: true, data: result, error: null };
    } catch (err) {
      return { success: false, data: null, error: err.message };
    }
  },
  { success: false, data: null, error: null } // 初始值
);

// 在 JSX 裡直接用 action 屬性，不需要 onSubmit + preventDefault
return <form action={submitAction}>{isPending && <Spinner />}</form>;
```

選哪個 hook 的決策樹：有表單 → `useActionState`；有耗時渲染想保持 UI 流暢 → `useTransition`；有耗時計算但只影響顯示、不需要 async → `useDeferredValue`。

### 3. 用 Rust 重寫 TypeScript 編譯器：tsrs 初探

`[工程知識]` `[TypeScript]` `[工具鏈]`

Cloudflare 與 VoidZero（Oxc/Vite 背後的公司）在 10 月 20 日聯合宣布 tsrs——一個正在開發中的 Rust 版 TypeScript 編譯器。初步 benchmark 在相同 worker 數量下比 TypeScript 7.0 快約 8 倍、記憶體用量減少約 70%。另一個主要賣點是 WebAssembly 相容：Rust 可以直接編譯成 Wasm，讓 tsrs 有潛力在任何環境（瀏覽器、Cloudflare Workers、邊緣節點）執行，不必依賴 Node.js 二進位。

目前可以透過 npm 安裝實驗版試用：

```bash
# 安裝 tsrs 實驗版
npm install -D tsrs

# 對專案執行型別檢查
npx tsrs check src/**/*.ts
```

效能比較（官方初步 benchmark）：

```
                TypeScript 7.0（tsc）   tsrs（Rust 實驗版）
型別檢查速度        1×（基準）              ~8×（快 8 倍）
記憶體用量          1×（基準）              ~0.3×（少 70%）
Wasm 支援           ✗                       ✓（實驗中）
```

需要注意：tsrs 是**移植（port）**，不是 fork——目標是保持與 TypeScript 語意完全一致，而不是另立一個方言。這跟微軟自己用 Go 重寫 tsc 是兩個平行進行的計畫。tsrs 目前被納入 Oxc toolchain 下孵化，未來計畫整合到 Oxlint 裡提供型別感知的 lint 規則。

```json
{
  "mcpServers": {
    "archify": {
      "command": "npx",
      "args": ["-y", "archify-mcp"]
    }
  }
}
```

```
// 生成後的架構圖：自帶樣式的單一 HTML 檔，可直接在瀏覽器開啟
```

### 6. Vue 3.6 Vapor Mode rc.14：無 Virtual DOM 的 Vue 元件

`[前端技術棧]` `[Vue]` `[效能]`

Vue 3.6 的第 14 個 Release Candidate 在 10 月 30 日發佈，距離 Vapor Mode 正式穩定版越來越近。Vapor Mode 是 Vue 3.6 最核心的架構變更：讓你按元件（component）為單位，選擇直接操作真實 DOM 而不走 Virtual DOM——對需要高頻更新的互動元件（遊戲 UI、即時資料圖表、大型列表）效能提升最明顯。底層響應式系統換用 alien-signals，讓資料追蹤和 DOM 更新更精確，只更新真正改變的部分。

Before / After——Vapor Mode 的 opt-in 寫法：

```vue
<!-- 一般元件（維持 Virtual DOM，現有程式碼不需改動） -->
<script setup lang="ts">
const count = ref(0);
</script>
<template>
  <button @click="count++">{{ count }}</button>
</template>

<!-- Vapor 元件（跳過 Virtual DOM，直接操作真實 DOM） -->
<script setup lang="ts" vapor>
<!-- 只加一個 vapor 屬性，其他寫法完全一樣 -->
const count = ref(0);
</script>
<template>
  <button @click="count++">{{ count }}</button>
</template>
```

因為是 opt-in，現有的 Vue 3.x 專案可以讓 Vapor 元件與一般元件混用，不需要全站遷移。官方預計 Q4 2026 推出穩定版，建議現在就開始在非關鍵元件上測試相容性，提前找出可能的邊界問題。

### 7. Astro 10 月精選：7.4 帶來 build 計時旗標與並行預渲染

`[前端技術棧]` `[Astro]` `[效能]`

Astro 月末發布了 10 月生態系精選，本期最大亮點是 Astro 7.4：新增 `astro build --timings` 旗標，讓你在 CI 和本地都能看到每個建置步驟各花多少時間（之前這些數字藏在 Vite 內部，很難追蹤哪一步是效能瓶頸）。實驗性的並行預渲染（Parallel Prerendering）讓多核心機器可以同時處理多個靜態頁面，大型靜態網站的 build 時間可以明顯縮短。

```bash
# 開啟 build 計時資訊
astro build --timings

# 輸出範例——每個步驟的耗時一目了然
# ✓ Completed in 4.2s
# ├── Static files      1.1s
# ├── Route generation  0.9s
# ├── Prerendering      1.8s   ← 大型靜態站的瓶頸通常在這裡
# └── Bundling          0.4s
```

```ts
// 在 astro.config.ts 開啟並行預渲染（實驗性功能）
import { defineConfig } from 'astro/config';

export default defineConfig({
  experimental: {
    parallelPrerendering: true,  // 利用多核心並行處理靜態頁面
  },
});
```

另一個值得注意的變動：Astro 7.4 把最低 Node.js 版本提升到 22.22.0。如果你的 CI 或部署環境還在跑 Node.js 20，要提前安排升級，否則升上 7.4 後建置會直接失敗。

### 8. Core Web Vitals in 2026：INP、LCP、CLS 實戰修復指南

`[前端技術棧]` `[效能]` `[Web Vitals]`

這篇文章整理了 2026 年針對三個 Core Web Vitals（INP、LCP、CLS）效果最明顯的實戰修法，重點在區分哪些是真正有效的改善、哪些只是聽起來有道理但實測效果有限。INP（Interaction to Next Paint）是 2024 年取代 FID 後最新的「互動響應速度」指標，也是目前最多網站達不到 Good 門檻（<200ms）的指標——主因往往是把太多邏輯堆在主執行緒的一個長任務裡。

INP 的核心修法——把長任務拆開，讓瀏覽器有機會響應使用者操作：

```javascript
// 問題：一次更新大量 DOM，整個過程 block 主執行緒
function renderAll(items) {
  items.forEach(item => updateDOM(item)); // 一口氣跑完，INP 很差
}

// 修法：用 scheduler.yield() 讓每批更新之間「讓位」給瀏覽器
async function renderInChunks(items, batchSize = 50) {
  for (let i = 0; i < items.length; i += batchSize) {
    items.slice(i, i + batchSize).forEach(item => updateDOM(item));
    await scheduler.yield(); // 讓瀏覽器先處理使用者的點擊/輸入
  }
}
```

LCP 的速效修法——直接在 HTML 裡給最大圖加 `fetchpriority="high"`，比 `<link rel="preload">` 更直接：

```html
<!-- LCP 圖片：加 fetchpriority="high"，讓瀏覽器列為最高下載優先度 -->
<!-- 同時給 width/height 避免 CLS（版面移位）-->
<img
  src="/hero.webp"
  fetchpriority="high"
  alt="Hero image"
  width="800"
  height="450"
/>
```
