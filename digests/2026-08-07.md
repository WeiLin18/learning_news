2. **[React][架構][工程知識] Octane：把 React 的程式設計模型直接編譯掉 Virtual DOM**
   Inferno 作者、前 React/Svelte 核心貢獻者 Dominic Gannaway 發布 Octane，定位是 Inferno 的正式後繼者：保留 React 熟悉的 Hooks、Suspense、Actions 寫法，但在編譯期就把這些語意直接編譯成具體的 DOM 操作指令，不需要 Virtual DOM，也不需要遵守「Hooks 規則」或手動維護 dependency array——編譯器會自己分析每個 closure 實際捕捉了什麼變數，自動產生對應的 reactivity。範例概念（寫法幾乎不變，但底層完全沒有 diff）：
   ```jsx
   function Counter() {
     const [count, setCount] = useState(0);
     // Octane 編譯器直接分析這個 closure 捕捉了 count，
     // 產生對應的細粒度更新指令，不用手動 useMemo/useCallback，也沒有 VDOM diff
     return <button onClick={() => setCount(count + 1)}>{count}</button>;
   }
   ```
   同時支援 TSX/JSX 與新的 TSRX 語法，並且在發布時就準備好 TanStack、React Three Fiber、StyleX 的整合，對想了解「React 程式設計模型」能不能徹底脫離 Virtual DOM 的工程師是很扎實的架構案例。
   來源：Developers Digest（開放搜尋補充，交叉比對 Dominic Gannaway 本人於 X 的公告與 octanejs.dev 官方站）｜https://www.developersdigest.tech/blog/octane-react-compiled-framework-2026
   發布日期：2026-07-27（較早，約 11 天前，beta 發布）

3. **[React][架構][RSC][工程知識] We Stopped Using RSC on TanStack.com**
   TanStack 團隊記錄了他們把官網從 React Server Components 換回傳統 SSR 的完整心路歷程，是少見的「RSC 退燒」實戰案例。原本用 RSC 是為了不把 Markdown 轉譯與語法高亮（主要是 Shiki 相關的 runtime、主題、語言 chunk）這類重量級依賴送到瀏覽器，單一文件頁一度要傳輸約 1.1 MiB 的 script，其中 358 KiB 純粹是語法高亮相關程式碼。但當團隊把這兩個依賴收斂成兩個更小的專屬套件 `@tanstack/markdown`、`@tanstack/highlight` 後，RSC 原本要解決的問題已經不成立，反而是 RSC 本身的 runtime 邊界、序列化開銷、特殊檔案慣例開始變成負擔。改回「SSR 一次渲染、客戶端重複使用同一份小型渲染器」後，實測傳輸量約 27 KiB（比 RSC/Flight payload 版本多出約 18–19 KiB，但整體渲染管線大幅簡化），團隊認為對這個網站的實際使用情境，SSR + 小函式庫是更划算的取捨。對正在評估「RSC 到底適不適合自己專案」的框架比較讀者，這是一篇誠實揭露取捨、而非一味推崇 RSC 的少見案例。
   來源：TanStack 官方部落格（開放搜尋補充）｜https://tanstack.com/blog/we-stopped-using-rsc-on-tanstack-com
   發布日期：2026-07-27 前後（較早，約 11 天前）

4. **[React][工程技巧][工程知識] Making Referential Stability a Type**
   Shopify 資深工程師 Jovi De Croock 提出一個有趣的想法：與其讓「這個值有沒有 memo 過」變成一種團隊默契／隱性規範，不如直接把它變成型別系統的一部分。他做了一個叫 `stableref` 的函式庫，讓 `useState`、`useReducer`、`useRef`、`useTransition` 回傳的值自動帶上一個 `Stable<T>` 品牌型別；如果把一個沒有被證明穩定的值餵給需要穩定依賴的地方，TypeScript 會直接在你寫錯的那一行報錯，而不是讓問題流到下游元件才在執行期出現奇怪的重渲染。範例概念：
   ```ts
   import { useMemo } from 'stableref/react';
   // 型別系統要求：這裡的 dependency 必須是 Stable<T>
   const sorted = useMemo(() => items.sort(cmp), [items]);
   // 若 items 沒有被證明穩定 → 編譯期直接報錯，而不是執行期才發現多餘的重渲染
   ```
   這個做法刻意設計成跟 React Compiler 互補而非取代：React Compiler 負責「自動推論」穩定性，`stableref` 負責在編譯器還沒涵蓋、或跨套件邊界時，把穩定性變成一份可以強制檢查的明確契約。對深入研究 React 效能與型別安全交界的工程師，是很扎實的一篇工程技巧文章。
   來源：Jovi De Croock 個人技術部落格（開放搜尋補充）｜https://jovidecroock.com/blog/referential-stability-types/
   發布日期：2026-07-24（較早，約 2 週前）

10. **[React][狀態管理] Announcing TanStack Table V9**
    歷經兩年多斷斷續續的開發，TanStack Table V9 正式穩定版發布，內部架構整個重寫成「每個功能狀態各自是獨立的 reactive atom」（分頁、列選取、欄寬、篩選各自獨立追蹤變化，不再共用一個大 state 物件），`table.store` 只是為了相容舊版 API 而衍生出的彙總視圖。功能全面改成 opt-in：一個陽春表格只需要約 5kb，真正的企業級表格才會依需要載入排序/篩選/分頁等功能；大型表格的記憶體用量也顯著下降，因為 row/column/cell/header 的 API 現在共用同一組 prototype，不再是每個物件各自持有一份。範例概念：
    ```ts
    import { createTable } from '@tanstack/table-core';
    // V9：只載入真正用到的 feature，不用的功能連程式碼都不會被打包進去
    const table = createTable({ data, columns, features: [sorting()] });
    ```
    對維護大型資料表格的 React/Vue/Svelte/Solid/Angular 團隊，這是一次值得規劃遷移的架構升級。
