### 1. How we cut Next.js memory from ~5GB to ~1GB：找到 SSR 記憶體積壓的真正元凶

`[工程知識]` `[Next.js]` `[React Query]` `[效能]` `[SSR]`

在 Next.js App Router + React Query v3 的 SSR 環境裡，一個隱藏的計時器悄悄讓每個 HTTP 請求在記憶體裡駐留長達 2–5 分鐘。這篇 Zepto 工程師的排查筆記，完整還原了從「Pod 一直 OOM kill」到找到根因、最終讓記憶體從 ~4.8 GiB 降到 ~1.2 GiB 的全過程。

**根因：React Query v3 的 GC timer 綁定了 AsyncLocalStorage context**

React Query v3 在 Server 端為每個 query 啟動一個 `setTimeout`（即 gcTime，預設 2–5 分鐘）。Node.js 的 AsyncLocalStorage 會把當前請求的 context 自動附在這個 timer 上——於是請求結束了，但只要 timer 還沒到期，整個請求的記憶體就無法被 GC 回收：

```ts
// 問題：React Query v3 SSR 預設行為
// 每個 query 都會啟動一個 GC timer，gcTime 通常 5 分鐘
// Node 把整個 request context（AsyncLocalStorage）掛到 timer 上
// 高流量下：200 req/min × 5 min = 1000 個請求同時積壓在記憶體裡

const queryClient = new QueryClient(); // ← 沒設 gcTime，預設觸發 timer
```

**修正方式：Server 端設 gcTime 為 Infinity，讓 GC 自己管**

```ts
// 修正：SSR 的 QueryClient 把 gcTime 設為 Infinity
// gcTime = Infinity → React Query 不會啟動 timer → 請求結束後 GC 正常回收
function makeServerQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        gcTime: Infinity,     // ← 不啟動 timer，GC 自己負責回收
        staleTime: 60 * 1000, // staleTime 照常設，決定 refetch 策略
      },
    },
  });
}

// 修復效果對比：
// Before：~4.8 GiB RAM per pod，頻繁 OOM kill
// After ：~1.2 GiB RAM per pod，記憶體使用穩定（下降約 75%）
```

注意：React Query **v4/v5** 已在 Server 端預設禁用 GC timer，這個問題只影響 v3。如果你還在跑 v3 而且用了 SSR，這份筆記值得照著修。另外修完之後記得重新審視 autoscaling 設定——很多團隊為了繞過這個 bug 而調高了 Pod 配置，修完可以往下調。

### 2. Storybook 11 beta：為 AI Coding Agent 重新設計的元件開發工作站

`[工程知識]` `[AI輔助開發]` `[DX工具]`

Storybook 11 beta 在 11 月初發布，把 AI coding agent 的整合從「可以接、但要自己搞」升級成一等公民。核心是兩個方向：一是官方 skill 和 plugin（Claude Code、Codex 都有對應套件），讓 agent 無需開啟瀏覽器就能查詢元件文件；二是全新的 headless CLI，讓你在 CI 和 agent 工作流裡直接執行 story，不用跑 dev server。

**headless CLI：agent 的元件測試和 review 工具**

```bash
# 升級到 Storybook 11 beta
npx storybook@next upgrade

# 安裝 Claude Code 專用 skill
npx storybook@next add @storybook/claude-skill

# headless CLI：不起動 dev server，直接跑 story 測試
storybook tools test run --story Button.stories.tsx

# headless CLI：讓 agent 生成 UI review 報告
storybook tools review create --component src/Button.tsx
```

**before / after：agent 要幫你改一個元件，現在可以這樣做**

```
Before（Storybook 10）：
  agent 想知道 Button 的 props → 要讀 TypeScript 型別定義
  agent 想驗改完的 UI → 要啟動 dev server、等瀏覽器載入
  
After（Storybook 11）：
  agent 問 @storybook/claude-skill：「Button 的 disabled 狀態 story 長什麼樣？」
  → skill 直接回傳 story 內容和截圖，不需要啟動任何服務

  agent 改完元件後執行：storybook tools test run
  → 在 CI 裡跑完所有 story，不需要瀏覽器
```

整包 package 比 v10 縮小 25%，context 交付速度最多快 10 倍。從 Storybook 10 升級的 migration guide 和 codemod 一起出。

### 3. Svelte 5 Runes 最佳實踐 2026：用 $state、$derived、Snippets 打造生產級應用 `[補收]`

`[工程知識]` `[Svelte]` `[框架]` `[補收]`

Svelte 5 的 Runes 系統（`$state`、`$derived`、`$effect`、`$props`）穩定超過一年，這篇生產實戰指南針對「從 Svelte 4 遷移後的常見踩雷」做了系統性整理。最關鍵的轉變是：舊版的 `writable store` 現在可以用 `.svelte.ts` 模組中的 `$state` 取代——reactive 狀態不再限定在 `.svelte` 元件檔裡，可以寫進任何 TypeScript 模組並 export 出去。

```ts
// ✅ Svelte 5：在 .svelte.ts 裡定義可共用的 reactive store
// cart.svelte.ts（注意副檔名 .svelte.ts，讓 Svelte compiler 認得 Runes）
let items = $state<CartItem[]>([])
let total = $derived(items.reduce((sum, i) => sum + i.price, 0))
//          ↑ $derived 是 lazy 的，只有被讀取時才重算，天生不浪費

export function addItem(item: CartItem) {
  items.push(item)  // 直接 mutate，$state 追蹤深層變更
}
export { items, total }  // 在任何元件 import，reactivity 完整保留
```

另一個重點是 Snippets（`{#snippet}`）的正確使用時機：它不是 React slots 的直接對應，而是「帶參數的 content projection」。判斷規則很清楚——只需要客製化某段 UI 模板但不需要獨立狀態時用 snippet；需要自己的 lifecycle 和邏輯時，才拆成獨立 component：

```svelte
<!-- ✅ Snippets：讓 DataTable 的格子渲染邏輯可以從外部傳入 -->
<!-- DataTable.svelte -->
<script>
  let { rows, renderCell } = $props()
</script>
<table>
  {#each rows as row}
    <tr>{#each Object.values(row) as cell}<td>{@render renderCell(cell)}</td>{/each}</tr>
  {/each}
</table>

<!-- 使用端：只傳渲染邏輯，不需要另外建元件 -->
<DataTable rows={products}>
  {#snippet renderCell(value)}
    <strong class="highlight">{value}</strong>  <!-- 完全客製顯示方式 -->
  {/snippet}
</DataTable>
```

適合正在導入 Svelte 5 或從 Svelte 4 遷移的專案，尤其是想用 `.svelte.ts` 取代 Pinia/Zustand 管狀態的場景。

### 4. ChromeDevTools/chrome-devtools-mcp：Chrome DevTools 官方的 AI Agent 瀏覽器眼睛

`[GitHub Trending]` `[AI輔助開發]` `[DX工具]` `[Chrome DevTools]`

`chrome-devtools-mcp` 是 Chrome DevTools 團隊官方開源的 MCP server，讓 AI coding agent 可以連進你的 Chrome 瀏覽器，做網路分析、截圖、讀取 console 錯誤（帶 source map 的原始行號），以及效能追蹤。11 月在 GitHub Trending 持續出現，目前超過 56k 顆星。

安裝方式極簡，支援所有主流 AI coding tools：

```json
// claude_desktop_config.json：加入 chrome-devtools-mcp
{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",
      "args": ["-y", "@chromedp/chrome-devtools-mcp"]
    }
  }
}
// 注意：連上 MCP server 本身不會自動開啟瀏覽器；
// 只有 agent 呼叫需要瀏覽器的 tool（如截圖、網路分析）時，才會啟動 Chrome。
```

**before / after：agent 在 debug 一個 UI bug 時的能力差異**

```
Before（沒有 chrome-devtools-mcp）：
  你：「這個按鈕點了之後 API call 失敗，幫我看」
  agent：只能看 source code，猜不到 runtime 的狀態
  你：只好自己打開 DevTools 截圖給 agent

After（有 chrome-devtools-mcp）：
  你：「這個按鈕點了之後 API call 失敗，幫我看」
  agent → 自動截圖當前頁面，看到「按鈕 disabled 狀態顯示異常」
  agent → 讀取 console，看到 TypeError: Cannot read properties of null
  agent → 分析 network log，看到 API 請求帶了 null token
  agent：「是因為 useAuth() 在 render 完成前 return null，
           建議在 button onClick 前加 if (!token) return; 」
```

安全提示：這個 MCP server 連接的是你**當前的 Chrome session**（包含已登入的帳號）。建議用一個專用的 Chrome profile 跑開發，不要指向裝有個人帳號的 profile。

### 6. XState v6 beta：State Machine 的 API 全面翻新，transitions 變成純函式

`[前端技術棧]` `[狀態管理]` `[DX工具]`

Stately 在 11 月 5 日發布 XState v6 第一個 beta，這是繼 v5 重寫以來最大幅度的 API 翻新。核心改變是「transitions 現在是純函式」——狀態機的 transition 不再是 JSON 描述物件，而是你可以直接 import、直接 TypeScript 型別推導的函式，測試也更容易。

**Before（v5）vs After（v6）的遷移直覺**

```ts
// XState v5：transition 定義在 config 物件裡
const machine = createMachine({
  id: 'checkout',
  initial: 'cart',
  states: {
    cart: {
      on: {
        PROCEED: { target: 'payment' }
      }
    },
    payment: { /* ... */ }
  }
});

// XState v6：用純函式定義 transition（型別推導更精確，IDE 支援更好）
// 注意：這是 beta，API 可能在 stable 前調整
import { createMachine, transition } from 'xstate';

const checkoutMachine = createMachine({
  id: 'checkout',
  initial: 'cart',
  states: {
    cart: {
      on: {
        // v6 裡 transition 可以是函式，讓條件邏輯更自然
        PROCEED: transition('payment', (ctx) => ctx.items.length > 0)
      }
    }
  }
});
```

**遷移工具和生態支援**

```bash
# 安裝 v6 beta 試用
npm install xstate@beta

# 自動 migrate v5 → v6（大多數改動可自動處理）
npx xstate migrate

# 安裝對應的 framework binding（一起安裝 beta 版）
npm install @xstate/react@beta @xstate/vue@beta @xstate/svelte@beta
```

v5 仍維持 LTS 支援，不用急著遷移。但如果你有在用 XState，現在開始試 beta 是好時機——可以提前找出你的 machine 定義有哪些需要調整，不要等 stable 才一次跑 migration。

### 7. React 19 vs Svelte 5：INP 優化的框架心智模型差異 `[補收]`

`[前端技術棧]` `[React]` `[Svelte]` `[效能]` `[框架比較]` `[補收]`

這篇文章把 React 19 Concurrent 渲染與 Svelte 5 Runes fine-grained reactivity 放在同一個 INP（Interaction to Next Paint）指標框架下對比，給出「哪個架構決策最划算」的實測結論。核心發現不是誰贏誰輸，而是兩種不同的設計取捨——理解差異才能做出適合專案的選擇。

**「即時篩選清單」這個場景，把兩個框架的心智模型差異說得最清楚：**

```jsx
// React 19：需要額外的 useDeferredValue 才能保持輸入框不卡頓
function ProductSearch({ products }) {
  const [query, setQuery] = useState('')
  const deferredQuery = useDeferredValue(query) // 輸入值快，篩選值慢，分開處理

  const filtered = useMemo(
    () => products.filter(p => p.name.includes(deferredQuery)),
    [deferredQuery] // ← 用 deferred 值計算，不阻塞輸入框的更新
  )

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ProductList items={filtered} />  {/* 顯示的是稍舊的結果，但輸入不卡 */}
    </>
  )
}
```

```svelte
<!-- Svelte 5：同樣的場景，天然不卡頓，不需要額外 hook -->
<script>
  let { products } = $props()
  let query = $state('')

  // $derived 是 lazy 的：只有 ProductList 被渲染時才計算
  // 輸入框的 $state 更新和篩選的 $derived 重算，
  // 在 Svelte 5 的更新批次裡天然就是分開的
  let filtered = $derived(
    products.filter(p => p.name.includes(query))
  )
</script>

<input bind:value={query} />
<ProductList items={filtered} />
<!-- 不需要 useDeferredValue，不需要 useMemo → 輸入同樣不卡 -->
```

**決策建議**：如果你已有大型 React 元件樹，`useTransition` 對「讓複雜更新降優先度」收益最大。如果是從頭開始且效能是首要考量，Svelte 5 的 `$derived` 讓計算性 state 天生 lazy，不需要手動 memoize。

### 8. CSS text-overflow：Chrome 157 終於支援客製字串，「…」不是唯一的選擇

`[Web Platform]` `[CSS]` `[瀏覽器新 API]`

Chrome 157（11 月 3 日 stable）讓 `text-overflow` 可以接受任意字串——你可以把截斷符號從「…」換成「(更多)」、「↓」、「[繼續閱讀]」或任何你想要的文字，讓溢出指示更貼近產品設計語言。

**基本語法和必要條件**

```css
/* text-overflow: <string> 只在以下三個條件同時成立時才有效：
   1. overflow: hidden（觸發溢出裁切）
   2. white-space: nowrap（限制單行）
   3. 文字確實超出容器寬度 */
.card-title {
  overflow: hidden;
  white-space: nowrap;
  text-overflow: "(more)";   /* ← Chrome 157+ 支援任意字串 */
}

/* Before（所有瀏覽器）：只能用省略號 */
.card-title { text-overflow: ellipsis; }

/* After（漸進增強寫法）：舊瀏覽器看到省略號，Chrome 157+ 看到客製字串 */
.card-title {
  overflow: hidden;
  white-space: nowrap;
  text-overflow: ellipsis;         /* 舊瀏覽器的 fallback */
  text-overflow: " (繼續閱讀→)";   /* Chrome 157+ 覆蓋上面 */
}
```

**before / after 範例——商品卡片的標題截斷**

```css
/* Before：所有截斷都長一樣，使用者不清楚「點了有沒有更多內容」 */
.product-title { text-overflow: ellipsis; }
/* 顯示效果：「限量版機械式電競鍵盤 Cherry MX...」 */

/* After：截斷符號本身就是 CTA，明確提示有更多內容 */
.product-title { text-overflow: " → 查看完整名稱"; }
/* 顯示效果：「限量版機械式電競鍵盤 Cherry MX → 查看完整名稱」 */
```

**目前的瀏覽器支援情況**
- Chrome 157：已 stable ✓
- Safari：在某些版本已支援，請自行測試
- Firefox：表格上有標記，但實際測試結果不一致，建議先驗證

注意：這個特性目前只對「單行溢出」有效，對 `line-clamp` 造成的多行截斷不適用。
