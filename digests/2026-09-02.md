### 1. Remix 3 ditched React: Should you stick with it?

`[工程知識]` `[框架比較]` `[Remix]` `[React]`

Remix 3 是一次徹底的重寫——捨棄 React，改用 Preact 分支，搭配更貼近瀏覽器原生的命令式（imperative）程式模型。LogRocket 這篇文章不是在介紹 Remix 3 有什麼功能，而是幫開發者釐清一個棘手的選擇：已有 Remix 2 的專案，要跟進 Remix 3 還是轉往 React Router 7？

兩個框架的思維模型差距相當大：

```js
// Remix 2 / React Router 7 的模型：React 狀態，宣告式更新
const [count, setCount] = useState(0);
return <button onClick={() => setCount(c => c + 1)}>{count}</button>;

// Remix 3 的模型：直接操作 DOM，命令式、接近原生
button.addEventListener('click', () => {
  output.textContent = ++count;
});
```

Remix 3 沒有提供任何自動遷移路徑——它是全新起點，而非升級。文章的結論偏向保守：現有大型 React 專案繼續走 React Router 7 的演進路徑風險最低；Remix 3 更適合不依賴 React 生態的全新小型專案。Preact 打包後約 3KB，React 約 45KB——如果要「幾乎沒有框架負擔的 Web 原生體驗」，Remix 3 值得用新專案試。

### 2. How to Survive an AI Mandate

`[工程知識]` `[AI輔助開發]` `[實務指南]`

公司要求開發團隊「必須使用 AI 工具」的情境越來越普遍。Builder.io 的 Alice Moore 寫的這篇文章不是在吹捧也不是在抱怨，而是提供一份務實指南：如何在 AI 強制推行的環境下維持程式碼品質，並避免只追「AI 使用率」數字而犧牲實際效率。

文章建議用分階段、有量化基準的方式導入，而不是全面開放：

```
第 1 週：只用 AI 寫測試
  量化指標：新功能首次提交的測試覆蓋率

第 2 週：用 AI 做 code review 的初稿
  量化指標：AI 建議中「需要人工再改」的比率

第 3 週：用 AI 寫文件與 JSDoc
  量化指標：函式文件的完成率
```

核心原則是「AI 不擁有你的程式碼——你才是」：不要因為 AI 生成就降低 review 深度，反而應該把 review 視為整個流程中最值得花人力的環節。對任何正被 AI 政策夾擊的前端工程師都很實用，尤其是沒有充分討論期就被要求轉型的情境。

### 3. Human judgment doesn't leave the software factory. It relocates.

`[Blog]` `[AI輔助開發]` `[工程文化]`

Addy Osmani 這篇文章的核心論點清楚：AI 時代不是「人類退出軟體工廠」，而是「人類判斷力的位置移動了」。它從程式碼的「執行層」移往兩端——往上游移到「決定要做什麼、設計系統邊界、制定品質標準」；往下游移到「評估 AI 產出的風險、承擔擁有權、用證據做決策」。

一個 before/after 讓這個概念更具體：

```
[Before AI] 工程師的時間分配（概念示意）
  60% 寫程式碼
  30% review 與測試
  10% 系統設計與決策

[After AI] 人類判斷力的新位置
  ↑ 上游：意圖定義 + 系統設計  ← 判斷力移往這裡
  ─ 中間：程式碼生成 + 實作     ← AI 接管
  ↓ 下游：風險評估 + 擁有權     ← 判斷力移往這裡
```

Osmani 補充：雖然人類親手打出的程式碼比例可能大幅下降，但「對結果的擁有權」不必跟著下降。「你沒有寫這段程式碼」不是「這不是你的責任」的理由。進行 AI 工具策略討論前先讀一遍，能幫助釐清人類在 AI 輔助流程中真正扮演的角色。

## GitHub Trending

### 4. open-slide — 給 AI Agent 用的簡報框架

`[GitHub Trending]` `[AI輔助開發]` `[開發工具]`

open-slide 從設計上就以 AI agent 為主要使用者——讓 Claude Code、Codex、Cursor 這類 AI agent 透過語言直接建立和編輯簡報，而不是讓人類手動拖放元件。目前在 GitHub Trending 上有約 7,300 顆星，上週增長顯著。

框架內建兩個 AI skill，可以直接叫 agent 執行：

```bash
# 請 AI agent 從零建立一份簡報（支援中文需求描述）
claude /create-slide "向技術團隊介紹 TanStack Start 的優點，包含 code 範例"

# 進入 AI 輔助的投影片撰寫模式（可持續迭代）
claude /slide-authoring
```

瀏覽器端有 comment inspector，讓 reviewer 直接在預覽介面標注意見（例如「第三張的標題太籠統」），然後用 `/apply-comments` 請 agent 讀取並自動應用修改。整個「寫 → 評論 → 修改」的循環都由 agent 接手，人類專注在方向與內容決策上。適合需要大量產出技術簡報的團隊，或想試驗 AI-first 工作流程的開發者。

## 前端技術棧 + Web 平台

### 5. Manifest V2 正式永久移除——Chrome 擴充套件生態洗牌

`[Web平台]` `[瀏覽器]` `[Chrome]`

2026 年 8 月 31 日，Google 永久移除 Chrome Web Store 上所有 Manifest V2（MV2）擴充套件。這件事早有預告，但執行日的到來代表沒有遷移到 MV3 的套件就此消失——包含 uBlock Origin 在內的部分知名套件都受到衝擊。

MV2 和 MV3 最大的技術差異在於網路請求的攔截方式：

```js
// MV2：可動態攔截並任意處理請求（廣告攔截的核心機制）
chrome.webRequest.onBeforeRequest.addListener(
  details => ({ cancel: true }),  // 可在執行時決定要不要封鎖
  { urls: ['<all_urls>'] },
  ['blocking']
);

// MV3：改用宣告式規則，只能預先定義，不能動態執行任意邏輯
chrome.declarativeNetRequest.updateDynamicRules({
  addRules: [{
    id: 1,
    action: { type: 'block' },
    condition: { urlFilter: 'ads.example.com' }
  }]
});
```

`declarativeNetRequest` 對廣告攔截套件的限制相當大——它不允許在執行時動態判斷是否封鎖某請求，只能套用預先定義的規則。Firefox 公開表示不跟進，將無限期維持 MV2 支援。對前端開發者的實際影響：你用的 DevTools 型擴充套件也可能已消失，值得確認是否有 MV3 版本或替代方案。

### 6. Nuxt 4.5：Vite 8、實驗性 SSR 串流、Rsbuild 三連發

`[前端技術棧]` `[Vue]` `[Nuxt]` `[效能]`

Nuxt 4.5 是這一輪版本中改動最密集的一次，三個大升級同時落地：底層換成 Vite 8（內建 Rolldown，冷啟動更快）、全新的 Rspack 2 + Rsbuild 建置管線（與 Vite builder 並存、可自選）、以及實驗性的 SSR 串流模式。

SSR 串流的效果最直觀——它改變了 HTML 傳送的時機：

```
[傳統 Nuxt SSR]
  完整渲染所有元件 → 一次傳送整頁 HTML → 瀏覽器才開始顯示
  └─ TTFB（首位元組時間）較長

[Nuxt 4.5 SSR 串流（實驗性）]
  立刻傳送 HTML shell → Vue 繼續渲染各 section → 邊渲染邊串流傳送
  └─ TTFB 立即，使用者更早看到骨架畫面，搭配 Suspense 效果更好
```

除了效能，這次也加入了穩定的錯誤代碼系統（例如 `NUXT_E1001`）——報錯時直接附上可 grep 的代碼加簡短修復建議，比過去純文字錯誤訊息好除錯。另外還有新的 `useLayout` composable（在腳本裡讀取當前路由的 layout 名稱）和命名視圖的檔案命名慣例（`child@sidebar.vue`）。Vue/Nuxt 用戶可以先在非關鍵功能上試用 SSR 串流，觀察 TTFB 的改善幅度。

### 7. What's new in Astro — August 2026

`[前端技術棧]` `[Astro]` `[效能]`

Astro 八月彙整的亮點集中在兩個方向：治理與效能。Project Steward 計畫讓社群成員可以正式承擔框架特定功能的長期維護責任，比「maintainer」這個頭銜更具體、有明確的負責範圍。Astro Playground 則讓你直接在瀏覽器裡跑 Astro，不用本機設定就能試新功能或分享可重現的 bug。

效能面最值得關注的是 Sätteri，一個用 Rust 重寫的 Markdown 與 MDX 處理器：

```
[既有 JavaScript Markdown 處理器]
  10,000 頁靜態內容站：建置時間 ~120 秒

[Sätteri（Rust-based 處理器）]
  相同的 10,000 頁靜態內容站：建置時間 ~48 秒（快約 60%）
```

Sätteri 對以大量 Markdown 文章為主的文件站或技術部落格效果最顯著，其他類型的 Astro 專案改善幅度會比較小。這個月也正式落地了 ImageKit 整合，可以直接在 Astro 裡接 ImageKit 的全球 CDN 做圖片轉換與最佳化，不需要自行設定 proxy。升級影響低、收益明顯，內容密集型的 Astro 站推薦試試。

### 8. What's new in Svelte: September 2026

`[前端技術棧]` `[Svelte]` `[SvelteKit]`

Svelte 九月月報帶來幾個讓日常開發更順手的改進。最實用的是 Svelte 5.57 的 `SvelteMap` 新方法——`getOrInsert()` 和 `getOrInsertComputed()`，解決「先讀看看有沒有、沒有再設預設值再繼續用」這個超高頻操作：

```js
// 舊寫法：三行，容易漏掉邊界處理
const arr = map.get('key') ?? [];
if (!map.has('key')) map.set('key', arr);
arr.push(item);

// Svelte 5.57 SvelteMap.getOrInsert()：一行解決
map.getOrInsert('key', () => []).push(item);
```

`createContext` 現在回傳第三個 `has` 函式，讓你在不觸發「context 不存在」錯誤的情況下先確認 context 是否已設定：

```svelte
const [setCtx, getCtx, hasCtx] = createContext();

// 安全地條件式取用 context（不需要 try/catch）
if (hasCtx()) {
  const value = getCtx();
}
```

SvelteKit 3 RC 方面，跨頁面的 form action 現在在成功/失敗時都會導向 action 頁面（與瀏覽器原生 form 行為一致），`sv` CLI 也把 `mcp` add-on 換成 `ai-tools`，並附上任務式的 SvelteKit 3 遷移指引，讓現有專案升級的路徑更清楚。
