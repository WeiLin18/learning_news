### 1. How Baseline Can Help You Ship Less JavaScript

`[補收]` `[工程知識]` `[Web平台]` `[效能]`

這篇處理一個每個前端專案都會遇到、但很少有人系統性檢查的問題：**當年因為瀏覽器不支援才裝的套件，現在瀏覽器早就原生支援了，但它們還躺在你的 `package.json` 裡**。作者用「Baseline」這個跨瀏覽器支援度標準當判斷依據——Widely available（四大引擎都支援滿 30 個月，可以放心用）、Newly available（剛全部支援，舊裝置可能沒有）、Limited availability（還沒到齊）。

最好懂的是「套件 → 原生 API」的一對一替換清單，很多都是一行對一行：

```js
// 之前：為了深拷貝裝 lodash.clonedeep（約 4KB）
import cloneDeep from 'lodash.clonedeep';
const copy = cloneDeep(state);

// 現在：瀏覽器原生就有，且能正確處理 Date / Map / Set / 循環引用
const copy = structuredClone(state);

// 之前：為了「N 分鐘前」裝 timeago.js
// 現在：Intl.RelativeTimeFormat 原生支援，還自動處理多語系
new Intl.RelativeTimeFormat('zh-TW', { numeric: 'auto' }).format(-3, 'day'); // 「3 天前」
```

作者也給了可以照做的稽核流程：`npm ls --omit=dev --depth=0` 列出正式相依 → 用 Bundlephobia 量成本 → 到 webstatus.dev 查 Baseline 狀態 → 用「你的受眾支援嗎／換掉的實際代價是什麼／原生功能真的涵蓋你的使用情境嗎」三個問題把關。文中估計一個中型應用通常可以瘦身 60–90 KB（gzip 後）。重點是它沒有無腦叫你全部換掉——像 `axios` → `fetch` 就明確標出缺口（fetch 不會在 4xx/5xx 自動 reject、沒有 interceptor）。

### 2. Tree Shaking（patterns.dev）

`[補收]` `[工程知識]` `[Build工具]`

這是一份常青的原理教材，解釋打包器（webpack、Rollup）到底怎麼判斷「哪些程式碼是死的、可以砍掉」。核心觀念是：打包器把整個應用當成一張圖，從進入點開始往外走，走得到的才留下——所以**能不能砍，取決於它在打包時就「靜態看得出來」誰用了誰**。

第一個範例說明為什麼一定要用 ES Module 的 `import` / `export`：

```js
// utilities.js
export function read(props) { return props.book }
export function nap(props)  { return props.winks }   // 沒有人 import 它

// index.js
import { read } from 'utilities';   // 靜態 import：打包器在編譯期就知道只用到 read
// → 最終 bundle 裡不會包含 nap()
```

第二個範例是實務上最常踩的坑——**副作用（side effect）會讓 tree shaking 直接失效**。只要模組在「被 import 的當下」就會動到全域狀態（polyfill、全域樣式、注册 prototype 方法），打包器不敢砍，因為砍掉會改變程式行為：

```js
// polyfill.js —— 光是被 import 就改了全域，即使你沒用到任何 export
Array.prototype.myHelper = function () { /* ... */ };

// 所以要在 package.json 主動告訴打包器「我這個套件哪些檔案是純的」
{ "sideEffects": ["*.css", "./src/polyfill.js"] }   // 只有列出來的有副作用，其餘可放心搖掉
```

這則之所以值得補收，是因為它是那種「隔幾個月再看仍然有用」的地基知識——理解了副作用這條規則，才知道為什麼有些函式庫號稱 tree-shakeable 卻怎麼砍都砍不掉。

### 3. Migrating a Large Flow Monorepo to TypeScript

`[工程知識]` `[TypeScript]` `[案例研究]`

Yelp 工程團隊完整記錄了一場**歷時 3 年 7 個月、140 萬行程式碼、570 個套件**的 Flow → TypeScript 遷移。最值得學的不是結果，而是他們刻意選的策略：不做「凍結開發、一次全換」的大爆炸式遷移，而是**一次換一個套件、讓 Flow 與 TypeScript 在正式環境並存**，全程維持型別檢查有效。

關鍵技巧是「從相依樹的最底層往上換」，再用 `flowgen` 把已轉好的 TypeScript 型別倒回去產生 Flow 能讀的宣告，讓還沒轉的上層套件照樣有型別可用：

```
相依樹（底層 → 上層）
  utils  ←  api-client  ←  web-app
   ①先轉        ②再轉         ③最後轉

轉好 utils 之後：
  utils/index.d.ts  --(flowgen)-->  utils/index.js.flow
  → 還在用 Flow 的 api-client 依然讀得到 utils 的型別，不會出現型別斷層
```

數字也很有說服力：發布後 6 個月就轉完 270 個套件；型別覆蓋率從 Flow 時代的 83.15% 提升到 96.44%；最終留下約 6,000 個 `@ts-expect-error`（而不是整包關掉型別檢查）；82% 的工程師回報生產力提升。作者強調成功的關鍵是「全程維持對型別檢查的信任」——不用暫時關掉檢查或大量塞忽略註解來換取進度，適合任何正在評估大型漸進式遷移的團隊照著抄流程。

📖 [Yelp Engineering Blog](https://engineeringblog.yelp.com/2026/08/migrating-a-large-flow-monorepo-to-typescript.html) ｜ 2026-08-04（較早，約 11 天前）｜ 優先來源（JavaScript Weekly #798 頭條）

### 4. Progressive Enhancement inside of JavaScript

`[Blog]` `[效能]` `[工程知識]`

Remy Sharp（JS Bin 作者）把「漸進增強」這個通常用在 HTML/CSS 層的觀念，往內搬進 JavaScript 自己：**先接住使用者的操作意圖，再慢慢等重的相依載入**。他的 Markdown 工具原本要下載約 600KB（壓縮後）的程式碼才能運作，在慢速網路上就是一段完全按不動的空白時間。

做法用生活化的比喻就是「餐廳還沒開火，服務生就先來點餐」——先把單記下來，廚房好了再一次出餐：

```html
<!-- 關鍵：這段極小的 inline script 緊接在 HTML 之後，不等任何 bundle -->
<script>
  window.__queue = [];
  // 使用者一拖檔案進來就先接住，即使 markdown-it / highlight.js 都還沒下載完
  dropZone.addEventListener('drop', e => {
    e.preventDefault();
    window.__queue.push(e.dataTransfer.files);   // 先排隊，不丟掉
    showLoading();                                // 給明確的「處理中」回饋
  });
</script>
```

```js
// 主 bundle 載入完成後，把排隊中的操作補跑一次
import { render } from './heavy-renderer.js';
window.__queue.forEach(render);
window.__queue = [];
```

結果是連 GPRS 這種極慢的連線都能「一進頁面就可以丟檔案」，渲染在相依載入完成後自動補上。這個模式對任何「首屏就有明確主要操作」的工具型網站都適用——與其顯示一個按了沒反應的按鈕，不如先把意圖排隊起來。

📖 [remysharp.com](https://remysharp.com/2026/08/05/progressive-enhancement-inside-of-javascript) ｜ 2026-08-05（較早，約 10 天前）｜ 優先來源（JavaScript Weekly #798）

### 5. vercel-labs/deepsec

`[GitHub Trending]` `[AI輔助開發]` `[資安]`

Vercel Labs 開源的「agent 驅動的漏洞掃描器」，目前約 7.6k star、TypeScript 撰寫、Apache 2.0 授權。它和一般 SAST 工具的差別在於**兩段式流程**：先用便宜的 regex 樣式比對把可疑位置全部撈出來，再讓 AI 模型以最高思考等級逐一複審——用低成本的方式縮小範圍，把貴的推論留給真正需要判斷的地方。

三個指令就能跑完一輪：

```bash
npx deepsec init                                  # 初始化設定（選模型供應商、成本上限）
pnpm deepsec scan                                 # 第一階段：樣式比對，快速撈出可疑點
pnpm deepsec process                              # 第二階段：AI 逐一複審，過濾誤報
pnpm deepsec export --format md-dir --out ./findings   # 匯出成 Markdown 報告
```

實務上比較有價值的是它的工程設計，而不只是「用 AI 掃描」這個賣點：掃描可中斷續跑（大型 repo 掃到一半停掉不用重來）、可設定成本上限與時間上限、支援用 Vercel Sandbox microVM 分散到多台機器、也能用 `process --diff` 只掃 PR 改動的檔案接進 CI。整個流程跑在自己的基礎設施上，程式碼不用交給第三方 SaaS。

```bash
pnpm deepsec process --diff    # PR 模式：只複審這次改動的檔案，適合接進 CI
```

### 6. Form v2 is here: All you need to know about the alpha

`[TanStack]` `[React]` `[框架]` `[TypeScript]`

TanStack Form v2 alpha 最大的改動是**驗證器從「以事件為 key」改成「以管線為單位」**。v1 的寫法是每個事件各掛一個 schema，同一份規則要在 `onChange` 和 `onBlur` 各寫一次，錯誤處理也各跑一次；v2 改成一個陣列，每個驗證器自己宣告要在哪些時機觸發：

```ts
// v1：同一份 schema 重複掛兩次，錯誤訊息也會重複處理
validators: {
  onChange: mySchema,
  onBlur: mySchema,
}

// v2：一個驗證器宣告多個觸發時機，不再重複
validators: [
  { run: mySchema, triggers: ['change', 'blur'] },
]
```

管線模型還帶來兩個 v1 做不到的能力：`when` 可以讓某個驗證器只在特定條件下跑（例如「只有在使用者勾了『寄送實體帳單』時才驗證地址」），`bailIfInvalid` 可以在前一個驗證器失敗時直接中斷後面的驗證（例如「格式都不對了就不用再打 API 檢查 email 是否已註冊」）：

```ts
validators: [
  { run: emailFormatSchema, triggers: ['change'], bailIfInvalid: true },  // 格式錯就停，不往下跑
  { run: emailUniqueCheck,  triggers: ['blur'] },                          // 只有格式對了才打 API
]
```

另外新增 `strictSchema` / `looseSchema` 兩種型別推導模式（讓 schema 而不是 `defaultValues` 當唯一事實來源），SSR 時伺服器驗證可直接共用 `formOpts`、不用再手動合併狀態。目前是 alpha，尚未支援表單持久化、Vue/Solid/Angular/Lit 的表單組合、以及 submit meta——要嘗鮮可以，正式專案建議再等等。

### 7. Introducing Kitesurf: The agent-first browser that runs in V8 isolates on Cloudflare Workers

`[Web平台][瀏覽器]` `[AI輔助開發]`

Cloudflare 做了一個**專門給 AI agent 用、而不是給人用的瀏覽器引擎**，直接跑在 Workers 的 V8 isolate 裡。設計出發點很直白：agent 不在乎分頁、佈景主題、擴充套件或跨裝置同步，它在乎的是 token 數、context window、規模與成本——所以 Kitesurf 刻意放棄像素級精準渲染與流暢動畫，換取極低的資源消耗。

對照 Chromium 跑同樣 14 個網址的數字（這是這則最好懂的部分）：

```
              CPU（截圖）  CPU（抽 HTML）   記憶體（截圖）        記憶體（抽 HTML）      速度
Chromium          1×            1×        271.0 MiB            273.7 MiB          1×
Kitesurf      省 3.1×       省 3.8×        57.8 MiB（省 4.7×）   39.4 MiB（省 7.0×）  慢 1.7–1.8×
```

換句話說：**用約 1.7 倍的時間，換 3–7 倍的資源節省**——對「一次要跑幾千個網頁」的 agent 工作負載，這個交換非常划算；對單次要快的互動情境則不划算。用法上只要在既有的 Browser Run API 加一個參數：

```bash
# 同一支 API，加上 browser=kitesurf 就切換引擎
curl -X POST 'https://api.cloudflare.com/client/v4/accounts/<accountId>/browser-run/screenshot?browser=kitesurf'
```

目前通過約 215,000 項 Web Platform Tests（CSS、DOM、HTML、SVG、XHR 覆蓋度高），TodoMVC、Wikipedia、Hacker News、Cloudflare dashboard 都跑得動；但不支援影片播放、WebGL、持久化登入 session 與 TLS 指紋協商，複雜互動應用仍要用 Chromium 版。

### 8. How we built a software factory to drive Astro's GitHub issue count to zero

`[Astro]` `[AI輔助開發]` `[實務指南]`

Astro 核心成員 Matthew Phillips 記錄他們怎麼用 AI agent 把**開啟中的 issue 從 200 多降到約 30**（下降約 85%），並預期一個月內歸零——這會是這個 repo 五年多歷史上第一次 issue 清空。重點不是「叫 AI 修 bug」，而是把 triage 拆成一台**以 issue 標籤驅動的狀態機**，每個階段交給互相隔離的子 agent 處理：

```
issue 進來
  → 標籤 needs-repro   → 子 agent A：clone 使用者提供的重現 repo，確認問題真的存在
  → 標籤 diagnosing    → 子 agent B：加 log／插樁，找出根本原因
  → 標籤 verifying     → 子 agent C：讀測試與文件，判斷這到底是 bug 還是預期行為
  → 標籤 fixing        → 子 agent D：把重現步驟寫成會失敗的單元測試，再實作修正
  → 產出 report.md ＋ 用 pkg.pr.new 發預覽版本，回貼到 issue
  → 回報者確認可用 → 自動開 PR
```

「拆成隔離子 agent」這件事是整篇最可遷移的設計：每個 agent 只看自己那一步需要的上下文，不會把整條對話塞爆 context window，也不會讓「重現階段」的錯誤猜測污染「修正階段」的判斷。實際串接方式就是一個 GitHub Action：

```yaml
- uses: withastro/triagebot-action@v1
  with:
    triage-model: cloudflare-workers-ai/@cf/moonshotai/kimi-k2.7-code   # 便宜的模型做初步分類
    verification-model: cloudflare-workers-ai/@cf/moonshotai/kimi-k2.6  # 另一個模型獨立驗證
    triage-skill: .agents/skills/triage                                  # 規則寫成可版控的 skill
```

底層框架叫 Flue（開放、平台中立的 durable agent／workflow 框架）。對維護 OSS 專案、或內部有大量待處理 issue 的團隊，這是一份帶著具體規模數據與可複製架構的實戰紀錄。

📖 [The Cloudflare Blog](https://blog.cloudflare.com/astro-issue-triage/) ｜ 2026-08-04（較早，約 11 天前）｜ 優先來源（JavaScript Weekly #798）
