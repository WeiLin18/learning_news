# 日報導讀（deep-dive）

日報（`digests/YYYY-MM-DD.md`）的每一則只有 3–5 句，任務是「幫使用者決定值不值得看」。
這個 skill 處理的是下一步：**使用者已經決定某幾則值得看了，要把它真的看懂。**

所以導讀的價值不在「講更多」，而在**轉譯**——把原文的專業敘述換成使用者已經懂的東西
（類比、最小例子、對照表、可照做的步驟），並誠實講出原文沒明說的取捨與限制。
如果產出讀起來只是「日報那 5 句話的擴寫」或「原文的翻譯」，就沒有達成目的。

`deep-dives/2026-08-02-followups.md` 是這個 skill 的標竿範例，動手前先讀它，感受一下密度與語氣。

---

## Step 0：載入情境

1. 讀 `preferences.md`。使用者過去的回饋會直接影響導讀的展開方式（例如已經記錄「偏好生活化
   類比＋最小程式碼片段」「偏好可直接落地執行的步驟清單」），照著調整。
2. 讀 `deep-dives/2026-08-02-followups.md` 當寫作標竿。
3. 讀 `AGENTS.md` Step 7–8（輸出格式與開 PR 的既有慣例），導讀要跟它們風格一致。

讀不到 `preferences.md` 就停下來回報，不要用預設值默默繼續——那會產出一份沒對齊偏好的筆記。

## Step 1：確認追問對象

使用者可能用這幾種方式指定，都要能接：

| 說法 | 怎麼解讀 |
|---|---|
| 「第 4 則多說明一點」 | 沒指定日期時，預設是**最近一次呈現給使用者的那份日報**；不確定就先確認，不要猜錯天。 |
| 「TanStack Start 那則」 | 用關鍵字在近期 `digests/*.md` 搜尋比對。 |
| 「幫我統整第 3、7、11 則」 | 多則合看，走 Step 3 的**型態 D**，不是寫三段各自獨立的導讀。 |
| 貼一個網址 | 不一定在日報裡。先搜尋 `digests/` 確認有沒有收錄過；沒有也照做，追問對象記為「使用者直接提供」。 |

**日報可能還沒 merge**：若在 `main` 上找不到那天的 `digests/YYYY-MM-DD.md`，去看有沒有還開著的
`digest-YYYY-MM-DD` 分支或 PR，從那裡讀。找不到就直接問使用者是哪一則，不要挑一則相近的硬上。

確認後，先用一句話跟使用者複述你要展開哪幾則、以及打算往哪個方向展開（例如「第 4 則，重點放在
跟 Next.js 的架構取捨差異」），這能在花時間研究之前就攔下理解錯誤。

## Step 2：取材

**先重新打開原始連結讀全文**，日報摘要只當索引用，不要當事實來源——摘要是壓縮過的，直接拿它
擴寫等於把壓縮失真放大成一整段。

讀完原文後，補足這些原文常常沒寫、但讀者一定會想知道的：

- 官方文件 / release notes（確認版本、確認 API 真的長那樣）
- repo 的 README、issue、討論串（看真實使用者踩到什麼）
- 同主題的其他觀點（原文若是作者自己的產品，特別要找外部評價）

**出網被擋或連不上時**：這個環境曾經發生過大量網域被 egress policy 擋掉。這時候不要假裝讀過，
在該則導讀開頭誠實標一行「未能開啟原文，以下內容依日報摘要與多組交叉搜尋推得，細節請以原文為準」，
並降低具體 API 簽章、版本號這類容易記錯的斷言強度。誠實標註的價值遠高於看起來很完整。

## Step 3：選一種展開型態

不同文章適合的展開方式不一樣，硬套同一個模板會產出很鈍的東西。先判斷這則屬於哪一型：

### 型態 A｜概念型（一個新工具／新 API／新概念是什麼）

1. **一句話定位**：它解決誰的什麼痛點。
2. **生活化類比**：用日常經驗解釋機制。例如「`WorkflowAgent` 像網購退款要等審核，審核期間你可以
   關掉 App，審核過了它自己繼續」。類比要對到**機制**，不是只對到氣氛。
3. **最小可讀範例**：5–15 行，把不相干的細節全部砍掉，用中文註解標出「這行為什麼重要」。
   程式碼要能讓人一眼看出差別，不是能複製貼上就跑（跑得起來更好，但可讀性優先）。
4. **限制與現況**：還沒支援什麼、只支援哪個框架、什麼時候不該用。這段最常被原文省略，
   卻最常是使用者真正要的決策資訊。

### 型態 B｜比較型（A vs B vs C 有什麼差別）

1. 各自的**設計哲學**一句話——差異的根源通常在這裡，不在功能列表。
2. **對照表**：欄位挑真正會分岔的維度（型別安全程度、資料載入模型、RSC 支援度……），
   不要湊滿一堆大家都一樣的欄位充數。
3. **點出真正的分岔點**：「三者裡最本質的差異是 X」。沒有這句，表格只是資訊，不是理解。
4. **該怎麼選**：依情境給建議（生態系優先→選 A；在意編譯期型別安全且願意當早期採用者→選 C）。
   使用者問比較，最後想要的通常是這個。

### 型態 C｜實務型（工作流程／方法論／best practice）

1. **完整流程拆解**（原文的骨架）。
2. **具體照做步驟**：把原則變成「第 0 步、第 1 步……」，帶上真實情境當例子
   （例如「以註冊表單 email 驗證為例」），包含實際會打的指令、會貼給 AI 的話、會改的設定檔。
3. **依風險分級**：什麼情況值得花力氣做全套，什麼情況做一半就夠。全都做的建議沒人會照做。
4. **最精簡版總結**：一兩句話講出「其他都是延伸，核心只有這件事」。使用者記得住的就這句。

### 型態 D｜統整型（多則合看，或跨日報的趨勢）

使用者說「統整」「這幾則有什麼關聯」時走這型。不要寫成 N 段各自獨立的導讀再拼起來——那沒有統整。

1. **共同趨勢一句話**：這幾則背後在回應同一個什麼變化。
2. **各則在這個趨勢裡的位置**：誰在解決哪一段、彼此是互補還是競爭。
3. **差異與矛盾**：如果它們的主張互相打架，明講出來，不要和稀泥。
4. **對使用者的意義**：所以現在該關注什麼、可以先不管什麼。

不確定屬於哪一型時，選最貼近使用者提問語氣的那一型；混合也可以（例如概念型講完再補一段比較表）。
型態是思考工具，不是要填的表格——某一節在這則沒有實質內容，就不要為了結構完整硬寫。

## Step 4：寫作要求

- **繁體中文**，技術名詞、產品名、程式碼保留原文。
- 每則約 **400–900 字**（含程式碼）。寧可少展開幾則但講透，不要每則都淺淺一層。
- **開頭不要複述日報摘要**。使用者已經讀過了，第一句就該給新東西。
- **分清楚事實與推論**：原文說的、官方文件寫的、你根據經驗推的，用語氣區分開
  （「文中提到……」vs「實務上通常……」）。不確定的就說不確定。
- **主動連結到 repo 裡的既有內容**：這則跟前幾天日報的哪一則是同一個趨勢、跟先前導讀過的哪個
  概念相關，用 `digests/YYYY-MM-DD.md 第 N 則` 的形式標出來。這是這份筆記隨時間越來越有價值的
  關鍵——單篇導讀網路上都有，累積起來的脈絡沒有。

## Step 5：輸出格式（`deep-dives/YYYY-MM-DD-followups.md`）

檔名日期用**產出當天**的日期，不是被追問那份日報的日期（同一份導讀可能同時追問好幾天的日報）。

**檔案不存在**時，建立：

```markdown
# 深入追問筆記 YYYY-MM-DD

<一段說明：這份文件整理使用者針對日報哪幾則的追問，跟 `digests/` 的分工關係>

## 目錄

1. [標題](#1-標題)（追問對象：`digests/YYYY-MM-DD.md` 第 N 則）

---

## 1. 標題

### 小節標題
...
```

**檔案已存在**時（同一天再追問）：讀進來，**接續既有編號**往下加，在目錄追加對應項目，
在檔尾用 `---` 分隔後追加新章節。不要覆蓋、不要重編號——舊編號可能已經被引用過。

## Step 6：開分支與 PR

比照 `AGENTS.md` Step 8 的慣例：

1. 分支名 `deep-dive-YYYY-MM-DD`；已存在就用 `-2`、`-3` 遞增，不要覆蓋既有分支或 PR。
2. 從 `main` 建分支，寫入 `deep-dives/YYYY-MM-DD-followups.md`。
3. 開 PR（base `main`），title「深入追問筆記 YYYY-MM-DD」，body 列出這次展開了哪幾則、
   各自的追問對象、用了哪種展開型態、以及有沒有哪則是在無法讀取原文的情況下寫的。
4. **不要自動 merge**，留給使用者決定。

## Step 7：在對話中呈現

導讀的主要消費場景是**對話**，不是 PR diff——使用者現在就想懂。所以把完整內容用繁體中文呈現在
對話裡（不是只給連結說「請看 PR」），最後附上 PR 連結。

呈現完之後，邀請使用者繼續追問或指出哪裡還是沒講清楚。

## Step 8：回饋寫回 `preferences.md`

**觸發條件**：使用者針對這份導讀明確給出喜歡／不喜歡的回饋時才做。

「使用者主動要求深入某個主題」這件事本身，就是很強的偏好訊號——它代表日報選文時該提高這類主題的
比例。所以在使用者確認導讀有幫助後，在同一個分支的 `preferences.md`「回饋紀錄」區塊**追加**一筆
（追加在最後，不要覆蓋舊紀錄），格式固定：

```
- YYYY-MM-DD：[喜歡/不喜歡] 主題或來源名稱——原因（若使用者沒說明原因，寫「未說明」）。
```

例：`- 2026-08-02：[喜歡] 框架架構比較類內容——使用者主動追問要求「多說明框架差異」，顯示偏好這類延伸比較。`

## Step 9：失敗與例外處理

- **找不到使用者指的那一則**：直接問，不要挑一則相近的頂替。
- **原文讀不到**：照 Step 2 誠實標註後繼續，不要放棄整則，也不要假裝讀過。
- **原文內容不足以撐起一則導讀**（例如只是一則公告）：誠實說「這則本身沒有更多可展開的內容」，
  並提供替代——例如改為導讀它背後的技術概念，或連結到同主題更有料的資料。硬撐出一篇空洞的
  導讀，比誠實說沒東西可寫更糟。
- **沒有 GitHub 寫入權限**：回報在第幾步失敗，並把內容完整呈現在對話裡，不要假裝已經開了 PR。
